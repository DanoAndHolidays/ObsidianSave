# Agent 设计题
> Last Format Time：10/6/2026 02:27:25

可以把它设计成一个“**能接需求、会拆任务、能改代码、会自测、能给出可交付结果**”的前端工程 Agent。核心不是“会聊天”，而是“**能稳定完成从需求到 PR/预览/上线前检查的一整条链路**”。

---
## 先定义它到底交付什么
一个端到端前端 Agent，最好不是泛泛地“帮我写代码”，而是明确交付物：

- 页面 / 组件代码
    
- 路由与状态改动
    
- 接口联调
    
- 单测 / E2E 测试
    
- 构建通过
    
- 预览链接 / 截图 / diff
    
- 可合并的 PR，或者至少是可直接落地的 patch
    

也就是说，它的目标是：**把一个模糊需求，变成一个可验证、可审查、可合并的前端变更**。

---
## 推荐的总体架构
可以拆成 6 层：

### 1）入口层：需求理解
负责把自然语言需求变成结构化任务。

输出最好包含：

- 目标
    
- 约束
    
- 影响范围
    
- 风险点
    
- 验收标准
    
- 未知问题清单
    

例如用户说“给列表页加搜索和分页”，Agent 应该先整理成：

- 改哪个页面
    
- 搜索条件有哪些
    
- 分页是服务端分页还是前端分页
    
- 空状态、加载态、错误态怎么处理
    
- 是否需要保留 URL 参数
    
- 是否需要埋点
    


### 2）规划层：任务拆解
把一个大需求拆成可执行子任务。

一个好的拆法通常是：

1. 找到相关页面与组件
    
2. 理解现有数据流
    
3. 设计改动方案
    
4. 修改代码
    
5. 补测试
    
6. 本地校验
    
7. 生成交付说明
    

这里很关键的一点是：  
**Agent 不能一上来就写代码，必须先形成计划。**


### 3）上下文层：代码库理解
这是前端 Agent 成败的核心。

它需要能读到：

- 路由结构
    
- 组件树
    
- 状态管理方式
    
- API 封装
    
- UI 组件库
    
- 设计规范
    
- 测试方式
    
- 构建和发布方式
    

建议做成“分层检索”：

- 先看目录和入口文件
    
- 再找相关页面
    
- 再追数据流
    
- 再看相邻组件和测试
    

不要把整个仓库一次性塞给模型，容易乱。  
更好的方式是：**先定位，再展开，再聚焦**。


### 4）执行层：代码修改器
这层负责真正改文件。

建议能力包括：

- 生成新文件
    
- 修改已有文件
    
- 批量重构
    
- 保持风格一致
    
- 尽量最小化 diff
    
- 保留可回滚性
    

前端场景里，Agent 最常做的其实不是“新写一个页面”，而是：

- 改一个表单
    
- 加一个状态
    
- 调整一个 hook
    
- 改列表筛选逻辑
    
- 补一个测试用例
    

所以执行层要特别擅长：

- 局部修改
    
- 保持现有结构
    
- 不引入无关重构
    


### 5）验证层：自动自测
这是“端到端交付”最重要的一环。

至少要有：

- TypeScript / ESLint 检查
    
- 单元测试
    
- 关键页面渲染检查
    
- 构建检查
    
- 必要时的 E2E 测试
    
- UI 快照或截图对比
    

Agent 不能只“觉得自己写对了”，而要能回答：

- 能不能编译？
    
- 逻辑有没有回归？
    
- 样式有没有跑掉？
    
- 空数据和错误状态是否处理？
    
- 交互是否符合预期？
    


### 6）交付层：结果包装
最终不要只给代码，要给一个“可审查交付包”：

- 做了什么
    
- 为什么这么做
    
- 风险点
    
- 如何验证
    
- 需要人工确认什么
    
- PR 摘要
    

这样它才像一个真正的工程协作者，而不是代码生成器。

## 一个更实用的 Agent 工作流
我建议用这个闭环：

### A. 先问 3 个关键问题
当需求不完整时，Agent 先补齐：

- 目标用户是谁
    
- 预期行为是什么
    
- 验收标准是什么
    

如果信息足够，就直接进入下一步。


### B. 生成实施计划
输出类似：

1. 定位页面和相关数据流
    
2. 找出复用组件和状态管理
    
3. 设计修改方案
    
4. 实施代码变更
    
5. 补充测试
    
6. 运行检查并修复
    
7. 产出交付说明
    


### C. 进入“读—改—验”循环
每轮只做一小步：

- 读现有代码
    
- 改一部分
    
- 立即验证
    
- 发现问题再修
    

不要一口气大改完再验证。  
前端工程里，局部验证比最后统一验收可靠得多。

## Agent 需要具备的关键能力
### 1）代码库定位能力
要能回答：

- 这个功能在哪个页面？
    
- 这个数据从哪来？
    
- 这个状态谁在管？
    
- 这个组件能不能复用？
    

### 2）UI 语义理解能力
前端不是纯逻辑，很多需求是视觉与交互问题。  
Agent 要懂：

- loading / empty / error / disabled
    
- 表单校验
    
- 焦点与可访问性
    
- 响应式布局
    
- 组件层级和遮罩层行为
    

### 3）测试思维
它要天然会想：

- 这个改动会影响哪条主路径？
    
- 边界条件是什么？
    
- 最小复现路径是什么？
    
- 如何自动化验证？
    

### 4）约束意识
Agent 不能每次都“自作主张优化架构”。  
它要知道：

- 什么时候只做最小修改
    
- 什么时候需要重构
    
- 什么时候必须请求确认
    

---
## 很重要的边界设计
一个真正能落地的 Agent，一定要给自己加边界。

### 不要做的事
- 不能在没确认的情况下大范围重构
    
- 不能假设接口字段
    
- 不能为了“更优雅”改掉用户没要求的行为
    
- 不能跳过测试就说完成了
    

### 必须做的事
- 记录每次修改理由
    
- 保留 patch 可审查
    
- 输出失败原因与未完成项
    
- 对不确定部分显式标记

## 推荐的技术模块
如果你要实现它，可以按这些模块搭：

### 1）Task Manager
管理任务状态：

- 待澄清
    
- 已规划
    
- 进行中
    
- 待验证
    
- 已完成
    
- 失败回滚
    

### 2）Repo Indexer
索引仓库：

- 文件树
    
- 关键入口
    
- 路由
    
- 组件
    
- 测试
    
- API 定义
    

### 3）Context Retriever
按任务拉上下文，不全量塞给模型。

### 4）Patch Engine
负责输出代码修改。

### 5）Verifier
负责跑：

- lint
    
- test
    
- build
    
- preview
    
- screenshot diff
    

### 6）Reporter
输出交付摘要和风险清单。

---
## 如果你想做“真正好用”，最好加入人类协同点
前端 Agent 很适合做成“**自动执行 + 人工确认关键点**”的模式。

比如这些地方让用户确认：

- UI 文案
    
- 交互细节
    
- 破坏性重构
    
- 路由变更
    
- 接口契约变更
    
- 上线前最终批准
    

这样既能自动化，又能避免把错误直接推到生产。

---
## 一个成熟形态的体验
理想体验不是“我说一句，它吐一堆代码”，而是：

1. 用户输入需求
    
2. Agent 自动识别范围
    
3. 先给出计划
    
4. 用户确认
    
5. Agent 修改代码并跑验证
    
6. 给出预览、diff、测试结果
    
7. 用户看完后合并
    

这才是真正的端到端交付。

---
## MVP 怎么做最合理
如果你现在要落地，建议先做最小版本：

- 只支持单仓库
    
- 只支持前端页面/组件修改
    
- 只支持读代码 + 改代码 + 跑 lint/test
    
- 先不做复杂自治
    
- 先做“可审查 patch”，不要一开始就做全自动上线
    

这个版本最容易验证价值。

---
## 一句话总结
**端到端前端 Agent = 需求理解器 + 代码库导航器 + 计划器 + 代码修改器 + 自动验证器 + 交付报告器。**

它的关键不是“能不能写代码”，而是**能不能把前端任务稳定地交付到可合并状态**。
