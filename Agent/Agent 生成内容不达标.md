# Agent 生成内容不达标

我不会直接把 Agent 生成的代码当成最终代码，而是把 Agent 当成一个执行效率比较高的协作者，最终质量还是由我负责。

一般我会分几个层次处理：

第一步是先确认需求和验收标准，比如接口契约、状态流转、异常场景、权限要求和性能要求是否明确。如果需求本身不清楚，我会先补充约束，而不是直接让 Agent 大范围生成代码。

第二步是控制修改范围，让 Agent 按照模块或者单个功能拆分提交，避免一次性修改太多文件。生成代码后，我会重点检查：

- 类型是否正确，尤其是接口输入输出和可空字段；
- 是否符合项目现有的分层和组件规范；
- 是否引入了重复逻辑、无用代码或者不必要的抽象；
- loading、error、empty、权限失败等状态是否完整；
- 是否存在性能问题，比如重复渲染、过度订阅和不必要的请求；
- 是否补充了测试，或者至少能够通过现有测试。

然后我会执行 TypeScript 检查、Lint、单元测试、构建和必要的端到端测试，再结合代码 Review 检查具体实现。

比如在 Data 官网项目里，我遇到过 AI 生成的重复组件和无用 Demo 残留，就不是简单接受，而是结合业务职责重新拆分组件，保留通用能力，同时清理冗余实现。类似地，在 Daedalus 里使用 Agent 辅助开发时，我也会先明确数据契约和状态机，再让 Agent 辅助实现，最后由我验证边界逻辑。

### 可以补充的一句话

> 我的原则是：Agent 可以提高编码速度，但不能替代需求判断、架构判断和最终验收。

### 面试官可能继续追问

**问：你具体怎么让 Agent 改得更好？**

可以回答：

> 我会尽量给 Agent 结构化约束，而不是只描述一个模糊目标。比如明确修改文件范围、已有组件、接口类型、不能改变的行为、异常状态和验收标准。如果第一次结果不达标，我会根据具体问题给出可验证的反馈，例如“不要重复请求”“这个字段为空时要保留默认值”“只能修改这个 Slice”，而不是泛泛地说“代码不太好”。
