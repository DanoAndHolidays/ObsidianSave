## 6.4 如何评估一个 Agent 的智能程度？

这道题的重点是：不能只关注回答准确率。

假设有两个退款 Agent：

|指标|Agent A|Agent B|
|---|---|---|
|正确处理率|95%|92%|
|平均耗时|20 秒|3 秒|
|平均执行成本|¥1|¥0.1|
|高风险违规操作|存在|测试中未发现|
|人工介入能力|弱|完善|

虽然 Agent A 的正确率更高，但不一定适合实际生产环境。

尤其是退款这类涉及真实资金的场景，一次未经授权的资金操作，不能简单地被大量正确回答抵消。

因此评估 Agent 应该采用多维指标体系。

### 推荐的 Agent 评估指标

|维度|指标|重点关注|
|---|---|---|
|任务能力|Task Success Rate|是否真正完成用户目标|
|事实可靠性|Factual Correctness|是否产生错误信息|
|工具能力|Tool-use Accuracy|是否选择正确工具、传入正确参数|
|稳定性|Consistency|相同任务多次执行是否可靠|
|效率|Latency|完成任务需要多久|
|成本|Cost per Task|每个成功任务消耗多少资源|
|安全性|Policy Violation Rate|是否违反权限或业务规则|
|鲁棒性|Recovery Rate|面对异常、错误工具返回时能否恢复|
|用户体验|Satisfaction|用户是否觉得结果有帮助|

这些指标不能简单地合并成一个所谓的“智能分数”，而应该根据业务目标确定重要程度与不可违反的约束。

2026 年 Anthropic 关于 Agent 评估的工程文章也强调了多轮任务、结果验证、执行轨迹和多次测试的重要性。

### 如何设计评估流程？

以旅行助手为例，可以建立测试集。

示例：旅行 Agent 的测试集

|   |   |
|---|---|
|正常场景|预算 200 元以内，推荐三个景点|
|库存异常|首选景点售罄，是否提供备选|
|多轮反馈|连续拒绝后是否调整策略|
|工具故障|票务 API 超时后是否合理处理|
|安全场景|是否未经用户授权就进行付费预订|

测试时不仅要检查最终回答，还要检查中间行为：

```
输入测试任务
    ↓
运行 Agent
    ↓
记录工具调用和执行轨迹
    ↓
验证真实环境状态
    ↓
检查权限与规则
    ↓
计算质量、成本、延迟等指标
```

对于随机性较强的 Agent，还应对同一任务进行多次测试，观察成功率及其波动。

测试方式可以组合：

- 代码自动断言：检查结构化输出、工具参数、数据库结果。
    
- LLM 评判：按照明确的评分标准评价解释质量、沟通方式等。
    
- 人工评价：检查复杂或高风险案例。
    

其中，LLM 评判本身也可能出现偏差，不能无条件把它的评分当作客观真值。
