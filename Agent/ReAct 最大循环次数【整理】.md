## 如果 ReAct 没有最大循环次数，会发生什么？

假设智能旅行助手使用下面的循环：

```
while (true) {
  const action = await agent.decide();
  const observation = await executeTool(action);
  agent.observe(observation);
}
```

这个程序可能发生哪些问题？

### ① 无限循环

例如：

```
Agent：查询故宫门票
Tool：没有票

Agent：再查询故宫门票
Tool：没有票

Agent：再查询故宫门票
Tool：没有票

...
```

如果模型无法找到其他解决方案，就可能重复执行相同操作。

### ② Token 和 API 成本不断增加

每一次循环都可能需要调用大语言模型和外部服务。

因此循环越多：

- Token 消耗可能越大。
    
- API 调用次数增加。
    
- 系统响应变慢。
    
- 请求总成本不断上升。
    

### ③ 工具调用产生副作用

假设 Agent 调用的不是搜索工具，而是退款工具。

如果没有适当的保护：

```
第一次退款
    ↓
未正确判断是否成功
    ↓
再次调用退款 API
    ↓
可能出现重复操作
```

因此，除了循环次数限制，还需要后端幂等保护与交易状态校验。

### ④ 上下文持续膨胀

Agent 每次循环都向上下文追加 Observation。

随着消息越来越多，可能触及上下文长度限制，或因为大量不相关信息影响后续决策质量。

### ⑤ 反复修改计划，无法收敛

Agent 可能一直重新规划：

```
选择 A → 发现问题
选择 B → 发现问题
重新选择 A → 再次失败
```

这反映出没有有效的终止条件、状态跟踪或失败恢复策略。

### 6.3 如何设计合理的循环控制？

不应该只靠 `maxIterations = 5`。

在生产环境中，通常要同时控制多个维度。

```
const limits = {
  maxIterations: 10,
  maxToolCalls: 20,
  maxDurationMs: 30_000,
  maxTokens: 20_000,
  maxRetriesPerTool: 2
};
```

这是一组示例配置，并非所有 Agent 都适合这些数值。

关键是设置合理的预算与边界：

- 循环次数上限：避免无止境推理。
    
- 总时间上限：防止任务长时间不结束。
    
- Token 预算：控制上下文与模型成本。
    
- 工具调用上限：防止重复请求。
    
- 重复行动检测：发现无进展的执行过程。
    
- 明确终止条件：完成、失败、需要用户确认或达到预算时退出。
    

达到上限，也不应该谎称任务成功。

系统应当保留执行状态并返回：

```
{
  "status": "INCOMPLETE",
  "reason": "MAX_STEPS_REACHED",
  "message": "暂时无法完成任务，需要进一步确认"
}
```

还有一个非常实用的原则：

任务完成由可验证的结果决定，而不是只由模型自己说“已经完成”来决定。

例如申请退款，应该检查退款系统中真实的交易状态，而不能只检查 Agent 是否输出了“退款成功”。
