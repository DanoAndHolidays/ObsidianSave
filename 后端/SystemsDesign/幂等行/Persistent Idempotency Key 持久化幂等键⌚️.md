# Persistent Idempotency Key 持久化幂等键
幂等性（Idempotency）：同一个业务操作执行一次和执行多次，最终产生的业务效果相同。

幂等键（Idempotency Key）：用于唯一标识一次业务操作，帮助服务端识别重复请求。

持久化幂等键：将幂等键及其执行状态、结果保存到 Redis、MySQL 等存储中，避免因服务重启或多实例部署导致去重信息丢失。

允许请求重复发送，但==避免业务逻辑重复执行==

- 支付、转账：防止重复扣款

- 订单创建：防止生成重复订单

- 消息队列：消费者重复消费时避免重复处理

- 网络请求重试：超时重试时防止业务重复执行

---
## 工作原理
客户端为每次业务操作生成唯一的 Key：
```
POST /api/payment
Idempotency-Key: pay-123456
```

服务端处理流程：

1. 收到请求，提取幂等键
2. 通过原子操作检查并占用 Key
3. 如果是首次请求，执行业务并保存执行结果
4. 如果是重复请求，不再执行业务，返回已有结果或处理中状态

例如支付 100 元：
```
第一次请求：pay-123 → 支付成功，保存结果
第二次请求：pay-123 → 不重复扣款，返回原结果
第三次请求：pay-123 → 不重复扣款，返回原结果
```

## 持久化存储方案

|方案|优点|注意事项|
|---|---|---|
|Redis|高性能，支持 SET NX 原子操作、TTL|需考虑数据丢失、过期和业务一致性|
|MySQL|唯一索引、事务支持，持久性更强|数据库写入开销相对较大|

MySQL 表结构示例：
```sql
CREATE TABLE idempotency_record (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    idempotency_key VARCHAR(128) NOT NULL UNIQUE,
    status VARCHAR(20) NOT NULL,
    result JSON
);
```

常见执行状态：

- PROCESSING：正在处理
- SUCCESS：执行成功
- FAILED：执行失败，需要根据业务判断能否重试

---
## 注意事项

- 保证原子性，==不能==简单使用==先查询，再插入==，否则并发请求可能同时通过检查，可以利用 Redis `SET NX` 或 MySQL 唯一索引进行原子抢占

- 保证事务一致性，如果业务执行成功，但保存幂等结果失败，仍然可能造成重复执行，对于 MySQL 内部的业务操作，最好将业务==数据修改==和==幂等记录写入==放在==同一个数据库事务==中

- 处理过期时间，Redis 中的幂等键通常==设置 TTL==，防止无限增长，但过期后可能无法识别历史重复请求

- 校验请求参数，同一个 Key 应对应同一个业务操作，可以保存参数摘要，避免不同请求错误地复用同一个 Key

---
## 面试总结
持久化幂等键是一种防止重复请求产生重复业务效果的机制

客户端通过唯一 Key 标识一次业务操作，服务端将 Key、状态和执行结果持久化到 Redis 或 MySQL 中。重复请求到达时，根据 Key 判断是否已经处理。

实现时重点考虑三个问题：

1. 并发安全：利用原子操作或唯一索引防止重复执行

2. 事务一致性：避免业务成功但幂等记录保存失败

3. 持久化可靠性：避免服务重启、数据丢失或 Key 过期导致去重失效
