# 服务端宕机排查
我会先判断“服务器挂了”到底是前端问题、接口服务问题，还是数据库、网络或者第三方依赖问题，而不是直接认为是服务端宕机

一般是分层进行

---
## 确认影响范围
先看是否所有接口都失败，还是只有某个接口失败：

- 页面静态资源能否正常加载；
- 是所有 API 都返回 5xx，还是单个接口失败；
- 是当前用户失败，还是所有用户都失败；
- 是开发环境、测试环境还是生产环境；
- 是否只有某个地区、控制面、网络或者浏览器失败。

如果只有一个接口失败，通常更可能是业务逻辑、参数或者下游依赖问题；如果所有接口都失败，才更像网关、服务实例、DNS 或部署问题。

---
## 看浏览器和网络请求
通过浏览器 Network 检查：

- 请求是否真正发出；
- DNS、CORS、TLS 是否报错；
- HTTP 状态码是 400、401、403、404、429 还是 500、502、503；
- 请求参数和响应体是否符合预期；
- 是否有 request ID 或 correlation ID。

例如：

- `401` 可能是登录过期；
- `403` 可能是权限问题；
- `429` 可能是限流；
- `500` 更偏向服务端业务异常；
- `502/503` 可能是网关、服务实例或部署问题；
- 请求超时可能是网络、服务阻塞或数据库连接池问题。

---
## 查看服务端日志和监控
如果有权限，我会根据时间范围和 request ID 查看：

- 应用日志；
- 错误堆栈；
- CPU、内存和请求延迟；
- 服务实例是否存活；
- 数据库连接池是否耗尽；
- Redis、消息队列或第三方服务是否异常；
- 最近是否有发布、配置变更或数据库迁移。

也会用健康检查接口或者 `curl` 验证服务是否能响应，但不会只依赖健康检查，因为健康检查正常不代表具体业务接口一定正常。

---
## 检查最近变更
重点排查：

- 最近是否刚发布了前端或后端版本；
- 是否修改了环境变量；
- 是否有数据库迁移；
- 是否改变了接口返回结构；
- 是否新增了某个高流量查询；
- 是否发生证书、域名、网关路由或权限配置变化。

如果和最近发布高度相关，我会优先考虑回滚、关闭 Feature Flag 或切换到稳定版本，而不是在生产环境里直接临时改代码。

---
## 前端侧的处理
如果确认是服务端暂时不可用，前端需要做好降级：

- 给用户明确的错误提示；
- 提供重试入口；
- 对幂等查询使用有限次数的退避重试；
- 避免无限自动重试把服务压垮；
- 保留用户已经填写的表单内容；
- 对提交类操作避免重复提交；
- 对 MCP 这种连接场景区分加载中、授权中、授权失败、撤销和重定向状态；
- 上报必要的错误信息和 request ID，方便后续定位。

### 总结成一句话

> 我的排查思路是从现象到范围，再到状态码、日志、监控、依赖和最近变更；同时前端要做好错误反馈、有限重试、数据保护和降级，而不是只显示一个空白页面。
