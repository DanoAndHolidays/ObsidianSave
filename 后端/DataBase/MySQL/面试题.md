## 1）索引到底解决什么问题
数据库最原始的查找方式，是**全表扫描**：

```sql
SELECT * FROM users WHERE email = 'a@example.com';
```

如果没有索引，数据库可能要一行一行看，直到找到目标。
数据量小的时候还行，数据量大了就慢。

有了索引，数据库可以先在索引里快速定位，再跳到对应行数据。
所以索引最擅长的是这几类场景：

- `WHERE`

- `JOIN`

- `ORDER BY`

- `GROUP BY`

- `LIMIT` 搭配分页


---
## 2）索引的代价是什么
索引不是白送的。

它的代价主要有 4 个：

### 占空间
每个索引都会额外占磁盘和内存。

### 写入变慢
你 `INSERT / UPDATE / DELETE` 一条数据时，数据库不只是改表，还要同步维护索引。

### 太多索引会拖累优化器
索引越多，数据库选择执行计划时越复杂，也更容易选错。

### 可能建了也没用
有些索引设计不对，查的时候根本用不上，白白增加成本。

---
## 3）你现在最该建立的思维：不是“字段要不要索引”，而是“这条 SQL 能不能被索引优化”
这是最关键的。

不要问：

- 这个字段看起来重要吗？

- 这个字段要不要加索引？


要问：

- 这条查询最常见的过滤条件是什么？

- 这条查询是按什么顺序排序的？

- 这条查询会不会经常连表？


**索引是为查询服务的，不是为字段本身服务的。**

---
## 4）索引的几种常见类型
### 主键索引
```ts
id: text("id").primaryKey()
```

主键一定是高频定位字段。
它通常天然就有索引能力。

适合：

- 按 id 查详情

- 按 id 关联其他表



### 唯一索引
```ts
email: text("email").notNull().unique()
```

它的作用有两层：

- 保证唯一，不允许重复

- 也能加快按这个字段查询


邮箱、手机号、用户名这类“不能重复”的字段，通常很适合。


### 单列索引
```sql
CREATE INDEX idx_users_created_at ON users(created_at);
```

适合这种情况：

```sql
WHERE created_at >= ...
ORDER BY created_at
```


### 联合索引
```sql
CREATE INDEX idx_users_created_id ON users(created_at, id);
```

这是多个字段按顺序组成的一个索引，不是两个独立索引。

它最重要的一点是：

**顺序非常重要。**

---
## 5）单列索引和联合索引到底差在哪
### 单列索引
只针对一个字段。

```sql
CREATE INDEX idx_email ON users(email);
```

适合：

```sql
WHERE email = ?
```


### 联合索引
针对多个字段，按顺序组织。

```sql
CREATE INDEX idx_user_status_created ON orders(user_id, status, created_at);
```

适合：

```sql
WHERE user_id = ? AND status = ?
```

或者：

```sql
WHERE user_id = ? AND status = ? AND created_at >= ?
```


### 关键区别：联合索引不是“拼接版单列索引”
这是很多人最容易误解的地方。

联合索引 `(a, b)` 的行为，和两个单列索引 `a` + `b` 完全不同。

比如联合索引是：

```sql
(a, b)
```

它通常能很好支持：

- `WHERE a = ?`

- `WHERE a = ? AND b = ?`


但对：

- `WHERE b = ?`


通常就没那么好用。

这就是常说的 **最左前缀原则**。

---
## 6）最左前缀原则，怎么理解
假设联合索引是：

```sql
INDEX(a, b, c)
```

数据库会优先利用从左往右连续的一段前缀。

它通常可以很好支持：

- `a`

- `a, b`

- `a, b, c`


但如果你直接查：

- `b`

- `c`

- `b, c`


通常就不能充分利用这个索引。

---
## 7）联合索引字段顺序怎么排
这是实战里最重要的点之一。

一般可以记这个规律：

### 等值条件放前面
比如：

```sql
WHERE user_id = ? AND status = ? AND created_at >= ?
```

通常更适合：

```sql
(user_id, status, created_at)
```

因为：

- `user_id = ?` 是等值

- `status = ?` 也是等值

- `created_at >= ?` 是范围条件


### 范围条件放后面
像：

- `>`

- `<`

- `BETWEEN`

- `LIKE 'abc%'`


这种范围型条件，通常放在后面更合理。

### 排序字段可以考虑放后面
如果你经常：

```sql
WHERE user_id = ?
ORDER BY created_at DESC
```

那么：

```sql
(user_id, created_at)
```

往往很合适。

## 8）什么字段适合建索引
优先考虑这几类：

### 经常出现在 WHERE 里的字段
比如：

- `email`

- `user_id`

- `createdAt`

- `tenantId`


### 经常出现在 JOIN 里的字段
比如外键关联字段。

### 经常排序的字段
比如：

- `createdAt`

- `updatedAt`

- `score`


### 唯一字段
比如：

- 邮箱

- 手机号

- 编号


---
## 9）什么字段不适合单独建索引
### 区分度很低的字段
比如：

- `gender`

- `status`

- `isDeleted`


这些字段值太少了，单独索引常常收益不大。

因为数据库查到索引以后，还是会回表找很多行，效果不一定好。

### 很少查询的字段
没人查它，就没必要建。

### 表特别小的字段
表就几十行、几百行，直接扫表可能更快。

### 写入特别频繁的字段
如果表是高频写入，索引太多会拖慢写操作。

## 10）你现在这张 users 表，怎么理解索引设计
你给的这段：

```ts
email: text("email").notNull().unique(),
```

这个很合理。

因为邮箱通常：

- 要查

- 要唯一

- 经常用于登录或查找用户


再看：

```ts
index("idx_users_created_id").on(table.createdAt, table.id)
```

这个也很典型，常用于：

- 按创建时间分页

- 时间倒序列表

- 游标分页


比如：

```sql
WHERE created_at < ?
ORDER BY created_at DESC, id DESC
LIMIT 20
```

这种结构就很适合联合索引。

---
## 11）分页场景里，索引特别重要
这是很多人容易忽略的。

### 偏移分页
```sql
SELECT * FROM users ORDER BY created_at DESC LIMIT 20 OFFSET 100000;
```

这种在大表里会越来越慢，因为数据库要跳过很多行。

### 游标分页
```sql
SELECT * FROM users
WHERE created_at < ?
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

这种就很吃索引。

所以你看到很多系统会建：

```sql
(created_at, id)
```

就是为了稳定支持分页和排序。

---
## 12）索引不等于一定会被用上
这是第二个大坑。

你建了索引，不代表数据库一定走索引。

数据库会自己判断：

- 用索引快不快

- 走索引后要不要回表太多次

- 数据量大不大

- 选择性高不高


所以你不能“建完就信”，要看执行计划。

---
## 13）怎么看索引有没有生效
常用的是：

```sql
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'a@example.com';
```

你重点看：

- 有没有走 `Index Scan`

- 是不是 `Seq Scan`（全表扫描）

- 实际耗时是多少

- 扫了多少行


如果你发现：

- 索引建了

- 但执行计划还是全表扫


那说明这个索引可能没被用上，或者 SQL 写法不利于使用索引。

---
## 14）哪些写法会让索引失效或变差
这是非常实用的一部分。

### 在索引列上做函数计算
比如：

```sql
WHERE DATE(created_at) = '2026-09-22'
```

这类写法往往不利于直接用索引。

更好的是：

```sql
WHERE created_at >= '2026-09-22'
  AND created_at < '2026-09-23'
```


### 前缀模糊匹配不一定好，前面带 `%` 更差
```sql
WHERE name LIKE '%tom%'
```

这类通常很难很好利用普通 B-tree 索引。

如果是：

```sql
WHERE name LIKE 'tom%'
```

相对更有机会用上索引。


### 类型不一致
比如列是 `text`，你查询时传了奇怪的类型，数据库可能要做隐式转换，影响索引使用。


### 条件写得太复杂
比如在 `WHERE` 里包了一层函数、`OR` 很多、表达式复杂，都会影响优化器选择。

## 15）什么时候需要“覆盖索引”思维
覆盖索引的意思是：
**查询需要的字段，索引里已经全有了，数据库可能连表都不用回。**

比如你查：

```sql
SELECT created_at, id
FROM users
WHERE created_at > ?
ORDER BY created_at, id;
```

如果索引里就有 `created_at, id`，数据库可能就能直接从索引里拿结果，少一次回表。

这在大表里很有价值。

---
## 16）数据库里还有两种更高级的索引思路
你先知道概念就行，不一定马上用。

### 部分索引
只给满足某个条件的数据建索引。

比如只给未删除数据建：

```sql
WHERE deleted_at IS NULL
```

适合软删除场景。

### 表达式索引
给表达式结果建索引，比如：

```sql
LOWER(email)
```

适合需要大小写不敏感查询的场景。

## 17）实战里怎么决定要不要加索引
你可以按这个流程走：

### 第一步：看查询
找最常见、最慢的 SQL。

### 第二步：看条件
它是 `WHERE`、`JOIN`、`ORDER BY` 里的哪些列。

### 第三步：看组合
经常一起出现的条件，考虑联合索引。

### 第四步：看顺序
等值条件优先，范围条件放后面。

### 第五步：验证
用 `EXPLAIN ANALYZE` 看效果。

## 20）最后给你一个最重要的结论
**索引不是“越多越好”，而是“越贴合查询越好”。**

真正好的索引设计，通常来自这三件事：

1. 你知道最常见的 SQL 是什么

2. 你知道这些 SQL 在 `WHERE / JOIN / ORDER BY` 里用到了什么字段

3. 你知道这些字段应该怎么排序才能匹配查询
