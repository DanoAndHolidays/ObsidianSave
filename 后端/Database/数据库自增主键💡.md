# 数据库自增主键
数据库自增主键（`AUTO_INCREMENT`）并不是不推荐使用，而是在分布式、高并发、分库分表等场景下存在一定局限性

实际上，如果你的项目使用的是 MySQL 单库架构，自增主键通常是非常合适的选择

如果需要替代，主要有三种方案：

- 雪花算法（Snowflake ID）：分布式系统中常见，生成 64 位整数 ID。
- UUID v7：128 位 ID，具备时间有序特性，适合分布式生成。
- 号段模式（如 Leaf-segment）：从数据库批量申请一段 ID，在应用侧分配。

自增主键在 MySQL InnoDB 中有几个明显优点：

1. 索引性能好：InnoDB 使用 B+ 树组织聚簇索引，递增 ID 通常在索引右侧插入，减少随机页分裂。

2. 存储空间小：`BIGINT` 占 8 字节，作为聚簇索引键较紧凑。

3. 实现简单：数据库负责生成 ID，业务代码不需要额外维护 ID 生成器。

4. 查询效率高：整数比较成本低，二级索引中存储的主键值也比较紧凑。

因此，在单库业务中，自增主键是一个很成熟的方案 [[03 优化]]

## 不推荐情况
### 分布式环境下容易发生主键冲突
假设你的项目发展到一定规模，需要将用户数据拆分到两个数据库中：

两个数据库都生成了 ID = 1、2、3，无法直接保证全局唯一
![[Pasted image 20261018164221.png]]

注意：单个数据库的自增主键能保证表内唯一，但多个独立数据库的自增序列不能天然保证全局唯一，当需要跨分片合并、迁移数据或者建立全局关联时，就容易出现 ID 冲突

自增 ID 也可以通过==设置不同起点==、步长或使用统一发号服务解决，但这会增加维护成本

当我我们根据 ID 去水平拆分的时候，会导致数据库中的最后一个库频繁的被插入，造成==尾部热点==问题：![[Pasted image 20261018165624.png]]

使用其他的字段去取模等操作可以解决

### 容易暴露业务信息
例如用户注册接口返回：
```
{
  "id": 10001,
  "username": "Alice"
}
```

下一个用户 ID 是 `10002`，攻击者就可能通过观察 ID 的增长，推测用户数量或者业务增长情况。

另外，如果接口设计不合理，还可能被枚举访问：
```
GET /api/users/10001
GET /api/users/10002
GET /api/users/10003
```

不过需要注意：ID 不可预测并不等于安全。无论采用什么 ID，都必须进行==身份认证和资源权限校验==

### 生成 ID 依赖数据库
假设你想实现：
```
Long userId = generateId();

saveToDatabase(userId);

sendMessage(userId);
```

使用数据库自增主键，通常需要先执行插入，再获取生成的 ID。

而使用雪花算法等应用侧 ID 生成方案，可以在插入数据库之前拿到 ID。

这在异步任务、消息队列、跨服务调用等场景中很有价值。

### 高并发下存在一定扩展限制
InnoDB 为自增值分配提供了不同锁模式。现代 MySQL 默认使用更适合并发插入的模式，因此不能简单地认为自增主键会导致所有插入串行执行，

真正需要考虑的是：当系统跨多个数据库节点扩展时，自增序列的管理会变得复杂

## 代替方案
### Snowflake 雪花算法
这是 Java 分布式系统中比较常见的选择

它的核心思想是：通过时间戳、机器编号和序列号共同生成全局唯一的整数 ID

典型的 Snowflake 结构：第一 bit 永远是 0 

![[Pasted image 20261018164846.png]]

经典 Snowflake 算法的特点：

- 不依赖数据库生成 ID
- 不同机器通过 Worker ID 区分，避免重复

- 趋势递增，对 MySQL B+ 树较为友好
- 使用 `BIGINT` （8 bytes）即可存储

- 需要处理==时钟回拨==、==机器编号冲突==等问题

经典配置下，每个毫秒，最多支持 1024（2^10） 个机器，每个机器最多生成 4096（2^12） 个 ID

### UUID v7
Java 的：
```
UUID.randomUUID().toString();
```

形式：8-4-4-4-12，36个字符
```
xxxxxxxx-xxxx-MMMM-NNNN-xxxxxxxxxxxx
```

M的四位是版本号，N为变体

它一般生成 UUID v4，随机性较强，但作为 MySQL 聚簇主键，UUID v4 的随机插入可能造成频繁的==索引页分裂==，降低缓存局部性

UUID v7 将时间戳放在高位，具有按时间大致有序的特性，能改善 UUID v4 的随机索引插入问题

它的优势是不需要统一发号中心；代价是占用 ==128 bit 空间，浪费空间==，相比 64 位 Snowflake ID 更大。

在 MySQL 中，可以使用 `BINARY(16)` 存储 UUID 的原始 16 字节，避免直接使用较长的字符串主键。

### 号段模式
例如数据库中记录：
```
当前可分配的 ID 区间：

10000 ～ 10999
```

应用服务器一次性申请 1000 个 ID，随后在内存中依次分配：
```
10000
10001
10002
...
```

用完后再从数据库申请下一段

这样既保留整数 ID 的优势，也减少了每次生成 ID 时对数据库的访问

不过要设计好号段分配的原子性，以及服务器异常时未使用号段的处理策略
