# 内容审核与变更标记规则

本文规定机械格式化之后的语义审核流程。凡是改变笔记表达、事实、代码含义或内容顺序的调整，都必须可追溯；不能只在最终回复中概括，也不能依赖 Git diff 才能看懂。

## 审核范围

逐篇完整阅读候选笔记，至少检查：

- **流畅性**：病句、指代不明、口语残片、上下文跳跃。
- **事实正确性**：概念、API 行为、版本差异、因果关系是否准确。
- **代码正确性**：语法、类型、运行结果、注释与正文是否一致。
- **结构顺序**：是否先定义再使用、先结论后解释、前置知识是否放在依赖它的内容之前。
- **完整性与去重**：关键前提是否缺失，重复内容是否影响理解。
- **术语一致性**：同一概念是否混用不同名称或大小写。

不因为“可以写得更多”而扩写。只修复有明确收益的问题，保留作者语气、学习阶段和仍有价值的疑问。

## 证据与修改权限

- 流畅性、顺序调整、明显重复和术语统一，可在高把握时直接修改。
- 事实纠错、代码修正和带事实判断的补充说明，必须先验证；前端主题优先使用 ECMAScript/WHATWG/W3C 规范、MDN、TypeScript/React/Vue/库官方文档、项目源码与测试。
- 信息可能受版本或时间影响时必须联网核对，不凭记忆修改。
- 来源冲突、无法确认或会改变作者核心观点时，不猜测；记录问题并询问用户。
- 不修改 frontmatter、标签体系、目录、附件和双链目标，除非用户明确授权。

## 可见锚点

每个语义调整使用文件内唯一编号 `CR-001`、`CR-002`……。在调整后的内容旁放置可见锚点：

```markdown
`useEffect` 的清理函数会在下一次 effect 执行前以及组件卸载时运行。〔CR-001〕
```

- 段落或列表调整：锚点放在调整后文本末尾。
- 标题调整：锚点单独放在标题下一行。
- 代码调整：锚点放在代码块闭合围栏后的下一行，不能写进代码块。
- 删除或去重：锚点放在最接近的保留内容末尾。
- 顺序调整：锚点放在内容的新位置。
- 一个锚点只对应一个连贯、可独立说明的调整；不得用一个编号笼统覆盖整篇笔记。

纯机械格式变化（标题层级、分隔符、空行、代码围栏标签等）由脚本统计和 Git diff 追踪，不添加 `CR` 标记。

## 变更记录

存在 `CR` 锚点时，必须在笔记末尾追加唯一的 `## 内容审核变更记录`，每个锚点有且只有一条记录：

```markdown
---
## 内容审核变更记录
### CR-001｜事实纠错
- 日期：8/13/2026
- 位置：`effect 清理时机` 第 2 段
- 原内容：清理函数只会在组件卸载时执行。
- 调整后：清理函数会在下一次 effect 执行前以及组件卸载时执行。
- 原因：原描述遗漏了依赖变化后重新执行 effect 前的清理阶段。
- 依据：[React 官方文档：Synchronizing with Effects](https://react.dev/learn/synchronizing-with-effects)
```

允许的类型：

- `流畅性`
- `事实纠错`
- `顺序调整`
- `补充说明`
- `删减去重`
- `代码修正`
- `术语统一`

每条记录必须包含日期、位置、原内容、调整后、原因、依据六个字段。仅润色、重排、去重或术语统一可将依据写为 `无需外部依据（措辞调整）` 等明确说明；事实纠错和代码修正不得写“无需外部依据”。

若原内容很长，可准确摘录足以识别调整的片段；顺序调整必须同时写明原位置和新位置；删除内容时，“调整后”写明删除或合并到哪里。

后续再次审核时，保留既有变更记录和编号；新编号从当前最大编号继续递增。审核变更记录本身不参与语义改写，只校验结构与可追溯性。

## 完成条件

一篇笔记只有同时满足以下条件才算完成：

1. 已完整阅读正文和代码示例，而非只看脚本报告的行号。
2. 高把握问题已修复，低把握问题已向用户说明。
3. 每个语义调整都有可见锚点和一一对应的完整记录。
4. 事实/代码调整已有可靠依据。
5. 机械格式复检为零，内容审核标记校验也为零。
