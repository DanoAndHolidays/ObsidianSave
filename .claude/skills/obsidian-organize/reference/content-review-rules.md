# 内容审核与变更标记规则

本文规定机械格式化之后的语义审核流程。凡是改变笔记表达、事实、代码含义或内容顺序的调整，都必须在修改位置附近留下清晰、简短的标记；不能只在最终回复中概括，也不能依赖 Git diff 才能看懂。

## 审核范围

逐篇完整阅读候选笔记，至少检查：

- **流畅性**：病句、指代不明、口语残片、上下文跳跃。
- **事实正确性**：概念、API 行为、版本差异、因果关系是否准确。
- **代码正确性**：语法、类型、运行结果、注释与正文是否一致。
- **结构顺序**：是否先定义再使用、先结论后解释、前置知识是否放在依赖它的内容之前。
- **完整性与去重**：关键前提是否缺失，重复内容是否影响理解。
- **术语一致性**：同一概念是否混用不同名称或大小写。

不因为“可以写得更多”而扩写。只修复有明确收益的问题，保留作者语气、学习阶段和仍有价值的疑问。

## 证据与修改权限

- 流畅性、顺序调整、明显重复和术语统一，可在高把握时直接修改。
- 事实纠错、代码修正和带事实判断的补充说明，必须先验证；技术主题优先使用官方规范、官方 API 文档、项目源码与测试。
- 信息可能受版本或时间影响时必须联网核对，不凭记忆修改。
- 来源冲突、无法确认或会改变作者核心观点时，不猜测；记录问题并询问用户。
- 不修改 frontmatter、标签体系、目录、附件和双链目标，除非用户明确授权。

## 局部标记

语义调整完成后，在修改位置附近添加以下标记之一：

- `*已修改*`：修改或重写已有内容，默认优先使用。
- `*已补充*`：新增原笔记没有的重点内容。
- `*已纠正*`：纠正事实、代码或容易误导的表述。

示例：

```markdown
`byte`、`short` 和 `char` 参与算术运算时会先提升为 `int`。 *已纠正*
```

- 段落或列表调整：标记放在调整后文本末尾。
- 标题调整或大段重写：标记可单独放在标题下一行，避免每句话都加。
- 代码调整：标记放在代码块闭合围栏后的下一行，不能写进代码块。
- 删除或去重：标记放在最接近的保留内容末尾。
- 顺序调整：标记放在内容的新位置。
- 纯机械格式变化（标题层级、分隔符、空行、代码围栏标签等）不添加标记。

不要使用 `〔CR-xxx〕`、`CR-001` 等编号锚点，也不要追加 `## 内容审核变更记录`。校验脚本会拒绝遗留的旧协议标记；它不会要求局部标记一一对应，也不会把合规的局部标记当作问题。

## 完成条件

一篇笔记只有同时满足以下条件才算完成：

1. 已完整阅读正文和代码示例，而非只看脚本报告的行号。
2. 高把握问题已修复，低把握问题已向用户说明。
3. 每个语义调整都在修改位置附近有合规局部标记；纯机械格式化不添加标记。
4. 事实/代码调整已有可靠依据，必要时在正文或任务说明中保留来源。
5. 机械格式复检为零，旧协议残留与非法标记校验也为零。
