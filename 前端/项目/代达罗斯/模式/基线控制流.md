# 基线控制流
> Last Format Time：8/13/2026 15:14:03

*这算不算黑化话呢*

这里的“基线控制流”不是 JavaScript 里的正式术语，更像是代码评审/迁移时的一种说法。

你可以把它拆成两个词理解：

**基线 = 原来那套已经存在、已经验证过的标准实现。**
**控制流 = 程序在什么条件下走哪条分支、调用什么函数、修改什么状态。**

所以：

> **复制基线控制流**
>
> 基本就是：为了实现一个相似的新交互，把原来那套 `if / switch / handler / 状态修改` 又复制一遍，只是换了几个变量或事件。

比如你原来有一个“点击按钮创建 Team”的逻辑：

```ts
const handleCreateTeamClick = () => {
  if (!canCreate) {
    setCreateErrMsg("没有权限");
    return;
  }

  setShowCreate(true);
};
```

后来需求增加：

* 点击按钮创建
* 按 Enter 创建
* 按快捷键 A 创建

一种比较差的写法可能是：

```ts
const handleButtonClick = () => {
  if (!canCreate) {
    setCreateErrMsg("没有权限");
    return;
  }

  setShowCreate(true);
};

const handleEnter = () => {
  if (!canCreate) {
    setCreateErrMsg("没有权限");
    return;
  }

  setShowCreate(true);
};

const handleShortcutA = () => {
  if (!canCreate) {
    setCreateErrMsg("没有权限");
    return;
  }

  setShowCreate(true);
};
```

这里后两个事件，其实就是把第一个已经存在的“基线控制流”复制了一遍。

而你截图里的规则是：

> 多个交互表达同一用户意图时，优先复用同一个业务动作；只要状态结果和副作用一致，就不必复制基线控制流。

意思就是应该写成：

```ts
const handleCreateTeamClick = () => {
  if (!canCreate) {
    setCreateErrMsg("没有权限");
    return;
  }

  setShowCreate(true);
};
```

然后三个入口都调用它：

```ts
// 点击
onClick={handleCreateTeamClick}

// Enter
if (event.key === "Enter") {
  handleCreateTeamClick();
}

// 快捷键 A
if (event.key === "a") {
  handleCreateTeamClick();
}
```

这里可以把它理解成：

```text
用户意图：我要创建 Team
               ↓
       handleCreateTeamClick
               ↓
      ┌───────────────────┐
      │ 权限判断           │
      │ 错误处理           │
      │ 修改 showCreate    │
      │ 修改 createErrMsg  │
      └───────────────────┘
        ↑       ↑       ↑
      click   Enter     A
```

三个事件只是**不同的入口**，真正的业务动作只有一个。

---
## 那为什么叫“基线”？
比如最开始只有鼠标点击：

```ts
onClick → handleCreateTeamClick → 修改状态
```

这一套是已经存在、已经工作的实现，它就可以被当作这次迁移/改造的**baseline（基线）**。

后来你加入键盘操作，如果写成：

```ts
Enter → 又写一遍权限判断 → 又修改状态
A     → 又写一遍权限判断 → 又修改状态
```

这就相当于：

> 把基线里的控制流程复制到了新事件里。

问题是以后基线改了：

```ts
const handleCreateTeamClick = () => {
  if (!canCreate) return;

  track("create_team"); // 新增埋点

  setCreateErrMsg(null);
  setShowCreate(true);
};
```

如果 Enter 的代码是复制出来的，你很容易忘记同步：

```ts
if (event.key === "Enter") {
  if (!canCreate) return;

  // ❌ 忘了 track
  // ❌ 忘了清 createErrMsg

  setShowCreate(true);
}
```

于是就出现：

```text
鼠标点击：正确
Enter：行为不一致
快捷键 A：可能又是另一套行为
```

这就是截图里那句话真正想防止的问题。

所以你可以先记一个非常实用的理解：

> **基线 = 原本正确的参考实现。**
>
> **基线控制流 = 原本那套“判断 → 调用 → 状态变化 → 副作用”的执行流程。**
>
> 如果新的交互只是“另一种方式表达同一个意图”，最好直接调用原来的业务函数，而不是把那套流程复制一遍。

你截图里让你“分别构造 `Enter`、`Escape`、`A` 三个事件，spy `handleCreateTeamClick` 并观察 `showCreate/createErrMsg`”，其实就是在检查：**键盘交互是不是复用了同一套业务语义，而不是偷偷长出了另一套控制流。**
