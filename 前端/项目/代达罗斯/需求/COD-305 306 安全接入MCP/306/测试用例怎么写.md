# 测试用例怎么写
> Last Format Time：8/13/2026 15:14:04

这段代码是在用 **Vitest 给 MCP 相关的数据结构和 Zod Schema 写单元测试**。

它一共验证了三条规则：

1. MCP 工具名称不能重复。
2. 分页查询一次最多取 50 条，默认取 20 条、从第 0 条开始。
3. 用户没有传确认参数时，必须视为“未确认”。


# 一、先认识 Vitest 的基本结构

Vitest 是一个 JavaScript/TypeScript 测试框架。最常见的测试结构是：

```ts
describe("测试分组", () => {
  it("应该有什么行为", () => {
    expect(实际结果).toBe(预期结果);
  });
});
```

可以把它理解为：

```ts
describe("我要测试谁", () => {
  it("它应该怎么表现", () => {
    expect(实际表现).符合某个预期();
  });
});
```

Vitest 官方把 `describe` 用于组织一组相关测试，`it` 和 `test` 基本是同一种写法，`expect` 用来创建断言。([Vitest][1])

你的代码开头：

```ts
import { describe, expect, it } from "vitest";
```

分别表示：

* `describe`：创建一个测试分组。
* `it`：定义一条具体测试。
* `expect`：检查实际结果是否符合预期。


# 二、整体结构是什么意思

```ts
describe("MCP tool schemas", () => {
  // 三个具体测试
});
```

意思是：

> 创建一个名为 `"MCP tool schemas"` 的测试分组，里面的测试都和 MCP 工具的 Schema 有关。

运行测试时，你大概会看到类似：

```text
MCP tool schemas
  ✓ keeps every tool name unique
  ✓ caps list queries at 50 rows
  ✓ does not treat a missing confirmation as confirmed
```

每个 `it` 都是一条独立规则。


# 三、第一个测试：工具名称不能重复

```ts
it("keeps every tool name unique", () => {
  const names = McpToolCatalog.map((tool) => tool.name);

  expect(new Set(names).size).toBe(names.length);
});
```

测试名称的意思是：

> 保证每个 MCP 工具的名称都是唯一的。

假设 `McpToolCatalog` 长这样：

```ts
const McpToolCatalog = [
  { name: "list_projects" },
  { name: "create_project" },
  { name: "delete_project" },
];
```

---
## 第一步：取出所有名称
```ts
const names = McpToolCatalog.map((tool) => tool.name);
```

`map` 会遍历数组，并返回每个工具的 `name`。

得到：

```ts
[
  "list_projects",
  "create_project",
  "delete_project",
]
```

也就是：

```ts
const names = [
  "list_projects",
  "create_project",
  "delete_project",
];
```

---
## 第二步：使用 Set 去重
```ts
new Set(names)
```

JavaScript 的 `Set` 集合不会保存重复值。

例如：

```ts
const names = ["create", "delete", "create"];

const nameSet = new Set(names);
```

此时：

```ts
names.length;
```

结果是：

```ts
3
```

但是：

```ts
nameSet.size;
```

结果是：

```ts
2
```

因为重复的 `"create"` 只会保留一个。

---
## 第三步：比较去重前后的数量
```ts
expect(new Set(names).size).toBe(names.length);
```

可以拆成：

```ts
const uniqueNameCount = new Set(names).size;
const originalNameCount = names.length;

expect(uniqueNameCount).toBe(originalNameCount);
```

如果没有重复：

```ts
names = ["create", "delete", "update"];
```

那么：

```ts
new Set(names).size === names.length
3 === 3
```

测试通过。

如果有重复：

```ts
names = ["create", "delete", "create"];
```

那么：

```ts
new Set(names).size === names.length
2 === 3
```

测试失败。

因此这条测试可以防止出现：

```ts
const McpToolCatalog = [
  { name: "create_project" },
  { name: "create_project" }, // 重复了
];
```

MCP 工具通常依靠名称进行查找或调用，工具名重复可能导致工具注册冲突或者不知道应该调用哪一个。


# 四、第二个测试：分页参数限制和默认值

```ts
it("caps list queries at 50 rows", () => {
  expect(mcpPageInputSchema.safeParse({ limit: 51 }).success).toBe(false);
  expect(mcpPageInputSchema.parse({})).toEqual({ limit: 20, offset: 0 });
});
```

测试名称的意思是：

> 列表查询一次最多允许获取 50 条数据。

这里测试了两件事：

1. `limit: 51` 应该验证失败。
2. 什么参数都不传时，应该使用默认分页参数。

---
## 验证 limit 不能超过 50
```ts
mcpPageInputSchema.safeParse({ limit: 51 })
```

`mcpPageInputSchema` 看名字应该是一个 Zod Schema。实际定义可能类似下面这样：

```ts
const mcpPageInputSchema = z.object({
  limit: z.number().int().min(1).max(50).default(20),
  offset: z.number().int().min(0).default(0),
});
```

这只是根据测试推测出来的示意代码，不一定和项目里的实现完全一样。

其中：

```ts
.max(50)
```

表示 `limit` 最大只能是 50。

---
## `safeParse` 是什么
```ts
const result = mcpPageInputSchema.safeParse({
  limit: 51,
});
```

`safeParse` 不会因为校验失败直接抛异常，而是返回一个结果对象。

验证成功时大概是：

```ts
{
  success: true,
  data: {
    limit: 20,
    offset: 0,
  },
}
```

验证失败时大概是：

```ts
{
  success: false,
  error: ZodError,
}
```

所以这里直接读取：

```ts
.safeParse({ limit: 51 }).success
```

结果应该是：

```ts
false
```

Zod 官方说明，`safeParse()` 会返回一个包含 `success` 的结果对象，失败时返回错误信息，而不是要求调用者使用 `try/catch`。([Zod][2])

完整断言：

```ts
expect(
  mcpPageInputSchema.safeParse({ limit: 51 }).success,
).toBe(false);
```

意思是：

> 我预期 `{ limit: 51 }` 不能通过验证。

可以拆成：

```ts
const result = mcpPageInputSchema.safeParse({
  limit: 51,
});

expect(result.success).toBe(false);
```

---
## 验证默认分页参数
```ts
expect(mcpPageInputSchema.parse({})).toEqual({
  limit: 20,
  offset: 0,
});
```

传入的是一个空对象：

```ts
{}
```

说明调用者既没有传 `limit`，也没有传 `offset`。

Schema 应该给它们添加默认值：

```ts
{
  limit: 20,
  offset: 0,
}
```

所以：

```ts
mcpPageInputSchema.parse({})
```

应该返回：

```ts
{
  limit: 20,
  offset: 0,
}
```

这里需要注意：`parse()` 不只是“检查数据”，还会返回经过 Schema 处理后的数据。

例如 Schema 定义了默认值：

```ts
const schema = z.object({
  limit: z.number().default(20),
});
```

那么：

```ts
schema.parse({});
```

返回：

```ts
{
  limit: 20,
}
```

---
## 为什么这里使用 `toEqual`，不用 `toBe`
```ts
expect(...).toEqual({
  limit: 20,
  offset: 0,
});
```

因为这里比较的是对象。

### `toBe`
主要比较值是否严格相同，可以理解为接近：

```ts
Object.is(actual, expected)
```

例如：

```ts
expect(10).toBe(10);
expect(false).toBe(false);
expect("hello").toBe("hello");
```

但是两个内容相同的对象，不是同一个对象：

```ts
const a = { limit: 20 };
const b = { limit: 20 };

a === b; // false
```

因此下面通常会失败：

```ts
expect(a).toBe(b);
```

### `toEqual`
`toEqual` 会递归比较对象里的内容：

```ts
expect(a).toEqual(b);
```

这会通过，因为两个对象的结构和属性值相同。Vitest 官方也将 `toEqual` 定义为结构上的深度比较。([Vitest][3])

---
## 这个测试还可以更严谨一点
当前测试验证了：

```ts
limit: 51 // 失败
```

但没有验证：

```ts
limit: 50 // 成功
```

更完整的边界测试可以写成：

```ts
it("caps list queries at 50 rows", () => {
  expect(
    mcpPageInputSchema.safeParse({ limit: 50 }).success,
  ).toBe(true);

  expect(
    mcpPageInputSchema.safeParse({ limit: 51 }).success,
  ).toBe(false);

  expect(mcpPageInputSchema.parse({})).toEqual({
    limit: 20,
    offset: 0,
  });
});
```

这样同时检查：

```text
50：允许
51：不允许
```

这叫做边界值测试。


# 五、第三个测试：缺少确认参数时默认为 false

```ts
it("does not treat a missing confirmation as confirmed", () => {
  expect(mcpConfirmedActionInputSchema.parse({})).toEqual({
    confirmed: false,
  });
});
```

测试名称可以翻译成：

> 不应该把“缺少确认参数”当成“用户已经确认”。

假设某个 MCP 工具会执行危险操作，例如：

```ts
deleteProject({
  projectId: "123",
  confirmed: true,
});
```

为了避免误操作，Schema 可能要求存在一个 `confirmed` 字段。

Schema 可能类似：

```ts
const mcpConfirmedActionInputSchema = z.object({
  confirmed: z.boolean().default(false),
});
```

当调用者传入：

```ts
{}
```

Schema 会返回：

```ts
{
  confirmed: false,
}
```

测试代码：

```ts
expect(mcpConfirmedActionInputSchema.parse({})).toEqual({
  confirmed: false,
});
```

验证的是：

```text
没有传 confirmed
        ↓
不能自动认为用户确认了
        ↓
confirmed 必须默认为 false
```

这是一种安全默认值，也就是：

> 默认拒绝，而不是默认允许。

如果默认值错误地写成：

```ts
confirmed: true
```

那么用户即使没有明确确认，某些敏感操作也可能被执行。

---
## 这条测试也可以增加正向情况
现在只验证了：

```ts
{} → { confirmed: false }
```

还可以增加：

```ts
it("accepts an explicit confirmation", () => {
  expect(
    mcpConfirmedActionInputSchema.parse({
      confirmed: true,
    }),
  ).toEqual({
    confirmed: true,
  });
});
```

这样可以同时验证：

```text
没有确认：false
明确确认：true
```


# 六、`parse` 和 `safeParse` 的区别

这是这段代码里非常重要的知识点。

---
## `parse`
```ts
schema.parse(data);
```

验证成功：

```ts
const result = schema.parse(validData);
```

直接得到处理后的数据。

验证失败：

```ts
schema.parse(invalidData);
```

会抛出 `ZodError`。

所以你可能需要：

```ts
try {
  const data = schema.parse(input);
} catch (error) {
  console.log("验证失败");
}
```

---
## `safeParse`
```ts
schema.safeParse(data);
```

无论成功失败，都不会直接抛出验证异常，而是返回结果对象：

```ts
const result = schema.safeParse(input);

if (result.success) {
  console.log(result.data);
} else {
  console.log(result.error);
}
```

所以测试非法输入时，经常使用：

```ts
expect(schema.safeParse(invalidData).success).toBe(false);
```

因为这样不需要在测试里写：

```ts
expect(() => schema.parse(invalidData)).toThrow();
```

两种方式都可以。


# 七、整个测试用通俗语言重写

你的代码可以理解成下面这段话：

```ts
describe("MCP 工具的 Schema", () => {
  it("所有 MCP 工具的名称都不允许重复", () => {
    // 取出所有名称
    // 使用 Set 去重
    // 如果去重前后数量相同，说明没有重复名称
  });

  it("列表查询最多只能取 50 条，并且有默认分页参数", () => {
    // 请求 51 条应该失败
    // 不传分页参数时，默认 limit=20、offset=0
  });

  it("用户没有明确确认时，必须认为没有确认", () => {
    // 不传 confirmed 时，默认 confirmed=false
  });
});
```


# 八、Vitest 最常用的匹配器

---
## 判断严格相等
```ts
expect(result).toBe(10);
expect(result).toBe(false);
```

适合原始值：

```ts
number
string
boolean
undefined
null
```

---
## 判断对象、数组内容相等
```ts
expect(result).toEqual({
  name: "Dano",
});
```

```ts
expect(result).toEqual([1, 2, 3]);
```

---
## 判断真假
```ts
expect(result).toBe(true);
expect(result).toBe(false);
```

还可以写：

```ts
expect(result).toBeTruthy();
expect(result).toBeFalsy();
```

不过测试布尔值时，`toBe(true)` 和 `toBe(false)` 通常更精确。

---
## 判断是否抛出异常
```ts
expect(() => {
  schema.parse(invalidData);
}).toThrow();
```

例如第二个测试也可以写成：

```ts
expect(() => {
  mcpPageInputSchema.parse({
    limit: 51,
  });
}).toThrow();
```

---
## 判断数组是否包含元素
```ts
expect(["a", "b", "c"]).toContain("b");
```

---
## 判断数字大小
```ts
expect(10).toBeGreaterThan(5);
expect(10).toBeLessThanOrEqual(10);
```


# 九、Vitest 怎么运行

一般先安装：

```bash
pnpm add -D vitest
```

或者：

```bash
npm install -D vitest
```

然后在 `package.json` 里配置：

```json
{
  "scripts": {
    "test": "vitest",
    "test:run": "vitest run"
  }
}
```

运行监听模式：

```bash
pnpm test
```

监听模式下，修改代码后 Vitest 会重新运行相关测试。

只运行一次：

```bash
pnpm test:run
```

或者直接：

```bash
pnpm vitest run
```

Vitest 官方说明，开发环境下直接运行 `vitest` 默认会进入监听模式，而 `vitest run` 会执行一次后退出。([Vitest][4])

测试文件通常命名为：

```text
mcp-tool-schema.test.ts
```

或者：

```text
mcp-tool-schema.spec.ts
```


# 十、你应该建立的核心理解

一条测试通常就是三个部分：

```ts
it("测试描述", () => {
  // 1. 准备数据
  const input = {};

  // 2. 执行被测试代码
  const result = schema.parse(input);

  // 3. 检查结果
  expect(result).toEqual(expected);
});
```

也就是常说的：

```text
Arrange：准备
Act：执行
Assert：断言
```

你的第一个测试把执行和断言写得比较紧凑：

```ts
expect(new Set(names).size).toBe(names.length);
```

第二、第三个测试也是把执行结果直接放进了 `expect`：

```ts
expect(schema.parse({})).toEqual(...);
```

因此，这段测试的本质就是：

> 把项目里的重要规则写成代码，并确保以后有人修改 Schema 时，不会无意中破坏这些规则。
