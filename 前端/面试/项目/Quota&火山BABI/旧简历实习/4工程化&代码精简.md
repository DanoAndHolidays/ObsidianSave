# 4工程化&代码精简
### 团队使用Git-Flow与MR规范，介绍分支管理、提MR流程，以及遇到的评审问题与修改方式
**回答**：团队遵循标准Git-Flow：`main`为线上稳定分支，`develop`为开发分支，新需求从`develop`拉出`feature/*`分支，线上紧急Bug从`main`拉出`hotfix/*`分支，禁止直接向主干推送代码。

提MR流程：开发完成后先本地自检，编写MR描述（改动内容、测试点、关联单号）再提交。

我17个合并MR中，主要遇到三类评审问题：代码命名/注释不规范、逻辑冗余、边界场景考虑不全。我逐条接收评审意见，结合团队规范修改，二次推送等待复核，也养成了规范编码、考虑边界问题的习惯。

你们团队严格执行 Git-Flow 和 MR 规范，你一共提交了17个合并MR，讲讲你的分支管理、提MR和代码评审的流程，遇到过哪些评审问题，如何修改？
**满分答案：**
团队标准遵循Git-Flow分支模型：`main`主分支（线上稳定版本）、`develop`开发分支、`feature/*`特性分支、`hotfix/*`热修复分支。

1. **分支流程**
   日常新需求/新Bug，从`develop`分支拉出`feature/xxx`分支独立开发；线上紧急Bug从`main`拉出`hotfix/xxx`分支修复。开发完成后，合并回对应分支，不允许直接往主分支推送代码。

2. **MR提交流程**
   每次开发完成，我会先做**本地自检**：代码格式化、ESLint校验、功能回归测试；然后撰写MR描述，写明本次改动内容、测试点、关联需求/Bug单号，再提交MR。

3. **代码评审问题&处理**
   17个MR评审中，我主要遇到三类问题：一是代码命名不规范、注释缺失；二是逻辑可以简化、存在冗余写法；三是边界场景考虑不全，缺少异常兜底。
   面对评审意见，我都会逐条理解原因，结合团队编码规范修改，修改后再次推送代码等待二次评审。整个过程也让我养成了写规范代码、多考虑边界场景的习惯。

*   **面试官追问**：你们使用Monorepo，你提交了17个MR。当你的修改影响到公共包（`packages`）时，如何保证不会破坏其他业务应用？
*   **标准话术**：
    1.  **流程先行**：我的流程是，任何对`packages`的修改，都要先在MR描述中**明确标出“BREAKING CHANGE”或“feat(pkg)**”的标签，并详细说明影响范围和迁移步骤。
    2.  **CI/CD 自动化验证**：我们团队的CI流水线配置了`pnpm --filter`。当我的MR修改了`packages/button`，CI会自动执行所有依赖这个button包的`apps`（如管理后台、运营后台）的**构建和单元测试**。任何一个`app`构建失败，这个MR都不允许合并。
    3.  **版本管理**：对于不兼容的修改，我们会遵循语义化版本规范，发布`packages/button`的`major`版本。在`apps`中，开发者需要主动升级依赖并适配，而不是被动接受破坏性更新。我的职责是和各个`app`的负责人沟通，提供迁移帮助。
    4.  **沟通先行**：在提交涉及公共包的MR前，我会先在群里@相关`app`的负责人，让他们知晓即将发生的变更，并提前评估影响。这大大减少了评审时的来回扯皮。

### 说说你对Vibe Coding的理解，以及如何借助该模式精简冗余代码
Vibe Coding是AI辅助编程模式，通过自然语言沟通，让AI协助代码生成、重构与梳理，提升开发效率。**Vibe Coding** 是当下结合AI辅助的编程模式：不再纯手写每一行代码，而是通过自然语言描述需求、逻辑，借助AI工具生成、重构、梳理代码，人和AI协作完成开发、代码优化工作，侧重**效率提升和代码重构**。

精简冗余代码的流程：
1. 梳理项目迭代历史，标记闲置组件、函数；
2. 借助AI分析代码调用关系，定位无引用的冗余代码；
3. 利用AI提炼通用逻辑，替换项目中重复代码；
4. 人工结合业务场景、测试用例二次校验，保证功能不受影响。AI负责检索与梳理，我把控业务逻辑与最终落地。

整个过程AI帮我节省了大量代码检索、逻辑梳理的时间，我主要负责**业务判断、最终校验和落地**，最终完成了模块冗余代码的精简，让项目代码更轻量化。

删减冗余代码很容易误删有效逻辑，你做了哪些措施保证代码精简后线上功能不出问题？
**满分答案：**
我设置了多层校验机制，规避误删风险：
1. **调用关系校验**：借助IDE、AI工具全局检索代码引用，只有确认**零调用**的代码才标记为可删除；
2. **分步删减**：不一次性大批量删除，分模块、分批次修改，每修改一小部分就本地全量回归测试；
3. **灰度验证**：代码合并后先部署到预发环境，完整走一遍业务流程，模拟用户所有操作；
4. **版本兜底**：每一次精简都单独提交MR，保留完整Git记录，一旦发现问题可以快速回退单条提交。

通过这几层保障，最终精简工作没有引发任何功能异常。

Monorepo（单体仓库）是一种将多个项目或包的代码集中存储在单一代码仓库中进行管理的架构模式。这种开发策略在带来显著优势的同时，也伴随着一些不可忽视的挑战。

*   **面试官追问**：你在Vibe Coding环境下精简冗余代码，具体是怎么做的？如何确保你删除的代码不会被其他“隐藏”的方式调用（比如动态字符串拼接）？
*   **标准话术**：
    1.  **多维度扫描**：我深知仅靠IDE的“查找引用”是不可靠的，因为存在**动态调用**（如`window['myFunc']`）和**第三方依赖**。所以我采用组合拳：第一，使用`ts-prune`、`knip`等工具进行AST级别的静态分析。第二，全局搜索可疑的`eval`、`new Function`、字符串拼接的调用模式。第三，与测试同学协作，对标记为“待删除”的代码分支进行线上全链路回归测试，观察是否有未被发现的调用命中了监控日志。
    2.  **分步删除与兜底**：我不会在一个MR里删掉所有冗余代码。我会按模块、按功能分批处理，每个MR只专注于删除一小部分。每次删除后，都会通过我们团队的**灰度发布机制**，先让小部分用户流量验证，并密切观察相关页面错误率。最后，由于每个精简操作都是独立的Commit，一旦出现问题，我可以**秒级回滚**那个特定的Commit，而不是整体回滚一个大版本。
    3.  **本质理解**：Vibe Coding 是我的副驾驶，它能高效完成“代码清理”这种模式化任务。但最终“安全”这关，必须由我这个驾驶员，结合业务理解、系统知识和风险控制流程来把控。

### Monorepo 的优缺点与挑战
优点：
1. **代码共享与复用便捷**：跨项目的公共组件、工具函数和配置文件可以直接在本地引用，无需发布到 npm 等外部包管理仓库，大幅降低了重复编写和维护的成本。
2. **依赖与版本管理统一**：所有子项目共用一套依赖管理体系，能够避免不同项目之间出现依赖版本冲突（即“版本地狱”），减少依赖漂移问题。
3. **工程规范与CI/CD一致**：可以全局配置 ESLint、Prettier、TypeScript 等工具链，确保所有模块的代码风格、类型定义保持一致；同时 CI/CD 流程也可集中配置，减少各模块流程碎片化导致的维护成本。
4. **协作效率极高**：修改一个包的代码后，其他依赖它的包可实时感知并生效，无需等待发包和更新。一次提交即可修改所有关联包，非常适合需要紧密协作的团队进行跨包调试和迭代。

缺点：
1. **仓库体积膨胀**：随着项目数量和代码量的积累，Git 仓库会变得非常庞大，导致拉取、克隆和提交的速度变慢，影响新成员的上手体验。
2. **构建与部署成本高**：由于代码高度耦合，即使只修改了一个小模块，也可能触发整个仓库的构建与测试流程。如果缺乏完善的增量构建机制，会导致 CI/CD 流水线耗时大幅增加。
3. **权限控制粒度粗**：Git 仓库通常采用统一的权限管理，难以做到“某个包只能被特定团队或个人修改”。在多团队协作时，容易出现误修改他人代码的风险，不适合跨组织或需要严格隔离的场景。
4. **技术栈锁定与扩展受限**：为了保持统一管理，Monorepo 往往倾向于使用相同的技术栈。当个别业务线希望尝试新技术时，可能会受到全局配置的制约，增加技术创新的成本。
5. **破坏性更改修复困难**：在严格的单版本规则下，升级核心底层库可能引发连锁反应。库的维护者必须一次性完成所有下游项目的适配，否则无法推进升级，这给维护者带来了极大的工作负担。

综合来看，Monorepo 更适合中小型团队、强一致性要求以及频繁共享代码的场景；而当应用规模达到超大型、团队人数众多且需要独立交付时，其弊端往往会成为制约效率的瓶颈。


简单介绍你们项目的 **Monorepo 架构**，以及你在该架构下的日常开发流程？
**满分答案：**
我们团队的前端项目采用Monorepo统一管理，简单来说就是**多个业务包、公共组件包、工具包放在同一个代码仓库**，统一版本管理、统一依赖管理，避免多仓库之间版本不一致、依赖重复的问题。

仓库主要拆分为两类：`packages` 公共包（通用组件、工具函数、请求封装、TS类型）、`apps` 业务应用包（各个官网、后台业务模块）。

我的日常开发流程：
1. 本地拉取主分支最新代码，基于Git-Flow创建**特性分支**；
2. 开发过程中，如果用到公共组件/工具，直接引用同仓库`packages`内的包，本地可以实时调试，不用单独发包；
3. 开发完成后，本地自测、运行lint、格式化代码，保证代码规范；
4. 提交代码、提MR，等待同事代码评审；评审通过后合并到主分支，触发流水线构建部署。

Monorepo对我们后台项目很友好，公共能力复用成本低，版本协同也更方便。

### 项目基于pnpm workspaces+Turborepo搭建Monorepo，遇到包循环依赖、公共包调试失效、构建缓慢如何解决？
**回答**：
1. **循环依赖**：拆分公共能力至底层工具包，切断双向依赖；历史无法拆分的场景，使用动态导入规避编译报错；
2. **公共包调试失效**：开启pnpm软链接，配置Turborepo监听文件变化，实现公共包热更新；
3. **构建缓慢**：开发环境仅编译当前业务包，CI环境开启并行构建、缓存构建产物，提升流水线速度。

### 动态调用代码、历史兼容代码、第三方隐性依赖，AI/IDE无法检索，如何识别？出现故障如何兜底？
**回答**：针对这类隐性代码：全局检索`eval`、动态函数调用等关键字，结合迭代文档、咨询老同事判断历史兼容代码，核对`package.json`识别闲置第三方包；同时添加运行时日志，观测代码执行情况。
故障兜底：不确认的代码优先注释而非直接删除，分批上线、灰度观测；依靠Git Commit记录，出现问题快速回滚。
