# 长耗时录像导出

---
## 业务场景
假设用户要导出一段两小时的会议录像。由于可能需要视频转码、音视频合成、文件压缩、上传对象存储等操作，整个过程需要几分钟。

当前方案是：
![[Pasted image 20261019153518.png]]

直观上看，这种方案很简单：发送请求 → 等待服务端完成 → 获取下载地址

但是一旦出现网络断开、请求超时、用户刷新页面等情况，就会出现很多问题

## 长时间等待 HTTP 响应
### 请求可能超时
HTTP 协议本身没有规定所有请求必须在某个固定时间内完成，但实际系统中存在很多超时限制，例如：

- 浏览器请求库中配置的超时。
- Nginx 等反向代理的超时。
- API 网关和负载均衡器的超时。
- 服务端自身的请求处理超时。

假设服务端需要 5 分钟完成导出，而网关只允许一个请求等待 60 秒，那么前端可能收到 `504 Gateway Timeout`，即使后端任务仍然正在执行

重点：HTTP 请求失败，不一定意味着后台任务失败

### 用户离开页面，可能失去任务状态
用户发起导出请求后：

- 关闭浏览器标签页
- 刷新页面
- 网络突然断开
- 手机切换网络

此时原来的请求可能被中断，而服务端是否继续执行取决于具体实现

前端无法仅凭请求断开判断导出任务最终是否完成

### 占用连接和服务端资源
长时间保持 HTTP 连接会持续占用连接相关资源，某些同步处理模型还可能长期占用工作线程。

需要注意，这不意味着 `await fetch()` 会阻塞浏览器的 JavaScript 主线程。`await` 等待的是异步结果，主线程仍然可以执行其他任务。

### 重试可能产生重复任务
假设用户点击一次导出，服务端成功接收任务，但客户端因为网络问题没有拿到响应。

用户误以为失败，再点一次：
```
第一次请求：任务 A 已创建，但响应丢失
第二次请求：又创建任务 B
```

结果服务端可能重复转码、重复生成文件，浪费大量计算资源

因此，第一问的核心是：请求生命周期与业务任务生命周期不应该强制绑定

## 设计为异步任务
前后端应该怎样交互？这里需要理解同步等待结果和异步提交任务的区别。

同步等待的思路是：用户发起请求，服务端完成所有操作之后再返回结果。

异步任务的思路是：用户发起请求，服务端创建任务并立即返回任务 ID，后续在后台执行。

异步导出任务交互流程（这不就是类似于 Daedalus 中的扫描任务）：

1. 用户提交任务：前端发送 `POST /exports`，服务端接收请求、创建任务记录，并返回任务 ID。典型情况下可以使用 HTTP `202 Accepted`。

2. 服务端后台执行：任务进入队列，由后台 Worker 执行转码、压缩、上传等工作。原 HTTP 请求已经结束。

3. 前端查询或订阅状态：前端根据任务 ID，通过轮询、SSE 或 WebSocket 获取执行状态与进度。

4. 导出完成：服务端记录文件信息，前端获得下载入口，用户可以下载文件。

例如：
```
POST /exports
```

典型响应：
```
{
  "taskId": "export_123",
  "status": "pending"
}
```

随后可以通过：
```
GET /exports/export_123
```

这里返回任务 ID 很重要，因为它相当于服务端给每一次导出任务分配了一个稳定的身份

这样即使前端刷新、关闭页面，后续也能重新查询同一个任务

## 用户重复点击、离开页面、重新进入页面
这里涉及一个非常重要的后端知识点：幂等性（Idempotency）

### 用户连续点击导出
前端最简单的方式是点击后禁用按钮，避免连续提交。

但这只能解决正常情况下的界面重复操作。

例如：

- 用户打开两个浏览器标签页。
- 用户在另一台电脑发起相同导出。
- 客户端请求超时后自动重试。

这些情况，单纯禁用按钮解决不了，因此服务端也需要根据业务规则进行幂等处理

典型做法是在提交时携带一个[[Persistent Idempotency Key 持久化幂等键⌚️]]：
```
Idempotency-Key: abc-123
```

服务端记录这个键与任务的关联

如果同一个操作因为网络原因被重新提交，服务端可以返回已经创建的任务，而不是再生成一个新任务。

需要注意：是否复用“相同视频、相同参数”的不同导出请求，属于业务去重策略，不完全等于幂等请求重试。不同的合法导出操作可能有意创建不同任务

### 用户离开页面
用户离开页面，应该区分两件事：

- 停止前端监听
- 取消服务端任务

例如用户关闭页面，前端的轮询自然停止，但不代表服务端必须终止导出。

在多数导出场景下，后台任务应该继续执行，直到完成或者失败。

如果业务提供明确的“取消导出”按钮，则应由服务端接收取消指令，并尽可能协作终止任务。

### 用户重新进入页面
前端重新加载后，可以向服务端查询当前用户的导出任务列表，恢复进度展示

关键是：任务状态要持久化在服务端，而不是只存在 React State 或浏览器内存中

`localStorage` 可以保存最近查看的 `taskId`，但不能作为任务状态的权威来源
