## 进阶篇
### HTML
* **Q: 如何理解HTML语义化**
  A: HTML 语义化是指使用恰当的标签表达内容含义，而不只是用标签控制样式。
  背景：早期网页大量使用 `<div>` + class 堆砌，结构对人、搜索引擎、辅助技术都不友好，W3C 在 HTML5 中引入了大量语义标签来明确内容角色。
  核心价值：
  1. 可访问性：屏幕阅读器能识别 `<nav>`、`<main>`、`<article>` 等区域，帮助视障用户快速跳转。
  2. SEO：搜索引擎通过 `<header>`、`<h1>`~`<h6>`、`<time>` 等标签理解页面结构和关键词权重。
  3. 可维护性：代码结构清晰，团队协作时更容易理解页面组织。
  常用标签：`<header>`、`<nav>`、`<main>`、`<section>`、`<article>`、`<aside>`、`<footer>`、`<figure>`、`<figcaption>`、`<time>`、`<mark>`。
  实践建议：优先使用语义标签，再考虑 CSS；`<div>`/`<span>` 仅作为无语义的样式容器。HTML5 新标签本质是块级元素，旧浏览器可通过 `display: block` 重置兼容。

* **Q: H5的新特性有哪些**
  A: HTML5 的核心新增特性可以从语义、多媒体、图形、存储、通信、性能等维度记忆：
  1. 语义标签：`<header>`、`<nav>`、`<main>`、`<article>`、`<section>`、`<aside>`、`<footer>`、`<figure>`、`<figcaption>`。
  2. 多媒体：`<audio>`、`<video>` 原生支持音视频，无需 Flash；`<track>` 支持字幕。
  3. 图形：`<canvas>` 提供 2D/位图操作 API；SVG 原生嵌入矢量图形。
  4. 表单增强：新增 `email`、`url`、`tel`、`number`、`range`、`date`、`color` 等 input type，以及 `placeholder`、`required`、`pattern`、`autofocus`、`multiple` 等属性。
  5. 本地存储：`localStorage`（持久）、`sessionStorage`（会话级）、`IndexedDB`（结构化大数据）。
  6. 通信：`WebSocket` 全双工通信、`Server-Sent Events`、`postMessage` 跨窗口通信。
  7. 多线程：`Web Workers`、`SharedWorker` 在后台线程执行 JS。
  8. 地理位置：`Geolocation API`。
  9. History API：`pushState`/`replaceState` 实现无刷新路由。
  10. 拖放 API：`draggable` + `dataTransfer`。
  11. 性能：`requestAnimationFrame` 更高效的动画调度。
  12. 其他：`ContentEditable`、`<template>`、Shadow DOM 基础等。
  实际应用：现代 SPA 路由依赖 History API；离线应用依赖 Service Worker + Cache Storage。

* **Q: 说一下 HTML5 drag api**
  A: HTML5 Drag and Drop API 允许页面元素或外部文件通过拖拽交互。
  基本使用：给元素设置 `draggable="true"`，通过事件监听控制行为。
  事件分类：
  1. 拖拽源事件：`dragstart`（开始拖拽，设置数据）、`drag`（拖拽中持续触发）、`dragend`（拖拽结束）。
  2. 放置目标事件：`dragenter`（进入目标）、`dragover`（在目标上移动，需 `preventDefault()` 才能成为可放置区）、`dragleave`（离开目标）、`drop`（释放，接收数据）。
  数据传输：`event.dataTransfer` 对象。
  - `setData(format, data)` 在 `dragstart` 中写入。
  - `getData(format)` 在 `drop` 中读取。
  - `files` 属性用于接收外部文件拖拽。
  其他能力：`setDragImage()` 自定义拖拽预览图；`effectAllowed`/`dropEffect` 控制光标样式。
  示例：
  ```html
  <div id="source" draggable="true">Drag me</div>
  <div id="target">Drop here</div>
  <script>
    const source = document.getElementById('source');
    const target = document.getElementById('target');
    source.addEventListener('dragstart', e => {
      e.dataTransfer.setData('text/plain', 'hello');
    });
    target.addEventListener('dragover', e => e.preventDefault());
    target.addEventListener('drop', e => {
      e.preventDefault();
      console.log(e.dataTransfer.getData('text/plain'));
    });
  </script>
  ```
  注意：移动端兼容性有限，通常需要结合 touch 事件实现。

* **Q: iframe有那些缺点**
  A: iframe 的缺点主要来自它创建独立的浏览器上下文：
  1. 性能开销：每个 iframe 都是独立的文档，需要独立的 DOM 树、CSSOM、渲染层和 JavaScript 上下文，显著增加内存和网络消耗。
  2. 阻塞主页面加载：父页面的 `window.onload` 会等待 iframe 的 `onload` 完成。
  3. SEO 不友好：搜索引擎对 iframe 内部内容的索引能力较弱。
  4. 通信复杂：跨域场景必须使用 `postMessage`，同域虽然可以直接访问 `contentWindow`，但仍存在上下文切换成本。
  5. 安全风险：嵌入第三方页面可能引入 XSS、点击劫持或钓鱼攻击；应配合 `sandbox` 属性限制权限，如 `<iframe sandbox="allow-scripts allow-same-origin">`。
  6. 可访问性差：屏幕阅读器难以识别 iframe 内部的内容层级。
  7. 响应式困难：iframe 内部按独立视口渲染，适配外部容器需要额外计算。
  替代方案：除非必须嵌入第三方内容（支付、地图、视频），否则优先使用 Ajax 加载、Web Component 或微前端方案。

* **Q: 简述一下src与href的区别**
  A: `src`（source）和 `href`（hypertext reference）都是引用外部资源，但语义和浏览器行为不同。
  - `src` 表示"嵌入替代资源"，资源是文档的组成部分。浏览器遇到 `<script src>`、`<img src>`、`<iframe src>` 时会暂停 HTML 解析/渲染，请求并执行/渲染后再继续，因此会阻塞关键渲染路径。
  - `href` 表示"建立关联关系"，资源只是被引用而非嵌入。浏览器遇到 `<link href>`、`<a href>` 时不会阻塞解析，会在后台并行下载（如 CSS），下载完成后继续解析。
  关键区别总结：

  | 维度 | src | href |
  |---|---|---|
  | 语义 | 嵌入 | 引用 |
  | 是否阻塞解析 | 是（默认 script） | 否 |
  | 资源与文档关系 | 文档组成部分 | 外部关联 |
  | 典型标签 | script、img、iframe、input(src) | link、a、area |
  
  实际应用：`<script>` 使用 `defer`/`async` 可以控制阻塞行为；`<link rel="stylesheet">` 会阻塞渲染但不阻塞解析。

* **Q: 知道的网页制作会用到的图片格式有哪些**
  A: 常见图片格式及选型原则：
  1. JPEG：有损压缩，不支持透明，24 位色，适合照片类复杂色彩图像，体积小但放大有锯齿。
  2. PNG：无损压缩，支持透明，适合图标、LOGO、截图等边缘清晰的图像；PNG-8 适合简单图形，PNG-24 支持 Alpha 透明。
  3. GIF：支持动画，仅 256 色，适合简单动画和表情包，压缩率差。
  4. WebP：Google 推出，支持有损/无损/透明/动画，同等质量体积通常比 JPEG 小 25%-35%，浏览器兼容性已较好。
  5. AVIF：基于 AV1 编码，压缩率优于 WebP 约 20%，支持 HDR 和透明，兼容性仍在提升。
  6. SVG：矢量格式，基于 XML，无损缩放，适合图标、图形、LOGO，支持 CSS/JS 控制，文件体积小但复杂图形体积可能变大。
  7. Base64 Data URL：将小图片编码为字符串内嵌到 HTML/CSS 中，减少 HTTP 请求，但体积膨胀约 33%，适合 < 10KB 的小图标。
  选型原则：照片用 JPEG/AVIF/WebP；图标/LOGO 用 SVG；需要透明用 PNG/WebP/AVIF；简单动画用 GIF/WebP；小图标可考虑 Base64 或 SVG Sprite。

* **Q: script标签中defer和async的区别**
  A: `defer` 和 `async` 都用于控制外部脚本（带 `src`）的加载和执行时机。
  默认行为：脚本同步加载并执行，阻塞 HTML 解析。
  `defer`：
  - 加载与 HTML 解析并行。
  - 延迟到文档解析完成后、`DOMContentLoaded` 之前按文档顺序执行。
  - 多个 `defer` 脚本保持加载顺序。
  - 适合需要操作 DOM 或依赖其他脚本的场景。
  `async`：
  - 加载与 HTML 解析并行。
  - 下载完成后立即执行，会阻塞解析。
  - 不保证执行顺序，谁先下载完谁先执行。
  - 适合独立无依赖的脚本（广告、埋点）。
  对比图：
  | 特性 | 无属性 | async | defer |
  |---|---|---|---|
  | 下载是否阻塞解析 | 是 | 否 | 否 |
  | 执行是否阻塞解析 | 是 | 是 | 否 |
  | 执行顺序 | 文档顺序 | 无序 | 文档顺序 |
  | 执行时机 | 立即 | 下载完 | DOM 解析完 |
  注意：动态创建的 `<script>` 默认是 `async` 行为；`async` 和 `defer` 对内联脚本无效。

* **Q: 说一下 web worker**
  A: Web Worker 允许在浏览器后台线程中运行 JavaScript，实现真正的并行计算，不阻塞主线程 UI。
  基本用法：
  ```js
  // main.js
  const worker = new Worker('worker.js');
  worker.postMessage({ num: 40 });
  worker.onmessage = e => console.log('result:', e.data);

  // worker.js
  self.onmessage = e => {
    const result = fibonacci(e.data.num); // 耗时计算
    self.postMessage(result);
  };
  ```
  限制：Worker 内无法访问 DOM、`window`、`document`、`parent`，但可以使用 `XMLHttpRequest`、`fetch`、`setTimeout`、`IndexedDB`、`WebSocket`、`importScripts()`（或 ES Module `type="module"`）。
  数据传输：默认使用结构化克隆算法拷贝数据；对于大内存数据，可以使用 Transferable Objects（如 `ArrayBuffer`）实现零拷贝。
  类型：
  - Dedicated Worker：仅被创建它的页面使用。
  - Shared Worker：同源多页面共享。
  - Service Worker：充当网络代理，实现离线缓存、PUSH 通知。
  应用场景：大数据处理、加密、图像处理、实时轮询、游戏物理计算。
  注意：Worker 调试较困难，且创建和通信有一定开销，不应滥用。

* **Q: 用一个div模拟textarea的实现**
  A: 核心思路是让 div 成为可编辑区域：`contenteditable="true"`。
  实现要点：
  1. 设置 `contenteditable="true"`，div 即可输入文本。
  2. 样式上设置 `white-space: pre-wrap; word-wrap: break-word;` 保持文本换行。
  3. placeholder 效果可通过 CSS `:empty::before { content: attr(data-placeholder); color: #999; }` 实现。
  4. 获取纯文本内容用 `innerText` 而非 `innerHTML`，避免混入 HTML 标签。
  5. 监听 `input` 事件实时获取内容。
  6. 限制输入长度需在 `input` 事件或 `beforeinput` 中手动截断。
  7. 自动聚焦和光标定位可用 `focus()` + `Range`/`Selection` API。
  示例：
  ```html
  <style>
    .edit-box { border: 1px solid #ccc; min-height: 80px; padding: 8px; }
    .edit-box:empty::before { content: attr(data-placeholder); color: #999; }
  </style>
  <div class="edit-box" contenteditable="true" data-placeholder="请输入..."></div>
  ```
  注意事项：contentEditable 在 IME 输入法、拼写检查、Tab 键行为等方面与原生 textarea 有差异。现代 React/Vue 项目中，推荐优先用 textarea + CSS 实现自动高度（如根据 `scrollHeight` 调整高度）。

* **Q: 介绍下资源预加载 prefetch/preload**
  A: 资源预加载通过 `<link rel="...">` 提示浏览器提前加载资源，优化关键路径和用户体验。
  主要方式：
  1. `preload`：当前页面肯定会用到，请立即高优先级加载。
     - 常用于关键 CSS、字体、首屏 JS 模块、首屏图片。
     - 必须指定 `as` 属性（style/script/font/image/fetch 等），否则浏览器可能不执行。
     - 示例：`<link rel="preload" href="font.woff2" as="font" crossorigin>`。
  2. `prefetch`：下一个页面可能用到，请空闲时低优先级加载。
     - 示例：`<link rel="prefetch" href="next-page.js">`。
  3. `preconnect`：提前建立连接（DNS + TCP + TLS），适合跨域关键资源。
     - 示例：`<link rel="preconnect" href="https://api.example.com">`。
  4. `dns-prefetch`：仅预解析 DNS，开销更小。
     - 示例：`<link rel="dns-prefetch" href="https://cdn.example.com">`。
  注意事项：`preload` 使用不当会浪费带宽；`prefetch` 的资源在下一个导航才生效；字体预加载必须加 `crossorigin`，即使同域。

* **Q: 介绍下 viewport**
  A: viewport 是浏览器用来渲染网页的可视区域。移动端浏览器默认使用一个较宽的"布局视口"（通常 980px）渲染页面，再缩放适配屏幕，导致文字过小。
  标准方案：
  ```html
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  ```
  核心参数：
  - `width=device-width`：将布局视口宽度设为设备宽度（理想视口）。
  - `initial-scale=1.0`：初始缩放比例为 1。
  - `minimum-scale`/`maximum-scale`：缩放范围限制。
  - `user-scalable=no`：禁止缩放（不推荐，影响可访问性）。
  三个视口概念：
  - 布局视口（layout viewport）：CSS 百分比布局的参照。
  - 视觉视口（visual viewport）：用户当前看到的区域，可通过 `window.visualViewport` 获取。
  - 理想视口（ideal viewport）：设备物理像素对应的 CSS 像素宽度。
  实际应用：移动端适配需结合 `rem`/`vw`、flexible 布局、媒体查询。处理 1px 物理像素问题时，可结合 `devicePixelRatio` 和 `initial-scale=1/dpr` 的 meta 方案。

* **Q: `target="_blank"`有哪些问题？**
  A: 主要问题有三个：安全、性能、体验。
  1. 安全问题（tab-napping）：新页面可通过 `window.opener` 访问原页面窗口（同源时），恶意页面可能通过 `window.opener.location = '钓鱼链接'` 重定向原页面。
     - 解决方案：添加 `rel="noopener noreferrer"`。
     - `noopener` 阻止新页面访问 `opener`；`noreferrer` 同时隐藏 Referer 头。
     - 现代浏览器（Chromium 88+、Firefox 79+、Safari 15+）默认对 `target="_blank"` 设置 `noopener`，但仍建议显式声明。
  2. 性能问题：打开新标签页会占用额外内存和进程。
  3. 用户体验：未经用户同意打开新窗口可能造成困扰。
  最佳实践：所有外链的 `target="_blank"` 都加 `rel="noopener noreferrer"`；若需双向通信，改用 `window.open()` + `postMessage`。

### CSS
* **Q: 如何理解a标点击后hover事件失效的问题?**
  A: 根本原因是 CSS 伪类优先级顺序未按 LVHA 规则书写。
  LVHA 规则：`:link` -> `:visited` -> `:hover` -> `:active`。
  当点击 `<a>` 后链接变为已访问状态，如果 `:visited` 的样式定义在 `:hover` 之后，`:visited` 会覆盖 `:hover`，导致 hover 不生效。
  解决方式：
  1. 按 LVHA 顺序声明：
     ```css
     a:link { color: blue; }
     a:visited { color: purple; }
     a:hover { color: red; }
     a:active { color: orange; }
     ```
  2. 使用 `:any-link` 统一匹配所有链接状态，再配合 `:hover`。
  3. 用 class 替代伪类，如 `.nav-link:hover`，避免伪类优先级冲突。
  深层原因：`:visited` 的样式受限（只有 color、background-color、border-color 等少数属性可修改）是浏览器的隐私保护措施，防止通过 CSS 探测用户浏览历史。Safari 对 visited 样式还有额外限制。

### JavaScript
* **Q: 原型链**
  A: JavaScript 通过原型链实现继承和属性查找。
  核心机制：每个对象都有一个内部 `[[Prototype]]` 属性（可通过 `__proto__` 或 `Object.getPrototypeOf()` 访问），指向其构造函数的 `prototype` 对象。
  属性查找：访问对象属性时，引擎先查自身属性（own property），找不到则沿 `[[Prototype]]` 向上查找，直到 `Object.prototype`（其 `[[Prototype]]` 为 `null`）。
  核心关系：
  ```js
  function Foo() {}
  Foo.prototype.constructor === Foo;        // true
  new Foo().__proto__ === Foo.prototype;    // true
  Foo.prototype.__proto__ === Object.prototype; // true
  ```
  所有函数都是 `Function` 的实例：
  ```js
  Foo.__proto__ === Function.prototype;
  Function.__proto__ === Function.prototype; // Function 自举
  Object.__proto__ === Function.prototype;
  ```
  `instanceof` 通过检查 `constructor.prototype` 是否在实例的原型链上来判定。
  ES6 class 本质上是原型链的语法糖。
  注意：原型链上的引用类型属性会被所有实例共享，因此属性定义通常放在构造函数内，方法放在 prototype 上。

* **Q: 闭包**
  A: 闭包是指一个函数能够记住并访问其词法作用域，即使该函数在其词法作用域之外执行。
  底层原理：JavaScript 函数创建时会保存对外部词法环境的引用（`[[Environment]]`），即使外部函数执行完毕，内部函数仍持有该引用，外部变量不会被垃圾回收。
  典型应用：
  1. 封装私有变量：
     ```js
     function counter() {
       let count = 0;
       return {
         increment: () => ++count,
         decrement: () => --count,
         get: () => count
       };
     }
     ```
  2. 模块模式（IIFE 实现命名空间隔离）。
  3. 回调中保存上下文：循环中通过闭包捕获索引值。
  4. 高阶函数：柯里化、debounce、throttle、once 等。
  经典面试题：
  ```js
  for (var i = 0; i < 3; i++) {
    setTimeout(() => console.log(i), 100); // 输出 3, 3, 3
  }
  ```
  原因：`var` 没有块级作用域，所有回调共享同一个 `i`。解决方案：使用 IIFE 创建私有作用域，或改用 `let`。
  注意事项：闭包会导致被引用的外部变量无法释放，过度使用可能造成内存泄漏。

* **Q: Event Loop（浏览器与 Node 区别）**
  A: Event Loop 是 JavaScript 异步执行的调度机制，因为 JS 是单线程的，需要协调同步代码、宏任务、微任务、IO 事件等。
  浏览器 Event Loop：
  1. 执行一个宏任务（如 script 整体、setTimeout 回调、用户交互事件）。
  2. 清空微任务队列（Promise.then/catch/finally、MutationObserver、queueMicrotask）。
  3. 如果需要渲染，执行 requestAnimationFrame。
  4. 执行渲染（样式计算、布局、绘制、合成）。
  5. 检查 requestIdleCallback。
  Node.js Event Loop（libuv）：
  分为六个阶段：timers -> pending callbacks -> idle/prepare -> poll -> check -> close callbacks。
  每个阶段执行对应类型的回调，每个阶段结束后都会清空微任务队列。
  关键区别：
  | 维度 | 浏览器 | Node.js |
  |---|---|---|
  | 渲染 | 有 | 无 |
  | setImmediate | 无（仅 IE） | 有（check 阶段） |
  | process.nextTick | 无 | 有，优先级高于微任务 |
  | 微任务清空时机 | 每个宏任务后 | 每个阶段之间 |
  | setTimeout vs setImmediate | 无 setImmediate | 同 tick 中顺序不确定 |
  Node 11+ 后，setTimeout 等回调内的微任务行为与浏览器趋于一致。

* **Q: 垃圾回收机制**
  A: JavaScript 的垃圾回收（GC）是自动的，主流引擎使用"标记-清除"（Mark-and-Sweep）及其优化算法。
  基本原理：GC 从根对象（全局对象、当前执行上下文、栈中变量等）出发，标记所有可到达的对象，然后清除未被标记的对象。
  V8 的分代回收：
  1. 新生代（Young Generation）：存放生命周期短的对象，采用 Scavenge 算法（Cheney 算法），将空间分为 From 和 To 两个半区，活动对象从 From 复制到 To，存活两次以上的对象晋升到老生代。
  2. 老生代（Old Generation）：存放生命周期长的对象，采用"标记-清除-整理"（Mark-Sweep-Compact）：
     - 标记阶段：遍历对象图标记活动对象。
     - 清除阶段：回收非活动对象内存。
     - 整理阶段：将活动对象向一端移动，减少内存碎片。
  优化技术：
  - 增量标记（Incremental Marking）：将标记工作拆分到多个小步，减少主线程停顿。
  - 并发标记（Concurrent Marking）：允许 GC 与 JS 执行同时进行。
  - 写屏障（Write Barrier）：跟踪老生代到新生代的引用，优化跨代引用。
  注意：早期的引用计数（Reference Counting）因无法处理循环引用已被现代引擎淘汰。

* **Q: 内存泄漏常见场景**
  A: 前端常见内存泄漏场景：
  1. 全局变量：未声明的变量自动成为全局变量（严格模式可避免），或挂载到 window 的引用未清除。
  2. 闭包：外层函数变量被内层函数持续引用。
  3. 定时器和回调：setInterval/setTimeout 未取消，事件监听未 `removeEventListener`。
  4. DOM 引用：JS 变量缓存了 DOM 元素引用，DOM 被移除后 JS 引用未置 null。
  5. 脱离 DOM 树的节点：`removeChild` 后仍有变量指向该节点。
  6. Map/Set 中的引用：使用普通 Map/Set 存储 DOM 引用，应改用 WeakMap/WeakSet。
  7. WebSocket/连接未关闭：保持长连接引用。
  8. 第三方库/组件销毁不彻底：SPA 中组件卸载时未清理副作用。
  9. 订阅未取消：Redux subscribe、RxJS 订阅、Event Bus 监听等。
  检测工具：Chrome DevTools Memory 面板、Heap Snapshot、Performance 录制、Allocation Timeline。

* **Q: 内存泄漏检测与场景**
  A: 检测方法：
  1. Chrome DevTools Performance 面板：录制时间线，观察 JS Heap 曲线。若 GC 后曲线不回落，可能存在泄漏。
  2. Memory 面板 Heap Snapshot：拍摄多次快照，使用 Comparison 视图对比对象数量增长。
  3. Allocation Instrumentation on Timeline：记录内存分配时间线，定位持续增长的位置。
  4. `performance.memory`：检查 JS heap 使用量（Chrome 限定）。
  验证方法：重复执行某个操作（如打开/关闭弹窗、路由切换），手动触发 GC，对比前后快照。重点关注 Detached DOM Tree（游离 DOM 节点），展开 retainers 链定位引用源。
  常见场景对应：
  - Detached DOM Tree 持续增长：DOM 引用未释放。
  - Closure 对象增长：闭包持有引用未释放。
  - 定时器/订阅对象增长：未清理副作用。
  修复后通过多次快照对比验证效果。

* **Q: Promise 可以取消吗**
  A: 原生 Promise 本身不支持取消。Promise 设计为不可变状态机：`pending -> fulfilled/rejected`，一旦 settled 就不可逆转。
  但可以通过以下方式实现"取消"语义：
  1. AbortController：现代浏览器原生支持，可与 fetch 结合。
     ```js
     const controller = new AbortController();
     fetch(url, { signal: controller.signal });
     controller.abort();
     ```
  2. Promise.race + 取消令牌：
     ```js
     function withCancel(promise, cancelPromise) {
       return Promise.race([promise, cancelPromise]);
     }
     ```
  3. 包装 Promise + 标志变量：
     ```js
     function makeCancellable(promise) {
       let cancelled = false;
       const wrapped = promise.then(data => cancelled ? Promise.reject({ cancelled: true }) : data);
       wrapped.cancel = () => { cancelled = true; };
       return wrapped;
     }
     ```
  4. RxJS Observable：支持取消订阅（unsubscribe），适合流式场景。
  生产建议：需要真正中断网络请求用 AbortController；UI 层面"取消"（如关闭弹窗后忽略旧请求结果）用标志变量即可。

* **Q: Async 原理**
  A: `async/await` 是 Generator + Promise 的语法糖，本质是利用生成器的暂停/恢复能力配合 Promise 实现同步风格的异步代码。
  执行原理：
  1. `async` 函数总是返回一个 Promise。
  2. 遇到 `await` 时，JS 引擎暂停函数执行，将右侧表达式包装为 Promise（非 Promise 则用 `Promise.resolve()` 包装）。
  3. 将 `await` 后面的代码注册为该 Promise 的 `.then()` 回调。
  4. Promise resolve 后恢复执行，将 resolved value 赋值给 await 表达式；若 reject 则在当前函数内抛出异常，可被 try/catch 捕获。
  示例：
  ```js
  async function fetchData() {
    try {
      const res = await fetch('/api');
      const data = await res.json();
      return data;
    } catch (err) {
      console.error(err);
    }
  }
  ```
  注意事项：
  - `await` 在 `forEach`/`map` 中会导致串行或并发混乱，循环中应使用 `for...of`（串行）或 `Promise.all`（并行）。
  - `await` 后的代码属于微任务。
  - async/await 错误处理比 Promise 链更自然，但 `await` 没有原生超时，需要配合 `Promise.race` 或 AbortController。

### DOM / 事件
* **Q: 如何实现浏览器内多个标签页之间的通信**
  A: 同源多标签页通信方案：
  1. BroadcastChannel（推荐）：
     ```js
     const bc = new BroadcastChannel('app_channel');
     bc.postMessage({ type: 'login', user: 'tom' });
     bc.onmessage = e => console.log(e.data);
     ```
  2. localStorage + storage 事件：同源其他标签页修改 localStorage 时触发，但当前修改页不触发。
  3. SharedWorker：多页面共享同一个 Worker 线程通信。
  4. postMessage + window.open：父页面打开子页面后通过引用互相发消息。
  5. IndexedDB：通过轮询或 `versionchange` 事件感知数据变更。
  6. Cookie：通过 setInterval 轮询变化，低效不推荐。
  7. WebSocket：通过服务端中转，适用于跨域/多设备场景。
  选型建议：同源简单场景首选 BroadcastChannel，兼容性不佳时降级为 localStorage。BroadcastChannel 不支持 Safari < 15.4。

* **Q: 点击一个input依次触发的事件**
  A: 使用鼠标点击 input 时的典型事件顺序：
  ```
  pointerdown -> mousedown -> focus -> focusin -> pointerup -> mouseup -> click
  ```
  部分浏览器中 `mousedown` 可能触发两次（activate 阶段和正常阶段）。
  若 input 是 radio/checkbox，还可能触发 `change`。
  键盘相关事件（如 keydown）需用户按键后触发。
  重点：
  - `focus` 不冒泡，`focusin` 冒泡。
  - `blur` 不冒泡，`focusout` 冒泡。
  - `input` 事件实时反映内容变化；`change` 事件在失焦且值变化时触发。
  - `event.isTrusted` 可判断事件是用户触发还是 JS 触发。

* **Q: 有写过原生的自定义事件吗**
  A: 通过 `CustomEvent` API 创建和派发自定义事件。
  示例：
  ```js
  const event = new CustomEvent('user:login', {
    detail: { userId: 123 },
    bubbles: true,
    cancelable: true,
    composed: true // 可穿透 Shadow DOM
  });
  element.dispatchEvent(event);
  element.addEventListener('user:login', e => console.log(e.detail));
  ```
  注意：
  - 自定义事件默认不冒泡，需显式设置 `bubbles: true`。
  - `cancelable: true` 允许 `preventDefault()`。
  - `composed: true` 让事件穿透 Shadow DOM。
  - 事件名建议用 kebab-case 或命名空间前缀避免冲突。
  应用场景：组件间解耦通信、Web Component 内部事件、封装第三方库回调。

* **Q: addEventListener和attachEvent的区别？**
  A: `addEventListener` 是 W3C 标准，`attachEvent` 是 IE6-8 专有实现。
  主要区别：
  | 维度 | addEventListener | attachEvent |
  |---|---|---|
  | 参数 | type, listener, options/useCapture | 'on' + type, listener |
  | 事件阶段 | 支持捕获和冒泡 | 仅冒泡 |
  | this 指向 | 绑定元素 | window |
  | 阻止默认行为 | preventDefault() | returnValue = false |
  | 阻止冒泡 | stopPropagation() | cancelBubble = true |
  | 多次绑定 | 相同函数去重 | 会重复绑定 |
  兼容写法：
  ```js
  function addEvent(el, type, handler) {
    if (el.addEventListener) {
      el.addEventListener(type, handler);
    } else if (el.attachEvent) {
      el.attachEvent('on' + type, handler);
    } else {
      el['on' + type] = handler;
    }
  }
  ```

* **Q: addEventListener函数的第三个参数**
  A: 第三个参数可以是布尔值或对象。
  布尔值 `useCapture`（默认 false）：`true` 表示捕获阶段触发，`false` 表示冒泡阶段触发。
  对象 `options`：
  - `capture`：等价于 `useCapture`。
  - `once`：回调只执行一次后自动移除。
  - `passive`：true 表示回调中不会调用 `preventDefault()`，浏览器可优化滚动性能。Chrome 对 touchmove/wheel 默认 `passive: true`。
  - `signal`：传入 `AbortController.signal`，可通过 `controller.abort()` 批量移除监听器。
  示例：
  ```js
  window.addEventListener('scroll', handler, { passive: true });
  el.addEventListener('click', handler, { once: true });
  ```

* **Q: DOM事件流是什么？**
  A: W3C 标准规定事件流分为三个阶段：
  1. 捕获阶段（Capture Phase）：事件从 `window` -> `document` -> `<html>` -> `<body>` -> 父元素 -> 目标元素，逐层向下传递。
  2. 目标阶段（Target Phase）：事件到达实际触发事件的元素。
  3. 冒泡阶段（Bubbling Phase）：事件从目标元素逐层向上传递回 `window`。
  通过 `addEventListener` 的第三个参数控制监听阶段：`true` 为捕获，`false` 为冒泡。
  `event.eventPhase` 标识当前阶段：1=捕获，2=目标，3=冒泡。
  注意：部分事件（如 focus、blur、load、scroll、mouseenter、mouseleave）默认不冒泡。

* **Q: 冒泡和捕获的具体过程**
  A: 以 `<div id="outer"><div id="inner"></div></div>` 为例，点击 inner：
  捕获过程：`window -> document -> html -> body -> #outer -> #inner`
  冒泡过程：`#inner -> #outer -> body -> html -> document -> window`
  行为规则：
  - 若 outer 用捕获、inner 用冒泡：先触发 outer 的捕获回调，再触发 inner 的回调，冒泡阶段 outer 不再触发（已走过）。
  - 若两个都用冒泡：先 inner 后 outer。
  - 在目标阶段，捕获和冒泡的回调都会执行，按注册顺序执行。
  阻止传播：
  - `stopPropagation()`：阻止事件继续传播。
  - `stopImmediatePropagation()`：阻止传播且阻止同元素上其他同类型监听器执行。

* **Q: 关于一些兼容性**
  A: 前端事件兼容性主要围绕旧版 IE（IE8 及以下）：
  1. 事件绑定：`addEventListener` vs `attachEvent`。
  2. 事件对象：标准回调参数 `event` vs IE `window.event`。
  3. 目标元素：`event.target` vs IE `event.srcElement`。
  4. 阻止冒泡：`stopPropagation()` vs `cancelBubble = true`。
  5. 阻止默认行为：`preventDefault()` vs `returnValue = false`。
  6. 事件类型前缀：IE attachEvent 需要 'on' 前缀。
  7. 鼠标按键：`event.button` 映射值不同。
  现代开发中通常通过 Polyfill（core-js）或工具库处理兼容问题。手写兼容时先做特性检测。

* **Q: 如何阻止冒泡和默认事件(兼容写法)**
  A: 阻止冒泡：
  ```js
  function stopPropagation(e) {
    const evt = e || window.event;
    if (evt.stopPropagation) {
      evt.stopPropagation();
    } else {
      evt.cancelBubble = true;
    }
  }
  ```
  阻止默认行为：
  ```js
  function preventDefault(e) {
    const evt = e || window.event;
    if (evt.preventDefault) {
      evt.preventDefault();
    } else {
      evt.returnValue = false;
    }
  }
  ```
  注意：
  - 内联事件处理函数中 `return false` 可同时阻止默认行为和冒泡。
  - `addEventListener` 中 `return false` 无效。
  - `preventDefault()` 不阻止冒泡，`stopPropagation()` 不阻止默认行为，两者可组合使用。

* **Q: 所有的事件都有冒泡吗？**
  A: 不是。常见不冒泡事件：
  - `focus`、`blur`
  - `load`、`unload`、`abort`、`error`（资源加载错误）
  - `scroll`（大部分浏览器中不冒泡）
  - `mouseenter`、`mouseleave`
  - `resize`
  - `DOMContentLoaded`、`beforeunload`
  替代方案：
  - `focus`/`blur` 不冒泡，但 `focusin`/`focusout` 冒泡。
  - `mouseenter`/`mouseleave` 不冒泡，但 `mouseover`/`mouseout` 冒泡。
  自定义事件默认不冒泡，需在 `new CustomEvent` 时设置 `bubbles: true`。
  不冒泡事件无法使用事件委托，需直接绑定或使用对应的冒泡替代事件。

* **Q: 拖拽有哪些知识点**
  A: 拖拽实现主要有两套方案：
  1. HTML5 Drag & Drop API：
     - 源元素设置 `draggable="true"`。
     - 事件：`dragstart`、`drag`、`dragend`。
     - 目标事件：`dragenter`、`dragover`（需 `preventDefault`）、`dragleave`、`drop`。
     - 数据传输：`dataTransfer.setData/getData`。
     - 自定义预览：`setDragImage()`。
  2. 鼠标拖拽（兼容移动端）：
     - `mousedown` -> `mousemove` -> `mouseup`。
     - 记录初始位置和偏移量。
     - touch 事件做移动端兼容。
  其他知识点：
  - 文件拖拽：通过 `dataTransfer.files` 获取 FileList。
  - 拖拽排序：计算偏移位置或使用 react-dnd、sortablejs 等库。
  - 效果控制：`effectAllowed`/`dropEffect` 控制光标样式。
  注意：移动端不兼容 HTML5 Drag API，需用 touch 事件；跨域拖拽数据读取受限。

* **Q: offset、scroll、client的区别**
  A: 三组属性用于获取元素尺寸和位置：
  1. offset：
     - `offsetParent`：最近的定位祖先（position 非 static）。
     - `offsetTop`/`offsetLeft`：相对于 offsetParent 的偏移。
     - `offsetWidth`/`offsetHeight`：content + padding + border（不含 margin）。
  2. client：
     - `clientTop`/`clientLeft`：border 宽度。
     - `clientWidth`/`clientHeight`：content + padding（不含 border、scrollbar、margin）。
  3. scroll：
     - `scrollTop`/`scrollLeft`：滚动条滚动距离（可读写）。
     - `scrollWidth`/`scrollHeight`：内容的总尺寸（含溢出部分）。
  判断是否滚动到底：
  ```js
  element.scrollHeight - element.scrollTop === element.clientHeight
  ```
  视口尺寸：
  - `document.documentElement.clientWidth`：不含滚动条。
  - `window.innerWidth`：含滚动条。

* **Q: children以及childNodes的区别**
  A: `children` 和 `childNodes` 都返回子节点集合，但筛选类型不同：
  - `children`：仅包含元素节点（nodeType === 1），返回 `HTMLCollection`（实时集合）。
  - `childNodes`：包含所有子节点（元素、文本、注释、处理指令等），返回 `NodeList`。
  示例：
  ```html
  <div>Hello <span>World</span><!-- comment --></div>
  ```
  该 div 的 `childNodes` 包含 3 个节点：文本节点 "Hello "、元素节点 `<span>`、注释节点。
  `children` 只包含 1 个元素节点 `<span>`。
  类似区别：`firstChild`/`firstElementChild`、`nextSibling`/`nextElementSibling`。

* **Q: HTMLCollection和NodeList的区别**
  A: 两者都是类数组的 DOM 节点集合：
  | 维度 | HTMLCollection | NodeList |
  |---|---|---|
  | 包含类型 | 仅元素节点 | 任意类型节点 |
  | 获取方式 | getElementsByTagName/ClassName、children | querySelectorAll、childNodes |
  | 动态性 | 实时（live） | querySelectorAll 为静态，childNodes 为实时 |
  | 迭代方法 | 无 forEach，需先转数组 | 支持 forEach、entries、keys、values |
  | 特殊访问 | 支持 name/id 索引 namedItem | 支持 item 和数字索引 |
  最佳实践：需要静态快照用 `querySelectorAll`；需要动态跟踪 DOM 变化用 `getElementsByTagName`。

* **Q: 事件委托的缺点**
  A: 事件委托优点突出，但也有局限：
  1. `this` 指向：回调中 `this` 指向委托的父元素，而非实际触发元素，需用 `event.target` 判断。
  2. `stopPropagation` 冲突：子元素调用 `stopPropagation()` 会阻止事件冒泡到委托元素，导致委托失效。
  3. 事件过滤开销：需要通过 `matches` 或 `closest` 判断目标元素，高频事件（如 mousemove）中增加计算。
  4. 无法委托不冒泡事件：focus、blur、scroll、mouseenter、mouseleave、load 等。
  5. 调试困难：事件面板显示监听器绑在父元素上，排查实际触发元素需查看回调逻辑。
  权衡：子元素少或层级浅时直接绑定；动态列表或大量子元素时优先委托。

* **Q: 事件委托中 target 和 currentTarget 区别**
  A: - `event.target`：触发事件的原始元素，即目标阶段的元素，在整个事件传播过程中不变。
  - `event.currentTarget`：当前正在处理事件的元素，即绑定监听器的元素，会随传播阶段变化。
  示例：
  ```js
  ul.addEventListener('click', e => {
    console.log(e.target);       // 被点击的 li 或其内部子元素
    console.log(e.currentTarget); // ul
  });
  ```
  判断委托目标时常用：
  ```js
  if (e.target.matches('li')) { /* ... */ }
  // 或
  const li = e.target.closest('li');
  ```
  在目标阶段，`target === currentTarget`。

### 浏览器
* **Q: 浏览器渲染原理**
  A: 从接收 HTML 到屏幕像素的完整过程：
  1. 解析 HTML：将字节流解析为 Token，构建 DOM 树。遇到 CSS 并行下载，遇到无 defer/async 的 script 阻塞解析。
  2. 解析 CSS：构建 CSSOM 树。
  3. 合并渲染树：DOM + CSSOM -> Render Tree，只包含可见元素（`display:none` 和 `<head>` 子元素不在其中）。
  4. 布局（Layout/Reflow）：计算每个可见元素的几何位置和尺寸。
  5. 绘制（Paint）：将布局结果绘制为屏幕像素，可能分为多个图层。
  6. 合成（Composite）：将不同图层合并为最终画面，GPU 加速合成。
  关键优化：
  - 避免频繁读写布局属性导致的强制同步布局。
  - 优先使用 `transform` 和 `opacity` 做动画，它们只触发合成。
  - 合理使用 `will-change` 创建独立图层。

* **Q: 为什么操作 DOM 慢**
  A: DOM 操作慢的根本原因是 JavaScript 引擎和渲染引擎之间的隔离。
  具体原因：
  1. 跨边界通信：JS 引擎和渲染引擎运行在不同线程/进程，操作 DOM 需要 IPC 和序列化开销。
  2. DOM 是 C++ 数据结构：JS 访问 DOM 属性会产生跨语言桥接调用。
  3. 强制同步布局：修改样式后立即读取布局属性，浏览器必须立即刷新布局队列。
  4. 重排/回流：修改几何属性会触发整棵布局树或部分子树重新计算。
  5. 重绘：修改视觉属性需要重新绘制像素。
  6. GC 压力：创建销毁大量 DOM 节点增加垃圾回收频率。
  优化策略：
  - 批量 DOM 操作（DocumentFragment）。
  - 离线修改（`display:none` 后修改）。
  - 虚拟 DOM 减少实际 DOM 操作。
  - `requestAnimationFrame` 合并布局读写。
  - 避免强制同步布局。

* **Q: 重绘和回流（Reflow / Repaint）**
  A: - 回流（Reflow/重排）：元素几何属性变化导致浏览器重新计算布局。如 width、height、margin、padding、position、display、font-size 变化。
  - 重绘（Repaint）：元素外观变化但不影响布局，如 color、background-color、visibility、outline 变化。
  关系：回流一定会触发重绘，重绘不一定会触发回流。
  触发回流的常见操作：
  - 添加/删除可见 DOM 元素。
  - 修改元素尺寸、位置。
  - 浏览器窗口 resize。
  - 读取布局属性：`offset*`、`scroll*`、`client*`、`getComputedStyle()`、`getBoundingClientRect()`。
  优化策略：
  1. 批量修改样式（class 切换替代多个 style 赋值）。
  2. 读写分离，先读后写。
  3. 用 `transform` 替代 `top/left` 做动画。
  4. 用 `opacity` 做显隐动画。
  5. 离线 DOM 操作。
  6. 使用 `will-change` 提示浏览器。

* **Q: 浏览器缓存机制**
  A: 浏览器缓存分为强缓存和协商缓存。
  强缓存：在资源过期前直接从本地读取，不发送请求。
  - `Cache-Control: max-age=31536000`（HTTP/1.1）。
  - `Expires`（HTTP/1.0，绝对时间）。
  - `Cache-Control` 优先级高于 `Expires`。
  - `Cache-Control: immutable` 表示资源永不变化，适合版本化文件名。
  协商缓存：资源过期后发送条件请求验证。
  - `Last-Modified`/`If-Modified-Since`：按文件修改时间验证，精确到秒。
  - `ETag`/`If-None-Match`：按资源哈希验证，更精确。
  - `ETag` 优先级高于 `Last-Modified`。
  状态码：强缓存返回 200（from memory cache / from disk cache），协商缓存命中返回 304。
  策略建议：
  - 版本化资源（JS/CSS）用强缓存 `max-age=31536000, immutable`。
  - HTML 用 `no-cache`（每次协商）或 `no-store`（不缓存）。
  - Service Worker 可实现更灵活的缓存策略。

### 安全
* **Q: XSS 防御**
  A: XSS（跨站脚本攻击）是攻击者向页面注入恶意脚本。分为三类：
  1. 反射型：恶意脚本在 URL 中，服务端未过滤直接返回。
  2. 存储型：恶意脚本存储到数据库，其他用户访问时执行，危害最大。
  3. DOM Based：客户端 JS 动态拼接数据到 DOM 时注入。
  防御手段：
  1. 输出编码：HTML 上下文转义 `<>&"'`；JS 上下文转义特殊字符；URL 上下文用 `encodeURIComponent`。
  2. CSP（Content Security Policy）：通过 HTTP 头限制脚本来源，如 `Content-Security-Policy: script-src 'self'`。
  3. HttpOnly Cookie：防止 JS 读取 Cookie。
  4. 输入验证：校验类型、长度、格式，拒绝可疑内容。
  5. 框架自动转义：React/Vue 默认转义，谨慎使用 `dangerouslySetInnerHTML`/`v-html`。
  6. DOM 操作安全：优先用 `textContent`，避免直接 `innerHTML`。
  7. Trusted Types：Chrome 支持的 API，强制执行安全的 HTML 赋值。
  纵深防御：后端也必须过滤和转义，前端防御只是第一道防线。

* **Q: CSRF 防御**
  A: CSRF（跨站请求伪造）利用用户已登录身份，诱导其在不知情下向目标网站发起恶意请求。根本原因是 Cookie 会自动随请求发送。
  防御方式：
  1. SameSite Cookie：`Lax` 模式（Chrome 80+ 默认）限制跨站 POST 带 Cookie；`Strict` 模式更严格。
  2. CSRF Token：服务端生成随机 Token，嵌入表单或请求头，请求时校验。Token 应绑定用户 Session。
  3. 双重 Cookie 验证：请求头携带自定义字段，服务端比对 Cookie 值。
  4. Referer/Origin 校验：检查请求来源是否合法。
  5. 关键操作二次验证：支付、改密等要求输入密码或验证码。
  最佳实践：现代 Web 首选 `SameSite=Lax` + CSRF Token。前后端分离使用 JWT 放在 Authorization 头中天然免疫 CSRF。

* **Q: 点击劫持防御**
  A: 点击劫持通过透明 iframe 覆盖目标页面，诱导用户点击实际触发目标页面操作。
  防御方式：
  1. `X-Frame-Options`：
     - `DENY`：禁止所有 iframe 加载。
     - `SAMEORIGIN`：仅同源可加载。
  2. CSP `frame-ancestors`（推荐，更细粒度）：
     - `frame-ancestors 'self'`：仅同源。
     - `frame-ancestors 'none'`：禁止所有。
     - 可指定具体域名。
  3. Frame Busting（辅助）：
     ```js
     if (top !== self) top.location.href = self.location.href;
     ```
  4. SameSite Cookie：可部分缓解非用户操作的跨站请求。
  推荐方案：CSP `frame-ancestors` 为主防御，配合 `X-Frame-Options` 做旧浏览器兼容。

### 框架（Vue / React）
* **Q: Vue2 / Vue3 双向绑定原理**
  A: Vue2 响应式：
  - 使用 `Object.defineProperty()` 递归重写 data 对象的 getter/setter。
  - 每个组件维护一个 Dep，getter 中收集依赖（Watcher），setter 中通知 Watcher 更新。
  - 流程：Observer -> Dep -> Watcher。
  - 缺点：无法检测属性新增/删除、数组索引/length 变化；递归遍历初始化性能差；不支持 Map/Set。
  Vue3 响应式：
  - 使用 ES6 `Proxy` 代理整个对象。
  - `reactive()` 返回原始对象的 Proxy，可拦截 get/set/has/deleteProperty/ownKeys 等 13 种操作。
  - 惰性代理：访问嵌套属性时才递归响应化。
  - 配合 `Reflect` 保证默认行为正确。
  - 天然支持动态属性、数组操作、Map/Set。
  - 引入 `ref()`、`computed()`、`effect()`、`watchEffect()` 等 API。
  双向绑定：响应式数据变化驱动视图更新，表单元素通过 `v-model` 语法糖实现视图到数据的同步（本质是指定 `:value` + `@input` 等事件的组合）。

* **Q: React 合成事件原理**
  A: React 合成事件（SyntheticEvent）是跨浏览器原生事件的一层封装。
  目的：
  1. 抹平浏览器差异（事件对象属性、阻止冒泡/默认行为 API）。
  2. 性能优化：使用事件委托统一管理。
  实现：
  - React 16 将事件监听器委托到 `document`；React 17+ 改为 root container。
  - 事件触发后，原生事件冒泡到根节点，React 收集路径上所有 Fiber 节点的监听器。
  - 构造合成事件对象，批量执行回调。
  特点：
  - `event.nativeEvent` 访问原生事件对象。
  - React 17 之前事件对象会被回收复用（事件池），异步访问需 `event.persist()`；React 17+ 移除了事件池。
  - `onScroll` 不委托，因为 scroll 不冒泡，直接绑定在元素上。

* **Q: Vue 组件渲染流程**
  A: Vue 组件完整渲染流程：
  1. 模板编译：将 template 编译为 render 函数。包括 parse（模板 -> AST）、optimize（标记静态节点）、generate（AST -> render 函数字符串）。
  2. 响应式初始化：data/computed 等建立响应式追踪。
  3. 创建 VNode：执行 render 函数生成 VNode 树，访问响应式属性时触发依赖收集。
  4. Patch/Diff：对比新旧 VNode 树，计算最小 DOM 更新。Vue2 双端比较，Vue3 用最长递增子序列优化移动。
  5. DOM 更新：根据 Diff 结果执行真实 DOM 增删改。
  6. 生命周期：触发 beforeCreate/created/beforeMount/mounted 等钩子。
  Vue3 编译优化：静态提升、PatchFlag、Block Tree 大幅减少非必要的 VNode 比较。

* **Q: Vue2 vs Vue3 响应式**
  A: 核心区别：
  | 维度 | Vue2 | Vue3 |
  |---|---|---|
  | 实现 | Object.defineProperty | Proxy |
  | 属性新增/删除 | 无法检测，需 Vue.set/delete | 天然支持 |
  | 数组索引/length | 无法检测，重写了 7 个方法 | 天然支持 |
  | 初始化性能 | 递归遍历所有属性 | 惰性代理，访问时才递归 |
  | 集合类型 | 不支持 Map/Set | 支持 |
  | API | Options API | Options + Composition API |
  | 副作用管理 | Watcher | effect/watchEffect |
  | TS 支持 | 类型推断一般 | 用 TS 重写，类型更好 |
  Vue3 用 WeakMap 按对象维度存储副作用，内存更紧凑。

* **Q: Redux / Zustand / MobX 区别**
  A: 三者设计哲学不同：
  - Redux：函数式、不可变数据、单一 Store。通过 dispatch action -> reducer 返回新 state。流程严格、可预测、调试强大。样板代码多，配合 Redux Toolkit 可简化。
  - Zustand：极简 API，基于 Hooks，单一 Store 可拆分。无需 Provider，按需订阅（selector），不会引起无关组件重渲染。体积小（~1KB）。
  - MobX：面向对象、响应式、可变数据。通过 observable/action/computed 实现自动追踪。自由度高，但追踪不透明，调试相对困难。
  选型建议：大型严格项目用 Redux Toolkit；追求开发体验用 Zustand；偏好响应式/OOP 选 MobX。

* **Q: useContext 实现原理**
  A: `useContext` 是 React 读取 Context 值的 Hook。
  原理：
  1. `React.createContext(defaultValue)` 创建 Context 对象，包含 Provider 和 Consumer。
  2. Provider 将 `value` 存入 Fiber 节点的依赖链表中。
  3. `useContext(Context)` 在渲染阶段从当前 Fiber 向上遍历，找到最近的 Provider，返回其 value；未找到则返回 defaultValue。
  4. Provider 的 value 变化时，React 标记订阅了该 Context 的子 Fiber 需要更新。
  性能注意：Context value 变化会导致所有使用它的组件重渲染。应拆分 Context 粒度，或用 `useMemo` 稳定 value 引用。

* **Q: Hooks vs Class 对比**
  A: 核心对比：
  | 维度 | Class 组件 | Hooks |
  |---|---|---|
  | 状态复用 | HOC/render props，嵌套深 | 自定义 Hook，扁平复用 |
  | 生命周期 | 逻辑分散在不同方法 | useEffect 聚合相关逻辑 |
  | this 指向 | 需绑定或使用箭头函数 | 函数作用域直接捕获 |
  | Tree Shaking | 体积大 | 按需引入，利于压缩 |
  | TS 支持 | 一般 | 更自然 |
  | 学习曲线 | 理解 this 绑定 | 理解闭包陷阱和依赖数组 |
  | 性能优化 | PureComponent/shouldComponentUpdate | React.memo + useMemo/useCallback |
  React 官方推荐 Hooks，Class 组件仍可用但不再新增特性。

* **Q: VDOM vs Fiber**
  A: Virtual DOM 是 DOM 的轻量 JS 表示，通过 Diff 算法最小化真实 DOM 操作，解决声明式 UI 与命令式 DOM 之间的鸿沟。
  Fiber 是 React 16 引入的新的协调引擎（Reconciler），是 VDOM 的升级实现：
  1. 任务分片：每个 Fiber 节点是一个工作单元，渲染可被暂停、恢复、终止。
  2. 双缓冲：current tree 和 workInProgress tree，构建完成后切换指针。
  3. 优先级调度：Lane 模型区分更新优先级，高优先级可打断低优先级。
  4. 两阶段渲染：render 阶段（可中断）和 commit 阶段（不可中断）。
  Fiber 实现时间切片，避免主线程长时间阻塞，为 Suspense、并发模式奠定基础。

* **Q: Suspense 实现原理**
  A: Suspense 用于处理异步依赖的加载状态。
  原理：
  1. 子树渲染过程中，若某个组件抛出一个 Promise（或 thenable），React 捕获该 Promise。
  2. React 暂停该子树渲染，展示 fallback UI。
  3. Promise resolve 后，React 重新尝试渲染子树，此时数据就绪，正常渲染。
  Suspense 边界管理这些状态，支持嵌套。
  数据获取框架（React Query、SWR、Relay）通过抛出 Promise 集成 Suspense。
  React 18 中 Suspense 可与 `startTransition` 结合，保持旧内容可见，避免全屏 loading。
  注意：Suspense 需要框架层配合，不是对所有异步操作自动生效。

* **Q: useEffect 清理函数使用场景**
  A: useEffect 返回的清理函数在组件卸载或依赖变化重新执行前调用。
  典型场景：
  1. 取消订阅：WebSocket、EventSource、addEventListener、RxJS 订阅。
  2. 清除定时器：setInterval、setTimeout。
  3. 取消未完成请求：AbortController.abort() 或设置取消标志。
  4. 关闭连接：WebSocket、IndexedDB 事务。
  5. 清理动画：requestAnimationFrame、动画库实例。
  6. 恢复状态：Modal 关闭时恢复 body overflow、移除全局 class。
  示例：
  ```js
  useEffect(() => {
    const controller = new AbortController();
    fetch(url, { signal: controller.signal });
    return () => controller.abort();
  }, [url]);
  ```
  React 18 严格模式下 Effect 会执行两次（挂载-卸载-挂载），帮助检测清理函数缺失。

* **Q: useMemo / useCallback 在 SSR 中有什么问题**
  A: SSR 中 `useMemo`/`useCallback` 基本不会带来性能收益：
  1. 服务端组件只执行一次，不存在多次重渲染，缓存仅在单次请求内有效，请求结束后内存释放。
  2. 增加了序列化和内存开销，可能使 hydration 的 JS 体积变大。
  3. 若 `useMemo` 内部有副作用，SSR 中执行一次，hydrate 时再执行一次，可能导致不一致。
  最佳实践：SSR 中不要为优化而使用它们，保留仅为了与 CSR 代码逻辑一致。真正的 SSR 优化应关注流式渲染、数据缓存、CDN。

* **Q: Hooks 为什么不能写在循环条件里**
  A: React 内部使用链表按调用顺序存储 Hook 状态。每次渲染时 React 按固定顺序遍历 `memoizedState` 链表。
  如果 Hook 写在 if/for/while 中，条件变化会导致某些渲染跳过某个 Hook，后续 Hook 索引错位，状态混乱。
  示例：
  ```js
  // 错误
  if (condition) {
    const [state, setState] = useState(0);
  }
  ```
  ESLint 的 `react-hooks/rules-of-hooks` 规则强制 Hooks 必须按固定顺序调用。
  解决方案：将条件判断放到 Hook 内部，或提前 return 前不调用 Hook。

* **Q: 为什么 React 19 的 use 可以写在循环 / 条件里**
  A: `use()` 不是传统 Hook，它不依赖调用顺序。
  原理：
  - `use(promise)` 直接读取 Promise 的值，不向 Fiber 的 `memoizedState` 链表注册节点。
  - Promise pending 时，`use()` 会抛出一个 thenable，被 Suspense 捕获，渲染 fallback。
  - Promise resolve 后重新渲染，`use()` 直接从缓存读取结果。
  - 因为它不创建持久化状态，只依赖传入的 Promise/Context 值，所以可以放在条件、循环、提前 return 之后。
  注意：`use()` 需配合 Suspense 使用，目前用于数据获取和读取 Context。

* **Q: useEffect 闭包陷阱**
  A: 闭包陷阱指 Effect 回调中捕获的是旧 state/props，而非最新值。
  原因：每次渲染都会创建新的 Effect 函数闭包，闭包捕获的是该次渲染的快照值。依赖数组未包含变化值时，Effect 中的值不会更新。
  示例：
  ```js
  useEffect(() => {
    const id = setInterval(() => setCount(count + 1), 1000);
    return () => clearInterval(id);
  }, []); // count 永远是初始值
  ```
  解决方法：
  1. 正确填写依赖数组。
  2. 使用函数式更新：`setCount(c => c + 1)`。
  3. 使用 useRef 保存最新值：`ref.current` 始终指向最新值。
  4. 使用 reducer 管理复杂状态。
  核心理解：React 的"渲染快照"语义是设计如此，不是 Bug。

* **Q: React 父子组件通信方式**
  A: React 组件通信方式：
  1. Props（父 -> 子）：最常见的下行数据流。
  2. Callback Props（子 -> 父）：父传函数，子调用时回传数据。
  3. 状态提升：兄弟组件共享状态提升到最近公共父组件。
  4. Context API：跨层级传递主题、语言、用户信息等。
  5. useImperativeHandle + forwardRef：父通过 ref 调用子组件方法（如表单校验、聚焦）。
  6. 全局状态管理：Redux、Zustand、MobX。
  7. Event Bus：发布订阅，但不利于追踪，不推荐。
  React 强调单向数据流：数据向下、事件向上。优先状态提升，必要时再用全局状态。

* **Q: React Native vs Web 区别**
  A: 核心区别：
  | 维度 | React Web | React Native |
  |---|---|---|
  | 渲染目标 | DOM | 原生 UI 组件（UIView/Android View） |
  | 组件 | div/span 等 | View/Text/Image 等 |
  | 样式 | CSS 层叠继承选择器 | JS 对象样式，Flexbox 为主 |
  | 导航 | URL 路由 | React Navigation 原生导航 |
  | 线程 | 单线程 | JS 线程 + 原生线程 + Shadow/Yoga 线程 |
  | 调试 | 浏览器 DevTools | Chrome DevTools / Flipper |
  | 性能瓶颈 | DOM 操作 | JS 与原生桥接通信 |
  RN 适合需要原生性能且共享代码逻辑的移动端应用。新架构（JSI/Fabric/TurboModules）通过直接内存访问替代桥接。

* **Q: React Navigation Stack 层数限制**
  A: React Navigation Stack 没有硬编码的数字限制，但底层原生导航实现（UINavigationController / FragmentManager）和系统内存构成实际约束。
  深层嵌套问题：
  1. 内存累积：每个 Screen 保持视图层级和状态。
  2. 动画卡顿：深层 Push/Pop 转场叠加增加 GPU 压力。
  3. 手势返回延迟：深层栈右滑返回响应变慢。
  建议：
  - 遵循 iOS HIG，层级控制在 3-4 层以内。
  - 超过时用 Modal、Tab 或嵌套导航拆分。
  - 使用 `reset` 替代无限 `navigate`。
  - Android 上超过 50 层可能触发 FragmentManager 问题。
  - 无限详情页等场景可用状态管理模拟路由参数变化，而非无限 push。

### 工程化
* **Q: npm / yarn / pnpm 原理对比**
  A: 三者都是 Node.js 包管理器，核心区别在于依赖管理策略：
  1. npm v1/v2：嵌套 node_modules，路径过长，Windows 易超出路径限制。
  2. npm v3 / yarn v1：扁平化 node_modules，将依赖提升到顶层。解决嵌套问题但导致"幽灵依赖"（项目可访问未声明的包）；版本冲突时仍需嵌套。
  3. pnpm：硬链接 + 符号链接。依赖存储在全局 store，项目通过硬链接引用，同版本只存一份。node_modules 结构与 package.json 严格对应，避免幽灵依赖。每个包的依赖通过符号链接找到自己的依赖，保持嵌套结构但不重复存储。
  pnpm 优势：磁盘空间省、安装速度快、严格隔离、Monorepo workspace 原生支持。
  yarn v2/v3（PnP）：通过 .pnp.cjs 映射文件消除 node_modules，但兼容性挑战较多。
  当前趋势：新项目推荐 pnpm。

* **Q: Sentry 日志监控**
  A: Sentry 是开源的错误追踪和性能监控平台。
  前端接入：
  ```js
  Sentry.init({
    dsn: '...',
    environment: 'production',
    tracesSampleRate: 0.2
  });
  ```
  核心功能：
  1. 错误捕获：未处理异常、Promise rejection、React ErrorBoundary。
  2. 手动上报：`captureException`、`captureMessage`。
  3. 性能追踪：Trace、Span、页面加载、路由切换、API 请求。
  4. Source Map：上传 Source Map 反解生产错误堆栈。
  5. Breadcrumbs：记录事件序列帮助定位上下文。
  6. Release 追踪：关联错误与版本。
  7. Session Replay：录制用户操作回放。
  最佳实践：配置 `beforeSend` 过滤噪音错误；CI/CD 自动上传 Source Map；生产环境不公开 Source Map。

* **Q: SSR / ISR 原理**
  A: SSR（服务端渲染）：请求时在服务端渲染完整 HTML，浏览器首屏可见，再 hydrate 为可交互 SPA。优点是首屏快、SEO 友好；缺点是 TTFB 长、服务端负载高。
  ISR（增量静态再生）：在 SSG 基础上实现按需更新。
  流程：
  1. 构建时生成静态 HTML 到 CDN，设置 `revalidate` 时间（如 60 秒）。
  2. 在 revalidate 时间内请求，直接返回缓存 HTML。
  3. 超过 revalidate 时间后，请求返回缓存版本，同时后台重新生成新页面并更新缓存。
  Next.js 中通过 `getStaticProps` 的 `revalidate` 属性和 `res.revalidate(path)` 实现。
  适用场景：电商商品页、博客文章等更新频率不高但需要 SEO 的页面。

* **Q: Next.js SSR 原理**
  A: Next.js SSR 核心机制：
  1. 服务端接收请求，匹配路由。
  2. 执行页面级 `getServerSideProps`（每次请求都运行），获取数据。
  3. 将 props 注入页面组件，React 在服务端渲染生成 HTML。
  4. 返回 HTML，浏览器首屏可见。
  5. 浏览器加载 JS 后执行 Hydration，将静态 HTML 变为可交互 SPA。
  6. 后续路由跳转通过 `next/link` 客户端路由实现 CSR。
  注意：
  - `getServerSideProps` 只在服务端运行，不会打包到客户端。
  - 服务端无 DOM，`window`/`document` 不可用，需在 `useEffect` 中条件执行。
  - React 18 支持 Streaming SSR，配合 Suspense 分块发送 HTML。

* **Q: WebSocket 握手**
  A: WebSocket 握手使用 HTTP Upgrade 机制从 HTTP 升级为 WebSocket 协议。
  流程：
  1. 客户端发送 HTTP GET 请求，携带：
     - `Upgrade: websocket`
     - `Connection: Upgrade`
     - `Sec-WebSocket-Key: base64(16字节随机数)`
     - `Sec-WebSocket-Version: 13`
  2. 服务端返回 101 Switching Protocols，携带：
     - `Upgrade: websocket`
     - `Connection: Upgrade`
     - `Sec-WebSocket-Accept: base64(SHA1(Key + 固定GUID))`
  3. 客户端校验 `Sec-WebSocket-Accept` 后，连接升级为全双工 WebSocket。
  此后通信使用 WebSocket 帧格式，而非 HTTP 请求-响应。
  注意：通过 Nginx 等代理转发时，需配置 Upgrade 和 Connection 头。

### 性能优化
* **Q: 首屏优化**
  A: 首屏优化目标是缩短 FCP（First Contentful Paint）和 LCP（Largest Contentful Paint）。
  策略维度：
  1. 网络：HTTP/2、CDN、Preconnect、DNS-prefetch、preload 关键资源。
  2. 资源体积：Code Splitting、Tree Shaking、JS/CSS 压缩、Gzip/Brotli、图片用 WebP/AVIF、字体子集化。
  3. 渲染：Critical CSS 内联、SSR/SSG、骨架屏、图片懒加载、避免同步脚本阻塞。
  4. 缓存：强缓存版本化静态资源、Service Worker、HTML 协商缓存。
  5. 度量：Lighthouse、Web Vitals，目标 LCP < 2.5s、INP < 200ms、CLS < 0.1。
  不同业务侧重点不同：电商重图片和列表，内容站重 SSR。

* **Q: 虚拟列表滚动原理**
  A: 虚拟列表只渲染可视区域内元素，上下超出部分用空白占位，解决大数据量渲染性能问题。
  核心步骤：
  1. 计算可视区域可容纳行数：`visibleCount = Math.ceil(viewportHeight / itemHeight)`。
  2. 监听 scroll，计算起始索引：`startIndex = Math.floor(scrollTop / itemHeight)`。
  3. 渲染 `[startIndex, startIndex + visibleCount]` 范围内元素。
  4. 用上下 padding 或 `transform: translateY` 将渲染列表偏移到正确位置。
  优化点：
  - 动态高度：渲染后回调上报真实高度，维护位置映射表。
  - 缓冲冗余（overscan）：多渲染上下几行，避免快速滚动白屏。
  - 使用 `transform` 替代 `top` 减少回流。
  - 使用 IntersectionObserver 替代 scroll 事件提升性能。
  常用库：react-window、react-virtuoso、vue-virtual-scroller。

* **Q: 图片懒加载方案**
  A: 图片懒加载延迟加载屏幕外图片，减少初始请求和带宽。
  方案：
  1. IntersectionObserver（推荐）：
     ```js
     const observer = new IntersectionObserver(entries => {
       entries.forEach(entry => {
         if (entry.isIntersecting) {
           const img = entry.target;
           img.src = img.dataset.src;
           observer.unobserve(img);
         }
       });
     });
     document.querySelectorAll('img[data-src]').forEach(img => observer.observe(img));
     ```
  2. 原生 `loading="lazy"`：最简单，但无法自定义占位和触发时机。
  3. scroll + getBoundingClientRect：需 debounce，性能较差。
  4. 占位处理：LQIP 低质量模糊图、纯色背景、aspect-ratio 占位。
  注意事项：首屏图片不要懒加载，避免影响 LCP；预留尺寸避免 CLS。

* **Q: 轮播图实现思路**
  A: 轮播图核心实现思路：
  1. 布局：外层容器 `overflow: hidden`，内部容器 flex 排列，通过 `transform: translateX` 控制偏移。
  2. 自动播放：`setInterval` 定时切换，鼠标悬停暂停。
  3. 无限循环：首尾各克隆一个 slide，切换到克隆位置时无动画跳转。
  4. 指示器：小圆点导航。
  5. 手势：移动端 touch 事件计算位移差。
  6. 性能：用 `transform` + `requestAnimationFrame`，图片懒加载非可见 slide。
  7. 无障碍：`role="listbox"`、aria-label、键盘左右键支持。
  复杂场景建议用 swiper.js、Embla Carousel 等成熟库。

### 综合 / 场景
* **Q: 技术选型怎么做**
  A: 技术选型需综合考虑：
  1. 业务需求：项目规模、性能要求、目标平台、更新频率、SEO 需求。
  2. 团队能力：技术栈熟悉度、学习成本、招聘难度。
  3. 技术生态：社区活跃度、文档完善度、第三方库丰富度、版本稳定性。
  4. 框架特性：SPA 选 React/Vue；SEO 需求选 Next.js/Nuxt；大量 DOM 操作考虑 Svelte/Solid。
  5. 运行时性能：轻量应用差异不大，大列表/高频更新选 Solid/Svelte。
  6. 工程化：构建工具、代码规范、测试、CI/CD。
  7. 迁移成本：老项目重构需平滑迁移方案。
  方法论：列出候选 -> POC 验证 -> 对比矩阵 -> 团队决策。

* **Q: 大文件上传**
  A: 大文件上传核心方案：分片 + 断点续传。
  实现步骤：
  1. 分片：用 `File.slice()` 切成固定大小（如 5MB）。
  2. 并发控制：限制同时上传切片数，避免连接数限制和内存溢出。
  3. 断点续传：上传前请求后端已上传切片列表，只传缺失部分。
  4. 哈希计算：用 spark-md5 或 Web Worker 计算文件 MD5，作为唯一标识。
  5. 进度：通过 XHR `upload.onprogress` 或分片进度汇总。
  6. 合并：所有切片上传完成后通知后端合并。
  7. 失败重试：单个切片失败自动重试。
  8. 暂停/恢复：记录已上传切片，暂停时中止未完成请求。
  常用库：uppy、plupload、resumable.js。

* **Q: Token 过期，正好在提交时怎么处理**
  A: 核心方案：请求拦截器 + Token 静默刷新 + 请求队列。
  流程：
  1. 请求发出前检查 Token 过期时间，若即将过期则同步刷新。
  2. 若未预检而收到 401，进入刷新流程：
     - 暂停当前请求，保存到队列。
     - 检查是否已有刷新请求，避免重复刷新。
     - refreshToken 成功后，用新 accessToken 重放队列中所有请求。
     - refreshToken 也过期则跳转登录。
  关键代码模式：
  ```js
  axios.interceptors.response.use(
    res => res,
    async err => {
      const original = err.config;
      if (err.response?.status === 401 && !original._retry) {
        original._retry = true;
        await refreshToken();
        original.headers.Authorization = `Bearer ${getToken()}`;
        return axios(original);
      }
      return Promise.reject(err);
    }
  );
  ```
  注意：
  - refreshToken 存 HttpOnly Cookie 最安全。
  - refresh 请求本身需排除拦截，避免死循环。
  - Token 即将过期时预先刷新（如 exp - now < 5min）可避免批量 401。
