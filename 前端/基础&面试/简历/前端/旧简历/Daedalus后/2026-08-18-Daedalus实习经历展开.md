## 具体工作一：Crate 关联路径表单重构（COD-171）
### 背景问题
Crate 需要维护一组关联路径。旧方案同时维护：

- 用于输入中的 `pathDraft` / `pathTypeDraft` 本地状态；
- React Hook Form 中真正用于提交的 `paths` 数组。

这形成了两个数据源，容易出现 stale closure：用户刚输入的路径已经显示在页面上，但提交时 payload 仍然拿到旧值。空值和重复值还会被静默忽略，用户不知道自己的操作是否生效。

### 我做的事情
- 抽离 `CratePathsField` 领域组件，减少 `CrateDialog` 中的复杂分支。
- 使用 React Hook Form `useFieldArray` 直接管理每一行路径，移除长期存在的草稿状态。
- 点击“添加路径”后直接新增一行并聚焦，让新增和编辑使用同一种交互模型。
- 使用共享 Zod Schema 做字段校验，并把错误定位到具体路径行。
- 处理空值、重复值和非法格式，不再让校验失败静默发生。

### 这项工作体现的能力
- React Hook Form 的 Field Array 与表单身份管理。
- 复杂表单的单一数据源设计。
- 领域组件拆分，而不是把所有逻辑堆在页面 Dialog 中。
- 从交互问题追到数据流和闭包时序问题。

### 结果与边界
该需求经历了首次实现、修复、回退和重写，最终在 7 月 16 日合并。这里可以明确说“完成了表单交互和数据流重构”，但不应把它描述成单纯的视觉改版。

## 具体工作二：Repository 归属与筛选链路（COD-173 / COD-174）
### 背景问题
Repository 归属、列表筛选和关联项目展示同时涉及前端表单语义、共享数据契约和列表数据 enrichment。原实现中存在几类风险：

- `undefined`、`null` 和空字符串的更新语义没有明确区分。
- 列表拿到多条记录后，逐条查询关联 GitHub 项目，存在 N+1 查询风险。
- 新增的搜索框和选择器直接使用原生控件，和项目已有 UI 规范不一致。
- 并行需求修改 Schema 时，migration 编号发生冲突。

### 我参与的处理
- 明确三种值的语义：`undefined` 表示不更新，字符串表示绑定，`null` 表示解绑。
- 配合把关联项目查询改成批量 `getByIds(ids)`，避免列表逐项 enrichment。
- 将搜索 `input` 和 Repository `select` 替换为项目已有的 UI 组件。
- 在实现前检查共享 Schema、develop 基线和 UI 组件目录，减少返工。

### 这项工作体现的能力
- 前端表单值与后端更新语义的对齐。
- 列表数据流、批量查询和跨层契约意识。
- 在 Monorepo 中遵守已有组件规范，而不是重复造原生控件。
- 处理并行分支对 Schema 和 migration 的影响。

## 具体工作三：大型仓库文件树虚拟化（COD-220）
### 背景问题
项目详情页左侧展示 GitHub 仓库文件树。原实现由递归节点组件渲染，并且目录默认展开。仓库规模变大后，会同时创建大量 React 组件、DOM 节点、事件处理器和 Effect，导致首屏渲染与滚动协调成本上升。

### 我做的方案
我没有只给递归节点加 `memo`，而是改变了渲染模型：

```text
完整 GitHub 文件树
  + 集中式展开状态 expandedPaths
  ↓
扁平化当前可见节点 visibleNodes
  ↓
@tanstack/react-virtual 计算视口附近的行
  ↓
只挂载少量 ProjectFileTreeNode
```

具体实现包括：

- 新增 `ProjectFileTree` 容器，集中管理展开状态、扁平化和虚拟列表。
- 将 `ProjectFileTreeNode` 改成受控的单行组件，不再递归渲染 children。
- 使用显式栈做深度优先遍历，把树转换成带 `depth` 的线性列表。
- 使用 `Set<string>` 保存展开路径，使用仓库、分支和 owner 组成 tree identity。
- 切换仓库或分支时重置展开状态和滚动位置；树刷新时清理已经不存在的路径。
- 使用固定 28px 行高、路径稳定 Key、12 行 overscan 和绝对定位。
- 补充 `role="tree"`、`role="treeitem"`、`aria-level`、`aria-expanded`、`aria-selected` 和基础键盘交互。
- 保留原有的文件选择、扫描文件/目录和跳转 GitHub 等业务行为。

### 结果与验证
- 该实现针对 500+ 节点仓库的滚动卡顿问题，减少了实际挂载的 DOM 和 React 协调规模。
- `bun run quality` 和 `bun run build` 通过。
- 最终提交记录为 `4173387 feat(COD-220): virtualize large repository file trees`。

### 需要诚实说明的限制
- 完整 GitHub 文件树仍一次性保存在前端内存中，本次没有实现目录级懒加载。
- 扁平化在展开状态变化时同步执行，极端超大目录仍需要进一步基准测试。
- 目前是基础树键盘交互，还不是完整的 WAI-ARIA Tree Pattern。
- 不能把“500+ 节点”改写成“稳定 60 FPS”或“响应低于 100ms”，因为自动化性能基准仍是后续技术债务。

## 具体工作四：Archetype、Conformance 与详情页结构
### 业务理解
Archetype 不是普通标签，而是描述“一个实例需要满足什么条件”的设计契约。Condition 可以是文本，也可以引用另一个 Archetype，因此页面需要处理动态条件列表、类型切换、引用选择和循环引用等边界。

### 我参与的内容
- 参与 Archetype 列表、创建/编辑表单和动态 Condition 编辑器相关页面理解与实现。
- 处理名称唯一、Scope 枚举、至少一个 Condition、空值和自引用等交互边界。
- 在 Crate 详情页参与 Conformance 相关 Tab 重组，让用户能从页面进入扫描和检查结果链路。
- 关注跨层 Job 的上下文契约：临时 `RuleContext` 和 `targetFiles` 需要序列化到 `context_snapshot`，worker 恢复时再校验并执行。
- 参与识别“上下文构建失败时应该 update 现有 Job，而不是重复 insert”的状态机问题。

### 状态说明
Conformance 涉及页面、Service、Job 和 worker 多层改动，部分 PR 在复盘时仍处于 In Review。因此这部分更适合表述为“参与实现和问题拆解”，不应直接写成“完整扫描链路已经生产上线”。

## 具体工作五：MCP 连接管理与 OAuth 接入（COD-305）
### 目标
让用户在 Daedalus 设置页创建一条绑定 Workspace 和客户端类型的 MCP 连接，并完成安装引导、授权确认、状态复查和撤销流程。

### 前端工作
- 在 Settings 中增加 MCP Tab。
- 完成连接创建 Dialog、连接列表、详情 Dialog、状态复查和永久撤销确认。
- 增加公开安装页和登录后的 OAuth Consent 页面。
- 使用 Refine `useList`、`useOne`、`useCreate`、`useCustomMutation` 和 `useInvalidate` 管理列表、详情和写操作后的缓存一致性。
- 通过 `dataProvider → tRPC` 接入项目既有数据流，页面不直接调用 tRPC。
- 将页面专用组件放在对应的 `pages/` 目录，而不是随意放进全局 `components/`。
- 将状态、失败原因、安装说明和操作反馈纳入中英文 i18n。
- 为基础态、空态、失败态、提交态和复查态补充 Storybook Stories。

### 跨层协作与安全边界
这项工作虽然以页面为入口，但需要理解后端和认证边界：

- 用 Zod Schema 集中定义客户端类型、连接状态、失败码、创建输入和详情实体。
- 区分 `pending`、`active`、`failed`、`unavailable`、`revoked`，让 UI 不把所有异常都显示成简单的“离线”。
- 连接授权同时检查 Token 用户、OAuth Client、业务连接和 Workspace 成员权限。
- 撤销时需要同步禁用 OAuth Client、清理 Token/Consent 并更新业务连接状态，避免 UI 状态与凭证状态不一致。

### 验证结果
这份实现记录了以下本地验证结果：

- `apps/app` 的 `bun run quality` 通过。
- 29 个测试文件、101 项测试通过。
- Storybook 静态构建成功。

### 不能夸大的部分
- 该记录明确说明这是尚未提交的实现复盘，不能写成“已经生产上线”。
- 真实 Codex、Claude Code 等客户端的 OAuth E2E、Token Exchange 和 MCP initialize 仍需单独 smoke 验收。

## 具体工作六：MCP Provider 边界问题排查
### 问题
`McpSetupGuide` 在 MCP Setup 页面正常，但被复用到连接详情 Dialog 后，`useMcpSetupPageStore()` 从 Context 取到 `null` 并抛错。

### 排查过程
我沿着 Consumer 反向检查真实渲染树：

```text
McpSetupGuide
  → useMcpSetupPageStore
  → useContext(McpSetupPageStoreContext)
```

发现正常页面路径拥有 `McpSetupPageStoreProvider`，但 Dialog 路径只有另一个页面的 Provider。React Context 按 Context 对象匹配，Store 结构相似并不能互相替代。

### 修复与验证
- 在 Dialog 中补上正确的 `McpSetupPageStoreProvider`。
- 使用 `key={connection.id}`，在连接 A 切换到连接 B 时重新创建带有正确 `setup` 闭包的 Store。
- 清理排查期间留下的 `console.log` 和 TODO。
- 目标 oxlint 检查通过。
- Dialog、Guide、Store 三个相关测试文件通过。

### 仍需补强
- 测试仍额外包裹了 Provider，生产树和测试树还没有完全一致。
- 需要补充连接 A 切换到连接 B 后复制内容不串线的回归测试。
- 独立 Content Story 仍需要通过 decorator 或专用 Wrapper 补齐 Provider。
- Prettier、全量类型检查和 Storybook 环境仍存在独立阻塞，不能把局部测试通过写成全仓质量通过。
