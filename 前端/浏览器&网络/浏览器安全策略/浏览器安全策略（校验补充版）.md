## 一、先区分几个概念
### Origin（源）
一个 URL 的 **origin** 通常由三部分组成：**scheme（协议）、host（主机名）、port（端口）**。只有这三部分都相同，两个 URL 才是同源；路径、查询字符串和片段不参与同源判断。

例如：

| URL | 与 `https://app.example.com:443/a` 是否同源 | 原因 |
|---|---:|---|
| `https://app.example.com:443/b` | 是 | 路径不同不影响源 |
| `http://app.example.com:80/a` | 否 | scheme 不同 |
| `https://api.example.com:443/a` | 否 | host 不同 |
| `https://app.example.com:8443/a` | 否 | port 不同 |

> 注意：`host` 不等同于“注册域名”。例如 `app.example.com` 和 `api.example.com` 的 host 不同，因此不同源。`localhost`、IP 地址以及某些特殊 URL 还可能有特殊的源判定规则。

### Site（站点）
**site 不是 origin。** 在通常的 Web 安全语境中，site 由 scheme 与可注册域（registrable domain，常写作 eTLD+1）共同决定，这就是 **schemeful same-site**。同站判断通常忽略子域名和端口，但不会因此变成同源。

例如，`https://app.example.com` 与 `https://api.example.com:8443` 可以是同站但不同源；它们是否能互相读 DOM、读取响应，仍要按同源策略和 CORS 规则判断。

### 同源策略（Same-origin policy）
同源策略是浏览器对 Web 内容进行隔离的核心机制，主要限制一个源的脚本读取另一个源的数据。它不是“所有跨域操作都禁止”：跨源页面仍可通过导航、表单提交、图片、脚本、样式表等方式发起或嵌入部分请求，但读取权限通常受到限制。

- **DOM 与 JavaScript 对象**：跨源页面不能自由读取或修改对方 DOM；对跨源 `Window` 对象只能访问少量受控属性和方法。
- **网络请求**：`fetch`/XHR 可能已经把请求发送到服务器，但浏览器默认不把不满足 CORS 的响应交给调用方脚本。简单请求通常不会因为缺少预检而自动安全，服务器仍需校验请求意图和权限。
- **存储隔离**：`localStorage`、`sessionStorage`、IndexedDB 等主要按 origin 隔离；Cookie 的匹配还受 domain、path、Secure、SameSite、分区策略和浏览器隐私策略影响，不能简单概括为“按 origin 共享”。
- **跨窗口通信**：需要跨源通信时，应优先使用 `window.postMessage()`，并在接收方严格校验 `event.origin`，不要无条件信任 `event.data`。


### 打开关系与 `window.opener`
`window.open()` 或链接导航会建立浏览上下文之间的 opener 关系，但**建立关系不等于获得对方页面的完整控制权**。跨源时，脚本通常只能访问受限的 `Window` 接口；同源时才可能访问更多 DOM 和 JavaScript 对象。

从安全角度看，打开新窗口时应考虑反向标签页劫持（reverse tabnabbing）：

```html
<a href="https://example.com" target="_blank" rel="noopener noreferrer">
  打开外部页面
</a>
```

也可以使用 `window.open(url, '_blank', 'noopener')`。现代浏览器对部分 `target="_blank"` 场景已默认采用类似 noopener 的行为，但显式写出 `rel="noopener"` 更清楚，也更便于兼容和代码审查。

## 二、浏览器安全沙箱与进程隔离
### 安全沙箱不等于“一个 Tab 一个进程”
浏览器的安全边界是多层防御：同源策略负责 Web API 层面的数据隔离，进程隔离和操作系统沙箱负责降低渲染器被攻破后的影响范围。**进程不是安全沙箱唯一或固定的最小单位，也不存在“Tab 与渲染进程一一对应”的简单关系。** 一个渲染进程可能承载多个页面；浏览器也会根据站点隔离、性能和资源情况动态创建或复用进程。

Chromium 等浏览器会使用多进程架构，把浏览器主进程、渲染器进程、GPU 进程等分开，并对渲染器施加操作系统级限制。Site Isolation 会尽量把不同站点放入不同的渲染器进程，但它是实现层面的防护策略，不应替代同源策略，也不应被理解为业务代码可以依赖的跨源通信机制。

### `iframe sandbox`
HTML 的 `iframe sandbox` 是另一层 Web 平台能力。未指定例外时，它会限制被嵌入文档的脚本、表单、弹窗、同源访问等能力；需要时可按最小权限添加 `allow-scripts`、`allow-forms`、`allow-popups` 等令牌。对不可信内容嵌入时，应同时配置合适的 CSP、权限策略和消息校验。

## 三、HTTPS、TLS 与数字证书
### HTTPS 提供什么
HTTPS 是 HTTP 运行在 TLS 保护通道之上。TLS 主要提供：

- **机密性**：降低通信内容被窃听的风险；
- **完整性**：降低传输内容被篡改而不被发现的风险；
- **服务器身份认证**：通过证书链和主机名校验，降低连接到冒充服务器的风险。

“HTTPS 加密了所有信息”是过度绝对的说法：HTTP 内容会在 TLS 记录层中受到保护，但 IP 地址、连接时间、流量规模等部分元数据可能仍可被观察；HTTPS 也不能阻止服务器本身、浏览器扩展或终端恶意软件读取明文。

### SSL 已废弃，现代重点是 TLS
SSL 3.0 是历史协议，TLS 1.0/1.1 也已不应作为现代 Web 服务的默认协议。当前应优先使用 TLS 1.2 和 TLS 1.3，并根据实际客户端兼容性与服务器配置禁用过时协议和不安全密码套件。日常口语中的“SSL 证书”通常实际指 TLS 使用的 X.509 证书，不代表连接仍在使用 SSL。

### TLS 1.3 握手的正确简化模型
原笔记中“客户端用服务器证书公钥加密 pre-master secret”的流程主要对应旧式 RSA 密钥交换，不能作为现代 TLS 1.3 的通用描述。TLS 1.3 的高层过程可以理解为：

1. **ClientHello**：客户端发送支持的版本、密码套件、随机数以及密钥共享参数（通常来自 (EC)DHE）。
2. **ServerHello**：服务器选择参数并返回自己的密钥共享参数；双方据此独立计算共享秘密。
3. **证书与签名**：服务器发送证书链，并使用证书对应的私钥对握手 transcript 签名；客户端验证证书链、主机名、有效期及用途等。
4. **派生会话密钥**：双方使用 HKDF 等密钥派生机制，从握手秘密派生出握手阶段和应用数据阶段的密钥。
5. **Finished 校验与应用数据**：双方验证握手未被篡改，之后用对称 AEAD 算法保护 HTTP 数据。

因此，现代 TLS 的重点不是“公钥加密一把会话密钥”，而是使用非对称密码完成身份认证和密钥协商，再使用对称密码高效保护数据。基于 (EC)DHE 的密钥交换还可以提供前向保密：即使服务器长期私钥日后泄露，也不应直接解密过去抓取的会话流量。

### CA 与证书验证
证书颁发机构（CA）不是“保证网站一定可信”的机构，而是参与公开密钥基础设施（PKI）信任链的实体。浏览器或操作系统维护受信任的根证书；服务器通常发送终端证书和中间证书，客户端据此构建并验证到受信任根的证书路径。

证书验证通常包括：

- 证书链签名和信任锚点；
- 有效期；
- 请求主机名是否匹配 Subject Alternative Name；
- 密钥用途和签名算法；
- 浏览器实施的撤销、约束与策略检查。

证书验证通过只能说明“本次连接的服务器满足证书体系的身份约束”，不说明网站没有漏洞、业务一定合法，也不意味着证书绝对无法被误签或私钥绝对不会泄露。

## 四、常见 Web 攻击与防护
### XSS（跨站脚本攻击）
XSS 是应用程序把不可信数据以可执行脚本或危险 HTML 的方式送入浏览器，导致攻击者代码在受害者站点上下文中执行。常见分类包括：

- **存储型 XSS**：恶意输入被保存，之后被其他用户加载；
- **反射型 XSS**：恶意输入经请求进入响应，并在页面中被不安全地解释；
- **DOM 型 XSS**：客户端脚本从 URL、存储或消息等来源读取数据，并写入危险 DOM sink；不一定经过服务器回显。

防护重点不是笼统地“过滤脚本”，而是：

1. 按 HTML、属性、URL、JavaScript、CSS 等输出上下文做正确编码；
2. 优先使用 `textContent`、安全的 DOM API 和框架默认转义，避免把不可信字符串传给 `innerHTML`、`eval` 等危险 sink；
3. 确需渲染富文本时使用经过审计的 HTML sanitizer；
4. 使用 CSP 限制脚本来源，并在条件允许时采用 nonce/hash；高风险应用可结合 Trusted Types；
5. Cookie 根据用途配置 `HttpOnly`、`Secure`、`SameSite`，减少脚本窃取和跨站滥用的影响。

CSP 是纵深防御，不是替代输出编码和安全 DOM 操作的“万能开关”。

### CSRF（跨站请求伪造）
CSRF 利用浏览器自动携带的身份凭证，让受害者在已登录状态下向目标站点发送非预期请求。攻击不一定需要用户点击链接，跨站表单、图片、自动跳转或其他可触发请求的方式都可能参与；是否成功取决于请求方法、Cookie 策略、浏览器限制以及服务器是否正确校验。

防护措施应组合使用：

- 对状态改变请求使用不可预测且与用户会话绑定的 CSRF Token；
- 校验 `Origin`，必要时回退检查 `Referer`，并拒绝缺失或异常的来源；
- 按业务需要设置 Cookie 的 `SameSite=Lax` 或 `Strict`，敏感 Cookie 同时使用 `Secure`；不要把 `SameSite=Strict` 当成所有业务流程都适用的唯一方案；
- 使用合适的身份验证、授权和幂等设计；
- 可结合 Fetch Metadata 请求头进行跨站请求策略控制。

CORS 主要控制“脚本能否读取跨源响应”，不是通用的 CSRF 防护方案；简单跨站请求仍可能到达服务器。

### SSRF（服务端请求伪造）
SSRF 是服务器代表攻击者请求其本不应访问的地址。它属于服务端应用安全问题，不是浏览器同源策略能够直接解决的问题。风险目标可能包括云实例元数据服务、内网管理面板、回环地址、链路本地地址或其他受信网络服务。

防护建议：

- 能不用“用户提供 URL 由服务器代请求”就不要提供；
- 对协议、主机、端口和路径使用严格白名单，而不是只维护黑名单；
- 解析并规范化 URL，防止 DNS rebinding、IP 编码、重定向和解析差异绕过；
- 对解析出的 IPv4/IPv6 地址阻断 loopback、私有网段、link-local、保留地址和云元数据地址；
- 限制服务器出网能力，使用网络层 egress policy；
- 每次重定向都重新校验目标，并设置超时、响应大小和连接数限制；
- 不把“服务器访问带有身份凭证”作为安全边界。

原笔记仅写“黑名单或白名单”，其中黑名单容易漏项；实际防护应以正向允许、网络隔离和多次校验为主。

## 五、CORS、JSONP 与反向代理
### CORS
CORS 是服务器通过响应头声明“哪些跨源请求可以被浏览器脚本读取”的机制。它不是绕过同源策略的前端开关，而是浏览器与服务器共同参与的读取授权流程。

典型响应头示例：

```http
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Access-Control-Allow-Methods: GET, POST, PUT
Access-Control-Allow-Headers: Content-Type, Authorization
```

当请求需要预检时，浏览器会先发送 `OPTIONS`。若请求携带凭证，`Access-Control-Allow-Origin` 必须是明确的 origin，不能与 `Access-Control-Allow-Credentials: true` 一起使用 `*`。同时，服务器不能只依赖 CORS 来保护写操作，应继续进行身份认证、授权和 CSRF 防护。

### JSONP
JSONP 利用 `<script src="...">` 可跨源加载脚本的历史行为，通过回调函数接收数据，因此通常只能使用 GET，并要求服务端返回 JavaScript。它存在脚本执行权限过大、回调注入、错误处理能力弱等问题，现代项目应优先使用 HTTPS + CORS；不要把 JSONP 用于敏感数据或写操作。

### 反向代理
反向代理位于客户端和后端服务之间：

```text
客户端 → 反向代理 → 后端服务
客户端 ← 反向代理 ← 后端服务
```

它可以统一域名和端口、按路径路由、做负载均衡、缓存、压缩、TLS 终止和 WAF 接入。对前端而言，反向代理常用于让 `/api` 与页面使用同一 origin，从而减少 CORS 配置；但它不会自动修复后端的认证、授权、注入或 CSRF 问题。

## 六、其他重要浏览器安全机制
### 混合内容（Mixed Content）
HTTPS 页面加载 HTTP 资源会形成混合内容风险。现代浏览器会主动升级或阻止一部分可升级/可阻止资源；生产环境应让页面及其依赖资源都使用 HTTPS，并避免把 HTTP API、脚本、样式或字体嵌入 HTTPS 页面。

### HSTS
服务器可通过 `Strict-Transport-Security` 告诉浏览器后续只使用 HTTPS 访问该主机。HSTS 必须通过安全连接发送；启用前应确认所有子域、重定向和证书配置都已准备好，否则可能导致站点不可访问。

### 常见安全响应头
```http
Content-Security-Policy: default-src 'self'; object-src 'none'; frame-ancestors 'none'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=()
Cross-Origin-Opener-Policy: same-origin
```

这些响应头应结合业务需求逐项配置，不能机械复制；例如 `frame-ancestors 'none'` 会禁止页面被 iframe 嵌入，`COOP: same-origin` 会影响跨窗口 opener 关系。

## 七、快速检查清单
- [ ] 是否正确区分 origin、site、域名和 URL？
- [ ] 是否把 CORS 误当成“请求不会发出”或 CSRF 防护？
- [ ] 是否使用 TLS 1.2/1.3，并避免用旧 RSA pre-master 流程解释 TLS 1.3？
- [ ] 是否对跨源通信使用 `postMessage` 并校验 `event.origin`？
- [ ] 是否对外部新窗口设置 `rel="noopener"`？
- [ ] 是否使用上下文相关输出编码，而不是只做字符串过滤？
- [ ] 状态改变请求是否有 CSRF Token、Origin/Referer 校验和合适的 SameSite？
- [ ] 用户可控 URL 是否采用白名单、地址解析校验和出网隔离？
- [ ] 是否检查混合内容、CSP、HSTS、权限策略和其他安全响应头？
