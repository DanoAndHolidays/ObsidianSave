# 身份认证
## Session
由于http是无状态的，使用Session ID来保存用户的信息。通过将用户的信息存储在服务器中，再生成一个session用来代表用户的登录状态：
![[Pasted image 20251125123233.png]]

在收到服务器的相应之后，前端每次访问都会附带cookie中的内容

简单来说，Session 是**“服务器记住你”**，而 Token 是**“你自己证明你是谁”**。

为了让你更直观地理解，我们可以先打个比方：

- **Session** 就像你去一家熟悉的咖啡馆，老板在**店里的电脑（服务器）**上记下了你的喜好和余额。你只需要带一张**会员卡（Session ID）**，老板刷卡就能在电脑里查到你的所有信息。
- **Token** 就像一张**加密的门票或盖章的通行证**。你每次进店都直接出示这张票，老板只需要**检验票上的章和防伪标识（验证签名）**，就能确认你的身份和权限，完全不需要去查店里的电脑。

## Token
JWT（JSON Web Token）用来解决Session存储在服务器以及在多个服务器中登录转态可能不一致的问题，Token是存储于用户端的：
![[Pasted image 20251125123855.png]]

**Token 直接存储在 localStorage 中确实存在被其他程序读取并盗用登录状态的风险**，这是当前 Web 安全领域中一个被广泛讨论和重视的问题。
![[Pasted image 20260528210708.png]]

localStorage 是浏览器提供的一种客户端存储机制，它允许网页在用户的本地设备上持久化存储键值对数据。虽然它非常方便，但它的核心设计原则是“同源策略”，即只有与存储数据的页面具有相同协议、域名和端口的脚本才能访问这些数据。这意味着，从理论上讲，不同网站的脚本无法直接读取你的 localStorage。然而，这个“理论上的安全”在现实中极易被攻破，主要威胁来自于跨站脚本攻击。

如果网站本身存在 XSS 漏洞，或者你安装了恶意的浏览器扩展程序，那么攻击者就可以在你的浏览器上下文中执行任意 JavaScript 代码。由于这些恶意代码运行在与目标网站相同的“源”下，它们可以毫无障碍地调用 `localStorage.getItem('token')` 来窃取你的 Token。一旦 Token 被窃取，攻击者就可以将其用于伪造你的身份，向服务器发起请求，从而完全接管你的账户。

为了应对这一风险，业界普遍推荐更安全的替代方案：
- **使用 HttpOnly Cookie**：这是目前最主流且被广泛认可的最佳实践。后端在用户登录成功后，通过设置 `Set-Cookie` 响应头将 Token 写入 Cookie，并加上 `HttpOnly` 属性。这个属性会阻止任何 JavaScript 代码（包括恶意脚本）读取该 Cookie 的内容。浏览器会在每次向该域名发起请求时自动携带这个 Cookie，从而实现无感知的身份验证。这种方式从根本上杜绝了 XSS 攻击窃取 Token 的可能性。
- **配合 CSRF 防护**：使用 HttpOnly Cookie 会引入一个新的安全风险——跨站请求伪造。为了防止这一点，通常需要结合使用 CSRF Token 或 SameSite Cookie 属性等机制来确保请求的合法性。
- **缩短 Token 有效期**：无论采用哪种存储方式，都应尽量缩短 Token 的有效期。即使 Token 不幸泄露，其可被利用的时间窗口也会被大大压缩。
- **使用 Refresh Token 机制**：可以采用短生命周期的 Access Token 和长生命周期的 Refresh Token 组合。Access Token 用于日常 API 调用，过期后通过 Refresh Token 获取新的 Access Token。Refresh Token 应存储在更安全的地方（如 HttpOnly Cookie），并且在使用一次后即失效（Rotation）。

总而言之，虽然 localStorage 使用方便，但其安全性不足。对于涉及用户敏感信息和登录状态的 Token，强烈建议采用 HttpOnly Cookie 等更安全的存储方案，以最大限度地保护用户账户安全。
