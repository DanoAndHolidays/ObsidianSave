# 3次重构
> Last Format Time：8/13/2026 15:14:04

PR 54～56 是一组连续重构：先整理后端分层和测试，再迁移页面状态，最后统一 UI 组件并补强审查流程。本文记录这三次重构做了什么，以及后续开发应遵守的写法。

### PR 54：重建项目分层
- 页面、tRPC、Service、DAO、Repository 和 Schema 重新划分目录。
- tRPC Procedure 拆成独立单元，并统一通过 Service 访问业务能力。
- Service 使用依赖注入，错误通过 `neverthrow Result` 返回。
- DAO 和 Repository 的公开操作拆成独立 Operation，并为 Operation 增加测试。
- 页面专用组件迁回对应 Page 目录。
- 增加 Storybook、Product E2E、QA Smoke 和架构文档。

主要收益是职责更清楚、单元测试更容易写。主要问题是一次改动 2699 个文件，DAO、Repository 和 Service 出现过度拆分，阅读一个完整业务流程需要频繁跳转文件。该 PR 合并时 App 仍有 1043 个 lint 问题，真实 QA Smoke 也没有执行。

### PR 55：页面状态迁移到 Store
- 22 个页面新增或调整页面级 Zustand Store。
- 将分页、筛选、弹窗、导航和提交操作从组件迁入 Store。
- Store 通过 Dependencies 注入请求、导航、缓存和本地存储能力。
- 为测试和 Story 增加 Store Provider、Story Provider。
- 拆分 Project Detail、Scan Dialog 和部分 Refine DataProvider 代码。

主要收益是减少 Props 层层传递，页面组件更专注于展示。主要问题是部分 Store 变成新的大文件，例如一个 Slice 同时处理导航、翻译、表单、请求和 DOM 事件。DataProvider 也只拆出了 delete 和 custom 等部分能力，主文件仍然较大。

### PR 56：统一 UI 和审查流程
- 将 Button、Dialog、Select、Tabs 等统一迁入 `@repo/ui`。
- 使用 Base UI 提供键盘、焦点和无障碍基础能力。
- 为 UI 包增加独立 Storybook。
- 增加 Finding 跳转到项目文件和具体行的能力。
- 为审查 Agent 增加每次运行独立的工具调用预算，并为 `outputResults` 保留最后一次调用。
- 调整 MCP Scan、Job Detail 和 Project Detail。

主要收益是 UI 组件只有一个来源，审查结果定位代码更方便。主要问题是 UI 重构、MCP、Agent 执行策略和代码导航被放在同一个 PR 中，不便于审查和回滚。Agent 的最大步骤从 15 提高到 501，也需要继续评估成本和耗时。

## 统一分层
业务请求统一按下面的方向流动：
```text
React Page
  → Refine Hook
  → tRPC Procedure
  → Service
  → DAO / Repository
  → Drizzle
  → PostgreSQL
```
- UI 不直接调用 tRPC、DAO 或数据库。
- tRPC 只处理输入、权限和 Service 调用。
- Service 处理业务规则和返回数据组装。
- DAO 只处理单表读写。
- Repository 只处理需要事务的跨表写入。

## Schema 写法
### 目录和文件
- 在 `packages/schemas/src/<domain>/` 下按领域建目录，例如 `anatomy/`、`crate/`、`mcp/`。
- 一个 Zod Schema 使用一个 `<PascalCaseName>.schema.ts` 文件。
- 一个 Schema 文件只导出主 Schema 和对应的 `z.infer` 类型。
- 枚举值、纯类型和辅助函数使用独立文件。
- 领域 `index.ts` 和根 `index.ts` 只做 re-export。
- 业务代码统一从 `@repo/schemas` 导入，不跨目录读取内部文件。

目录示例：
```text
packages/schemas/src/crate/
├── Crate.schema.ts
├── CrateFormValues.schema.ts
├── CratePath.schema.ts
├── CrateTypeValues.ts
└── index.ts
```

类型必须从 Zod 推导：
```ts
import { z } from "zod/v4";

export const CrateSchema = z.object({
  id: z.string(),
  name: z.string(),
});

export type Crate = z.infer<typeof CrateSchema>;
```

禁止再创建聚合多个 Schema 的 `<domain>-schema.ts`，也不要手写一份与 Schema 重复的 `interface`。

## 数据访问写法
### DAO
- 放在 `packages/models/src/daos/<entity>Dao/`。
- 外层 DAO 是单例聚合对象，只组合 `_operations/` 中的操作。
- 每个 Operation 负责一个明确的单表操作。
- Operation 使用 Drizzle，不写原始 SQL，不处理业务判断。
- Operation 测试与实现放在同一目录。

目录示例：
```text
anatomiesDao/
├── anatomies.dao.ts
├── anatomies.dao.spec.ts
├── index.ts
└── _operations/
    └── createAnatomy/
        ├── createAnatomy.operation.ts
        ├── createAnatomy.operation.spec.ts
        └── index.ts
```

简单操作不要继续拆出更多 helper。只有查询或事务逻辑确实复杂时，才继续分解。

### Repository
- 放在 `packages/models/src/repositories/`。
- 只有一次操作需要写入多张表时才创建 Repository。
- 使用 `createXxxRepository(db)` 绑定数据库。
- 所有跨表写入放在同一个事务中。
- Repository 只返回关键标识，不组装页面需要的完整数据。
- 单表写入继续放在 DAO，不额外套一层 Repository。

### Service
- 放在 `packages/services/src/<Domain>Service/`。
- 使用 `createXxxService(dependencies)` 注入 DAO、Repository 或外部服务。
- Service 不直接导入 `db`，也不写 Drizzle 查询。
- Service 负责权限以外的业务校验、流程编排和返回数据组装。
- Service 返回 `Result<T, ServiceError>`，调用方必须处理成功和失败。
- 一个 Service 目录按业务能力拆 methods 和 helpers，但不要为了缩短文件而机械拆分。

## tRPC 写法
- 每个领域 Router 使用独立目录。
- Router 文件只聚合 Procedure，不写业务逻辑。
- Query 和 Mutation 分别放在 `_queryProcedures/`、`_mutationProcedures/`。
- 一个 Procedure 一个目录，包含实现、测试和 `index.ts`。
- Procedure 从 `ctx.services` 获取 Service。
- 使用统一方法解包 `neverthrow Result`。
- Procedure 不直接导入 `db`、DAO 或 Repository。

调用示例：
```ts
export const listProcedure = workspaceProcedure
  .input(ListInputSchema)
  .query(async ({ ctx, input }) => {
    const result = await ctx.services.anatomies.list({
      ...input,
      workspaceId: ctx.workspaceId,
    });

    return unwrapServiceResult(result);
  });
```

## 页面和组件写法
### 目录归属
- 路由文件只负责读取路由参数和挂载页面。
- 页面放在 `apps/app/src/pages/<PageName>/`。
- 页面专用组件放在对应页面的 `_components/`。
- App 内跨页面复用的业务组件放在 `apps/app/src/components/`。
- 基础 UI 组件统一放在 `packages/ui/src/`。
- 不要为了复用一次就把页面组件提升为全局组件。

### 组件单元
页面业务组件使用独立目录：
```text
ComponentName/
├── ComponentName.tsx
├── ComponentName.test.tsx
├── ComponentName.stories.tsx
└── index.ts
```
- 一个组件文件只放一个主组件。
- `index.ts` 只做 re-export。
- 组件优先负责展示，不在 JSX 中堆积请求和复杂数据处理。

### 页面 Store
- 全局状态放在 `apps/app/src/store/`。
- 页面状态放在 `pages/<PageName>/_store/`。
- 页面 Store 使用 Store、Slice、Provider 和 Dependencies 结构。
- 组件通过 selector 读取具体字段，不订阅整个 Store。
- Store 已有的数据和操作不要再通过多层 Props 传递。
- Store Action 接收 `id`、`value`、业务对象等数据，不接收 `MouseEvent`、`ChangeEvent` 等 React 事件。
- 组件负责从事件中取值，再调用 Store Action。
- 一个 Slice 同时负责列表、弹窗、编辑器等多类状态时，应按职责拆分。

推荐写法：
```tsx
const handleNameChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  setName(event.currentTarget.value);
};
```

不推荐把完整事件传入 Store：
```tsx
const handleNameChange = (event: React.ChangeEvent<HTMLInputElement>) => {
  pageStore.getState().handleNameChange(event);
};
```

## UI 组件写法
- Button、Select、Dialog、Input、Table 等标准控件统一使用 `@repo/ui`。
- 禁止在 App 中复制 `components/ui` 实现。
- 禁止使用原生 `<button>`、`<select>` 替代已有 UI 组件。
- 复合组件优先使用组合方式，不用一个组件接收大量配置对象。
- 新增 UI 组件时补充 Storybook 和关键交互测试。
- Select、Dialog 等弹层组件必须验证键盘操作、焦点、受控值和表单提交。
- `@repo/ui` 只提供通用交互和样式，不包含具体业务请求。

---
## 数据请求写法
- 页面组件使用 Refine 的 `useList`、`useOne`、`useCreate`、`useUpdate` 等 Hook。
- 使用 Refine DataProvider 封装 tRPC 调用。
- Loading 状态读取 Refine Hook 返回的 `query`，不要重复维护一份 loading state。
- 不在组件中直接调用 `trpcClient`。
- DataProvider 按资源或操作类型继续拆分，避免主文件持续增长。

---
## 错误和类型写法
- Zod 是数据类型的唯一来源，类型通过 `z.infer` 推导。
- 枚举值从 `@repo/schemas` 导入，不在页面和 Router 中重复写字符串数组。
- 仅用于类型的 import 使用 `import type`。
- Service 使用 `neverthrow Result` 表达错误。
- Service、Repository 和 DAO 不使用原生 `try-catch` 隐藏错误。
- 错误转换集中处理，不在每个 Procedure 重复写相同判断。

## 测试和 Storybook
- Component、Store、Procedure、Service、DAO Operation 都需要对应测试。
- 页面组件至少覆盖默认渲染、主要交互、Loading、Empty 和 Error 状态。
- UI 组件为主要变体提供 Story。
- 关键产品流程使用隔离数据运行 Product E2E。
- QA Smoke 只读访问真实环境，不写入生产数据。
- 合并前运行根目录 `bun run quality`；不能因为已有问题而默认跳过检查。

---
## Agent 工具预算
- 工具调用预算在一个位置定义，不在各工具中重复硬编码。
- 每次审查创建独立预算，运行之间不能共享计数。
- 必须为最终 `outputResults` 保留一次调用。
- `maxSteps` 与工具预算保持一致，当前为 501 steps 和 500 次工具调用。
- 后续应按单文件、PR、全仓扫描设置不同预算，避免小任务也允许 500 次调用。
- 达到预算时要明确记录原因，不能静默返回空结果。

## 后续需要收敛的问题
- DAO 和 Service 已拆得很细，新代码不要继续机械增加只有十几行的目录层级。
- 大型页面 Store 应按列表、筛选、弹窗、编辑器等职责拆分。
- Refine DataProvider 需要继续按资源拆分，不能只拆 delete 和 custom。
- UI、Agent、MCP、代码导航等不同类型的改动应使用不同 PR。
- Agent 工具预算应改成按扫描范围配置，并记录耗时和费用数据后再确定默认值。
