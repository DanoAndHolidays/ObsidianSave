### 第1题：把键盘意图映射到已有动作——5/5，通过
##### 本题验收

##### 答卷如何运行
```text
input 触发 keydown
→ handleCreateKeyDown 读取 event.key
→ Enter：void 调用 handleCreateTeamClick
→ Escape：调用 handleCloseCreateClick
→ 其他值：两个分支均不进入
```

##### 证据与等价性
```ts
if (event.key === "Enter") {
  void get().handleCreateTeamClick();
} else if (event.key === "Escape") {
  get().handleCloseCreateClick();
}
```

基线在 Escape 分支直接执行 `set({ createErrMsg: null, showCreate: false })`；答卷复用了已有的 `handleCloseCreateClick`，而该动作写入完全相同的状态，因此是行为等价实现。`else if` 与两个独立 `if` 也等价，因为一次键盘事件的 `key` 不可能同时等于两个字符串。

##### 分项评分
- 功能与边界：3/3
- 项目模式与接口：1.25/1.25
- 题内实现质量：0.75/0.75

`console.log` 不在此重复扣分；它和全卷 TODO、格式漂移统一在提交清理项审批。

##### 知识解析
`void promiseExpression` 不会取消异步任务，它只是明确丢弃表达式的返回值。因此创建仍会执行，但事件处理器维持 `void` 语义。直接写 `return get().handleCreateTeamClick()` 也未必立即破坏 React，但会改变函数签名和未处理拒绝的边界，不符合本题已有接口。

复用 `handleCloseCreateClick` 的价值不是少写两行，而是让“点击返回”和“按 Escape”共享同一业务动作。以后如果退出创建面板还需要重置别的状态，只改一个动作即可。

- 功能与边界：3/3
- 项目模式与接口：1.25/1.25
- 题内实现质量：0.75/0.75

##### 知识解析：浅合并到哪一层
Zustand 对象式 `set` 默认只合并顶层：

```text
{ createName: "", createErrMsg: "必填", menuOpen: true }
       + set({ createName: "A", createErrMsg: null })
→ { createName: "A", createErrMsg: null, menuOpen: true }
```

如果状态是嵌套对象：
```ts
form: { name: "old", error: "必填" }
```

执行 `set({ form: { name: "A" } })` 会整体替换顶层 `form`，不会递归保留 `error`。要保留它，需要显式展开：
```ts
set((state) => ({
  form: { ...state.form, name: "A" },
}));
```

关键不是“使用更新函数就自动深合并”，而是更新函数让你能读取 `state.form`，真正保留字段的是 `...state.form`。

##### 失分点
无失分点。

##### 迁移规则与自检
规则：顶层独立字段直接传补丁；嵌套对象先判断是“整体替换”还是“局部保留”。

自检：更新前后读取 `store.getState()`，同时断言 `createName`、`createErrMsg` 和未修改的 `menuOpen`。

### 第4题：串联刷新并保留创建结果——10/10，通过
##### 本题验收
创建成功后才能刷新；刷新失败应进入统一错误分支并阻止选中；刷新成功后，下游仍需拿到创建阶段产生的 `team.id`。

##### 答卷如何运行
```text
createTeam 成功得到 team
→ andThen 执行 refreshWorkspaces
→ refresh 失败：ResultAsync 进入 Err，跳过成功 match
→ refresh 成功：其 void 被 map 成原 team
→ match 成功回调收到 team
```

##### 证据与等价性
```ts
return ResultAsync.fromPromise(
  dependencies.refreshWorkspaces(),
  (cause) => cause,
).map(() => team);
```

与基线行为完全等价。运行检查得到成功顺序 `create:Alpha|refresh|select:team-1`，刷新失败顺序只有 `create:Alpha|refresh`。

##### 分项评分
- 功能与边界：6/6
- 项目模式与接口：2.5/2.5
- 题内实现质量：1.5/1.5

##### 知识解析：为什么要把 `void` 映射回 `team`
`ResultAsync<T, E>` 同时携带成功值类型 `T` 和失败值类型 `E`。`refreshWorkspaces()` 的 Promise 成功时没有业务返回值，所以包装后成功类型是 `void`。如果直接返回它，整条链成功值会变成 `void`，后面的 `match` 无法读取 `team.id`。

`.map(() => team)` 不会重新执行创建，也不会吞掉刷新错误；它只在刷新成功时把成功值从 `undefined` 转换回闭包中的 `team`。

直接返回原生 Promise 不是当前 `andThen` 的等价局部替换，因为 `andThen` 需要 `Result/ResultAsync` 才能保持统一错误通道。如果整体改成 `async/await + try/catch`，可以实现等价行为，但需要完整接管错误分支：

```ts
const team = await dependencies.createTeam(trimmed);
await dependencies.refreshWorkspaces();
dependencies.selectWorkspace(team.id);
```

这只是另一套控制流，并非标准答案才成立。

##### 失分点
无功能失分。答卷明确参考过答案，因此代码正确计满功能分，但独立掌握程度由后面的掌握验证单独评价。

##### 迁移规则与自检
规则：连接每个异步步骤时都问：“这一阶段成功值是什么？下一阶段需要什么？”不一致时使用 `map` 或显式变量保留业务实体。

自检：IDE 悬停 `match` 的成功参数；若变成 `void`，说明上游丢失了需要的值。再模拟刷新 rejected，确认 select 不调用。

##### 分项评分

- 项目模式与接口：3.75/3.75
- 题内实现质量：2.25/2.25

##### 知识解析：统一收束点
把 `set({ creating: false })` 放在 `await ...match(...)` 之后，等于为成功和失败提供共同的完成阶段。这样两个 match 回调只处理各自差异：成功负责选中和关闭，失败负责错误反馈。

```ts
set({ creating: true });
try {
  await operation;
} finally {
  set({ creating: false });
}
```

本题依赖回调都是同步且简单，当前实现满足验收，不因没有使用 `finally` 扣分。

##### 失分点
无失分点。`"错误"` 可以作为“建议改进：让错误更具体”，但不能仅因和基线文案不同扣分。

##### 迁移规则与自检
规则：先列成功与失败的差异状态，再找两条路径共有的结束状态；共有状态放到统一收束点或 `finally`。

自检：分别让 create、refresh reject，断言 select 不调用、面板仍显示、错误可见、`creating === false`。


### 第6题：为 Provider 创建稳定 Store 实例——5/5，通过
##### 本题验收
Provider 在一次挂载生命周期中只创建一个 Store，并把构造依赖注入其中；父组件普通重渲染不能重置 `menuOpen/createName`。

##### 答卷如何运行
```text
Provider 首次渲染
→ useInit 检查内部 ref 为空
→ createWorkspaceSwitcherStore(dependencies)
→ Store 放进 ref 并提供给 Context
→ 后续渲染直接返回 ref 中同一 Store
```

##### 证据与等价性
```ts
const store = useInit(() => createWorkspaceSwitcherStore(dependencies));
```

与基线等价，接口和生命周期均正确。

##### 分项评分
- 功能与边界：3/3
- 项目模式与接口：1.25/1.25
- 题内实现质量：0.75/0.75

##### 知识解析
如果在组件函数体中直接执行 `createWorkspaceSwitcherStore(dependencies)`，每次渲染都会产生新 Store；Context 的 `value` 随之替换，消费者会看到初始状态，用户正在输入的名称可能丢失。

`useInit` 用 `useRef` 保存首次计算值。它与 `useMemo(..., [])` 目标相似，但语义更明确：这是实例初始化，不是性能缓存。当前实现还意味着后续 `dependencies` 引用变化不会重建 Store；这是该架构刻意的生命周期选择。若业务要求动态更换依赖，应通过 Store action 更新依赖或以 `key` 重挂 Provider，不能期待 `useInit` 自动响应。

##### 失分点
无失分点。

##### 迁移规则与自检
规则：组件拥有的可变外部实例（Store、客户端、控制器）通常需要“每次挂载一个”，而不是“每次渲染一个”。

自检：保存首次 Store 引用，触发父组件重渲染，再用引用相等和状态保留断言验证。

```text

→ useSyncExternalStore 调用 subscribe
→ menuOpen=true 时注册 handler
→ mousedown：ref.contains 判断内外
→ subscribe 返回 removeEventListener
→ 依赖变化或卸载时 useSyncExternalStore 调用返回函数
```

##### 证据与等价性
```ts
const handler = (event: MouseEvent) => {
  if (ref.current && !ref.current.contains(event.target as Node)) {
    closeMenu();
  }
};
if (menuOpen) document.addEventListener("mousedown", handler);
return () => document.removeEventListener("mousedown", handler);
```

答卷使用单行 `if`、省略分号，与基线风格不同但行为等价。add/remove 共享同一个词法作用域里的 `handler` 引用，这是清理成立的关键。

##### 分项评分
- 功能与边界：6/6
- 项目模式与接口：2.5/2.5
- 题内实现质量：1.5/1.5

##### 知识解析：到底哪个 Hook 有 cleanup
`useCallback` 没有 cleanup 协议。它只根据依赖返回稳定的函数引用，既不会自动调用这个函数，也不会处理函数的返回值。

本题真正的消费者是 `useSyncExternalStore`：

```text
useCallback 产生 subscribe
→ useExternalSubscription 包装为 normalizedSubscribe
→ useSyncExternalStore 调用 normalizedSubscribe
→ subscribe 返回 unsubscribe
→ React 在重订阅或卸载时调用 unsubscribe
```

[[useExternalSubscription]]

常见 Hook 对比：

- `useEffect` / `useLayoutEffect`：React 把 effect 回调的返回函数当 cleanup；下一次 effect 前和卸载时调用。
- `useCallback`：缓存函数引用，没有自动 cleanup。
- `useMemo`：缓存计算结果，不应用来承载副作用。
- `useSyncExternalStore`：调用 `subscribe`，把其返回函数当 unsubscribe。

“对称清理”要求目标、事件类型、捕获配置和 handler 引用对应。下面的写法无法清掉旧监听器，因为两个箭头函数不是同一引用：

```ts
document.addEventListener("mousedown", () => closeMenu());
return () => document.removeEventListener("mousedown", () => closeMenu());
```

##### 失分点
无功能失分。答卷明确说明参考了答案，代码仍按行为计满分；答辩未完整解释 `useSyncExternalStore` 的角色，因此独立掌握分另行保守评分。

##### 迁移规则与自检
规则：看到回调“返回一个函数”时，不要凭位置猜它是 cleanup；查看接收这个回调的 API 契约，确认谁负责调用返回值。

自检：spy `document.addEventListener/removeEventListener`，反复开关菜单，比较次数、事件名和 handler 引用；再点击内部与外部节点验证 contains 分支。

##### 知识解析：受控输入的闭环
受控输入的 `value` 不从 DOM 自己维护，而来自 React/Store 状态。用户键入不会直接成为长期界面真值；`onChange` 必须把值写回状态，下一次渲染再把状态送回 `value`。

缺少任一环都会断链：

- 只有 `value` 没有 `onChange`：输入看起来不可编辑；
- 只有 `onChange` 没有 `value`：DOM 自己保存值，Store reset 不一定反映到界面；
- 没有 `disabled={creating}`：请求期间用户可继续改名，界面显示值和已提交值可能不同。

##### 失分点
无失分点。

##### 迁移规则与自检
规则：检查受控组件时沿“状态 → value → 用户事件 → action → 状态”画闭环，再检查 pending/disabled 是否阻止不一致操作。

自检：输入名称后读取 Store；调用 `setState` 重置名称观察 UI；把 `creating` 设为 true 确认输入无法编辑。
