# 浏览器安全策略
### 同源策略（ Same-origin policy ）
这是浏览器最基础也是最核心的安全机制。它要求“协议、域名、端口”三者完全相同才算作同源。同源策略严格限制了不同源之间的交互，防止恶意站点窃取敏感数据，具体限制包括：

- **DOM访问限制**：禁止跨源的脚本读取或修改彼此的页面DOM内容（例如通过iframe嵌入的页面）。
- **网络请求限制**：默认禁止跨域的AJAX请求（XMLHttpRequest/Fetch API），防止前端脚本向其他网站发送请求并获取响应结果。
- **存储隔离**：不同源的站点无法共享Cookie、LocalStorage、IndexedDB等客户端存储数据。

严格来说，“同一站点”是基于域名的可注册域（或称为 eTLD+1，即公共后缀列表中的一个条目加上它前面的域名部分）来确定的。只要两个 URL 的可注册域相同，它们就被视为同一个站点。在判定过程中：

- 忽略子域名和端口：不同的子域名（如 app.example.com 和 api.example.com）以及不同的端口号不影响同站点的判定。
- 考虑协议（Scheme）：在现代浏览器的安全策略下，通常会考虑协议。这意味着 http://example.com 和 https://example.com 可能会被视为不同的站点（这被称为 Schemeful Same-Site），以防止不安全的 HTTP 站点被误认为与安全的 HTTPS 站点属于同一站点。

### 网络安全（SSL/TLS）
https://developer.mozilla.org/zh-CN/docs/Glossary/TLS
**传输层安全性协议**（Transport Layer Security，缩写作 TLS），前身安全套接层（Secure Sockets Layer，缩写作 SSL），是一个被应用程序用来在网络中安全通信的[协议](https://developer.mozilla.org/zh-CN/docs/Glossary/Protocol)，防止电子邮件、网页、消息以及其他协议被篡改或是窃听。TLS 和 SSL 都是客户端/服务器协议，通过使用加密协议来提供网络安全。当服务器和客户端使用 TLS 通信时，它确保没有第三方可以窃听或篡改任何消息。

**SSL**（Secure Sockets Layer，安全套接层）是旧的标准安全技术，用于在服务器和客户端之间创建加密的网络链路，确保传递的所有数据都是私密且安全的。SSL 的当前版本是 Netscape 于 1996 年发布的 3.0 版本，已被 [TLS](https://developer.mozilla.org/zh-CN/docs/Glossary/TLS) 协议取代。

随着 web 的发展，http 的功能越来越不够用，伴随着功能上的完善，网络安全问题也成为重要研究对象。http 的风险有三点：
- 窃听风险：第三方可以获知通信内容
- 篡改风险：第三方可以修改通信内容
- 冒充风险：第三方可以冒充他人身份参与通信

TCP 和 HTTP 之间被插入一个安全层，所有经过的数据会被加密／解密。
![](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/db907e33a59c47c5840958f93d6962cf~tplv-k3u1fbpfcp-zoom-in-crop-mark:1512:0:0:0.awebp)

接入了安全层的 http 变成了 https ，它的特点有：
- 所有信息都是加密传播，第三方无法窃听。
- 具有校验机制，一旦被篡改，通信双方会立刻发现。
- 配备身份证书，防止身份被冒充。

##### https 加密过程
HTTPS（超文本传输安全协议）通过在 HTTP 的基础上引入 SSL/TLS 协议，实现了网络数据的加密传输和身份认证。其核心加密过程通常被称为“TLS握手”，巧妙地结合了非对称加密、对称加密以及数字证书来保障通信的安全与高效。具体的加密过程可以划分为以下几个关键阶段：
![](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/7c7772fc6b7b42daa58a7683ecb6fcba~tplv-k3u1fbpfcp-zoom-in-crop-mark:1512:0:0:0.awebp)

**1. 客户端发起请求（Client Hello）**  
当浏览器访问一个 HTTPS 网站时，会向服务器发送一个打招呼的消息。该消息中包含了客户端支持的 TLS 版本、加密算法列表，以及一个由客户端生成的随机数（Client Random）。

**2. 服务器响应与证书下发（Server Hello）**  
服务器收到请求后，会从客户端支持的算法列表中挑选出双方都支持且安全性最高的加密套件。随后，服务器生成自己的随机数（Server Random），并将其连同服务器的数字证书（包含服务器的公钥）一起发送给客户端。

**3. 客户端验证证书**  
浏览器接收到证书后，会进行严格的合法性校验。这包括检查证书是否过期、域名是否匹配，以及最重要的——通过内置的受信任 CA（证书颁发机构）根证书的公钥来验证签名，确保该证书未被篡改且来源可靠。如果验证失败，浏览器通常会弹出安全警告；若验证通过，则继续后续步骤。

**4. 密钥交换（预主密钥生成与加密）**  
证书验证通过后，客户端会生成第三个随机数，称为“预主密钥”（Pre-Master Secret）。为了防止被窃听，客户端会使用刚刚从服务器证书中获取的公钥，对这个预主密钥进行非对称加密，并将加密后的密文发送给服务器。

**5. 服务器解密并生成会话密钥**  
服务器收到密文后，使用自己严格保管的私钥进行解密，从而获取到相同的预主密钥。此时，客户端和服务器双方都已经拥有了这三个随机数（客户端随机数、服务器随机数、预主密钥）。双方会根据预先协商好的算法，利用这三个随机数独立计算出完全相同的“会话密钥”（Session Key）。

**6. 建立加密通信通道**  
握手完成后，后续的 HTTP 数据传输将全面切换到对称加密模式。无论是客户端发送的请求还是服务器返回的响应，都会使用这个共享的会话密钥进行快速的对称加密和解密。由于对称加密的计算开销远小于非对称加密，这种方式既保证了极高的安全性，又兼顾了网页加载等大数据量传输的效率。

总结来说，HTTPS 的加密过程就是先用非对称加密安全地传递一把“临时钥匙”（会话密钥），然后再用这把“临时钥匙”走对称加密来高效地传输实际数据，完美平衡了安全性与性能。

一个重要的规则是，公钥加密的数据只有私钥能解密。

公钥是明文的，黑客容易破解，但私钥只有服务器有，而 pre-master 是公钥加密生成的，因此只有服务器能破解。最终的 master secret 有了 pre-master 的参与，数据发送和接受了都很安全。

而且，只需要进行一次非对称加密就可以了，传输效率也比较高。

当然，黑客服务器自己生产公钥私钥，客户端可能进入假的页面。服务器怎么证明自己是真实合法的呢？数字证书。

### 常见攻击
##### XSS 跨站脚本攻击
Server对用户输入的数据没有进行严格的过滤，导致出现了意外的脚本语句被执行。主要就是通过URL与输入框来进行脚本的注入。

三种常用的 XSS 攻击方法：

- 存储型，利用内容管理系统的漏洞，比如评论，编辑文章，向服务器发送了恶意代码，将恶意代码存储在Server中，其他的用户加载这些存有恶意代码的评论、文章就会受到攻击：

![](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/0118e4e7ef0f4f9593a62eb8e59f9788~tplv-k3u1fbpfcp-zoom-in-crop-mark:1512:0:0:0.awebp)

- 反射型，与存储型 xss 攻击不同的是，服务器不存储恶意代码，服务端会将恶意代码再次传回前端，这时恶意代码就会存在于用户的界面中，有可能会被执行：

- 基于 DOM 的攻击，和反射型很像，但仅在前端运行，并不会提交到后端再返回来：
![](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/5c874a5d84cf4062a4f49ed179f71eff~tplv-k3u1fbpfcp-zoom-in-crop-mark:1512:0:0:0.awebp)

**阻止 XSS 攻击**
- 服务器对输入的脚本进行过滤／转码
- 使用 CSP （内容安全策略）让服务器决定浏览器可以加载哪些资源，执行哪些脚本。

##### CSRF 跨站请求伪造攻击
![](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/84281f9c78744c02835771c7232ba8a0~tplv-k3u1fbpfcp-zoom-in-crop-mark:1512:0:0:0.awebp)

CSRF 攻击利用用户的登录状态和服务器的漏洞。通过链接或者其他方式，伪装成用户请求信息来发送请求到服务器，这样就可以顶替用户的信息来修改或者破坏网站，比如自动转发邮件，转账等等，但是有两个前提：
1、服务端有漏洞；
2、用户要点击黑客页面的链接。

**防止 CSRF 攻击**
我们需要提升服务器的安全性。
- 从第三方站点发送请求时，==禁止发送 Cookie== —— set-cookie 中设置 SameSite 为 Strict
- 验证请求的来源站点 —— 通过 ==Request Header: Referer || Origin==
- CSRF Token 验证，服务器要求所有请求必须携带 CSRF ==Token== ，第三方无法拿到 Token ，伪造的请求会被拒绝访问
